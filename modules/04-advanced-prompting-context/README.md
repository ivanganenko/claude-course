# Модуль 04. Продвинутые prompts и управление контекстом

> **Зачем:** реальные задачи редко решаются одним prompt. В этом модуле ты научишься разбивать большую работу на шаги, планировать вместе с Claude, проверять качество и управлять context так, чтобы длинная работа не превращалась в «Claude всё забыл и запутался». **Время:** ~3–4 ч. **Нужно:** модули 01–03; папка `~/claude-practice`; файлы из `practice/texts/`.

## Что ты будешь уметь

- разбивать сложную задачу на цепочку prompts, где каждый шаг сохраняет результат в файл;
- просить Claude сначала задать уточняющие вопросы или составить план — и проверять план до выполнения;
- использовать plan mode в Claude Code;
- задавать критерии качества и давать обратную связь, которая реально улучшает результат;
- выбирать между `/clear`, `/compact` и новой сессией и следить за context через `/context`;
- работать с большими документами и собрать свою библиотеку prompt-шаблонов в файлах.

## 1. Декомпозиция и prompt chaining

Большая задача в одном prompt — это много целей одновременно: прочитать, понять, отобрать, проанализировать, написать. Модель делает всё сразу и везде понемногу недорабатывает.

**Prompt chaining** (цепочка prompts) — разбиение задачи на последовательные шаги, где результат одного шага — вход для следующего.

Пример: подготовить служебную записку директору по квартальному отчёту.

```text
Шаг 1. Извлечение     →  facts.md      факты, цифры и цитаты из отчёта по темам
Шаг 2. Анализ         →  analysis.md   проблемы, причины, противоречия — только по facts.md
Шаг 3. Текст          →  memo.md       записка для директора — только по analysis.md
```

Каждый шаг проще проверить: в `facts.md` ты сверяешь цифры с отчётом, в `analysis.md` — логику, в `memo.md` — тон и формат. Ошибку видно сразу там, где она появилась.

**В Claude Code результаты шагов храни в файлах.** Тогда:
- шаг можно перезапустить отдельно, не повторяя предыдущие;
- между шагами можно сделать `/clear` — следующий шаг возьмёт всё нужное из файла, а context останется чистым;
- ты можешь поправить промежуточный файл руками, если Claude ошибся.

Когда декомпозиция нужна:
- результат проверяется по частям (данные → выводы → текст);
- у шагов разные «режимы»: точное извлечение vs творческий текст;
- задача большая, и одним заходом получается поверхностно.

Когда не нужна: короткая задача, которую Claude стабильно делает с первого раза.

> **Почему так?** Каждый шаг получает одну цель и только нужные данные — модель фокусируется лучше. А промежуточные файлы превращают «чёрный ящик» в конвейер, где можно найти, на каком шаге возникла ошибка. Цена — больше запросов и твоего времени на проверку, поэтому декомпозируй, когда задача этого стоит.

## 2. «Сначала спроси»: уточняющие вопросы

Часто ты сам не до конца понимаешь, что нужно, — или не знаешь, какой контекст важен. Тогда попроси Claude **провести интервью**:

```text
Мне нужно составить регламент работы отдельной очереди поддержки для клиентов «Премиум».
Прежде чем писать, задай мне вопросы, которые нужны для хорошего регламента
(не больше 7, самые важные первыми). Не начинай писать, пока я не отвечу.
```

Что получаешь:
- Claude показывает, *какая информация важна* для задачи — часто это то, о чём ты не подумал (кто дежурит в выходные? что считать «первым ответом»?);
- ты отвечаешь коротко — это быстрее, чем писать подробный prompt с нуля;
- итоговый результат опирается на твои ответы, а не на догадки.

Варианты:
- «Задавай вопросы по одному, пока не будешь уверен, что понял задачу» — для сложных тем;
- «Если на какой-то вопрос я отвечу "не знаю", предложи разумный вариант по умолчанию и отметь его» — чтобы не застревать.

> **Почему так?** Без вопросов модель заполняет пробелы самыми «средними» предположениями — и ты узнаёшь о них, только прочитав результат. Интервью переносит эти предположения *до* выполнения, где их дешевле исправить. Компромисс — лишний раунд диалога, поэтому для простых задач это избыточно.

## 3. План → проверка → выполнение. Plan mode

Для задач, где Claude будет менять файлы или выполнять много действий, полезно разделить работу:

1. **План** — Claude изучает ситуацию и предлагает, что и в каком порядке сделать.
2. **Проверка** — ты читаешь план, задаёшь вопросы, правишь.
3. **Выполнение** — только после твоего «да».

Можно просто попросить: «Сначала предложи план, ничего не меняй». Но в Claude Code для этого есть специальный режим — **plan mode**:

- включается через **Shift+Tab** (режимы переключаются по кругу: `default` → `acceptEdits` → `plan`; следи за индикатором под полем ввода);
- в plan mode Claude **только читает** файлы и исследует, но не меняет их и не выполняет изменяющие команды;
- в конце он предлагает план, и ты решаешь: доработать план или перейти к выполнению (выход из plan mode — снова Shift+Tab или подтверждение плана; конкретный интерфейс зависит от версии).

Что проверять в плане:

| Вопрос | Пример проблемы |
|--------|-----------------|
| Правильно ли понята цель? | ты просил сводку для менеджеров, а план — про графики для директора |
| Какие файлы будут изменены? | в плане правка исходных данных, которые трогать нельзя |
| Есть ли шаг проверки? | скрипт напишут, но не запустят |
| Нет ли лишнего? | «заодно переименую все файлы» |
| Какие предположения сделаны? | «считаю, что пустой менеджер — ошибка, удалю строку» |

Если план не устраивает — скажи, что изменить, и попроси обновлённый план. Это дешевле, чем откатывать изменения.

> **Почему так?** Ошибка в плане стоит одного сообщения, ошибка в выполнении — откатов, перепроверок и потерянного времени. Plan mode гарантирует, что на этапе обсуждения ничего не изменится, — можно спокойно исследовать и спорить. Для мелких правок план избыточен: это инструмент для задач, где больше 2–3 шагов или есть риск что-то сломать.

## 4. Критерии качества, самопроверка и итерации

**Критерии качества** — явный список того, каким должен быть хороший результат. Их стоит писать в prompt, а не держать в голове:

```text
Критерии хорошего ответа клиенту:
1. В первом абзаце — признание проблемы и что мы уже делаем.
2. Ни одного обещания, которого нет в <facts> (сроки, суммы, бесплатные услуги).
3. Не длиннее 120 слов.
4. Есть конкретный следующий шаг: кто и когда свяжется.
5. Тон — спокойный, без канцелярита и без оправданий.
```

**Самопроверка**: попроси Claude после выполнения проверить результат по критериям и исправить найденное:

```text
После того как напишешь письмо, проверь его по каждому критерию (✅/❌ + почему).
Если есть ❌ — исправь письмо и покажи итоговую версию.
```

Самопроверка ловит многие ошибки (длина, забытый пункт, лишнее обещание), но **не заменяет твою проверку**: модель может «проверить» и не заметить свою же ошибку. Особенно — фактические ошибки.

**Итерации и обратная связь.** Первый результат почти никогда не финальный. Разница между хорошей и плохой обратной связью:

| Плохая обратная связь | Хорошая обратная связь |
|-----------------------|------------------------|
| «Не то, переделай» | «Второй абзац звучит как оправдание. Убери объяснение причин, оставь только решение» |
| «Сделай лучше» | «Слишком формально: замени "в рамках" и "осуществить" на простые слова» |
| «Короче» | «Сократи до 80 слов, сохранив пункты 1 и 4 из критериев» |

Хорошая обратная связь говорит **что** не так, **где**, и **каким** должно быть. Если одну и ту же правку приходится делать снова и снова — перенеси её в prompt (или в шаблон, или в `CLAUDE.md` — модуль 06).

> **Почему так?** Критерии делают «хорошо» проверяемым — и для Claude, и для тебя. Без них самопроверка превращается в «всё отлично», а обратная связь — в угадывание. Конкретный фидбек работает по тому же принципу, что и хороший prompt: чем меньше модели нужно угадывать, тем точнее результат.

## 5. Управление контекстом

### Почему длинная сессия деградирует

Вспомни модуль 01: context window — это всё, что модель видит за раз. В длинной сессии туда копится:
- прочитанные файлы, которые уже не нужны;
- неудачные попытки и отменённые решения («давай так… нет, лучше по-другому»);
- обсуждения других задач.

Последствия: Claude начинает опираться на устаревшие договорённости, путает версии файлов, «забывает» детали из начала разговора, отвечает медленнее. Даже если окно не заполнено, лишняя информация размывает внимание модели.

### Инструменты

| Инструмент | Что делает | Когда использовать |
|------------|-----------|--------------------|
| `/context` | показывает, чем и насколько занят context | регулярно в длинной работе; перед большой задачей |
| `/clear` | полностью очищает историю разговора (файлы не трогает) | переход к **новой, не связанной** задаче; Claude «запутался» |
| `/compact [инструкции]` | сжимает историю в краткое резюме и продолжает с ним | задача **та же**, но история разрослась; важно сохранить решения |
| новая сессия (`claude` заново) | чистый старт; старую можно вернуть через `/resume` | новый день / другая задача; хочешь сохранить старую сессию как есть |

**`/compact` с инструкциями** — говоришь, что важно сохранить:

```text
/compact Сохрани: принятые решения по формату отчёта, список созданных файлов
и открытые вопросы. Обсуждение отклонённых вариантов можно отбросить.
```

Без инструкций Claude сам решает, что важно, — и может выбросить нужную деталь.

Claude Code также умеет **автоматически** сжимать историю, когда context приближается к пределу. Но лучше делать это самому в удобный момент (после завершения этапа), а не посреди сложной правки.

**Главное правило:** состояние работы храни в **файлах**, а не в истории чата. План — в `plan.md`, решения — в `decisions.md`, промежуточные результаты — в файлах шагов. Тогда `/clear` ничего не ломает: новая сессия прочитает файлы и продолжит.

> **Почему так?** Context — общий ресурс для всего: инструкций, данных, истории и ответа. Сжатие и очистка освобождают место и убирают «шум», но любое сжатие теряет детали. Файлы — единственная память, которая не сжимается и не теряется; это тот же принцип, по которому агент-преподаватель ведёт `PROGRESS.md`.

## 6. Большие документы и работа с файлами

### Порядок: документ сверху, вопрос внизу

Когда вставляешь большой документ в prompt, ставь его **в начало**, а инструкции и вопрос — **в конец**. Длинный текст между вопросом и ответом «отодвигает» вопрос, и модель хуже ему следует.

```text
<document name="report.md">
… длинный текст …
</document>

Вопрос: …
Инструкции по формату: …
```

### Сначала цитаты, потом ответ

Для вопросов по большому документу попроси Claude **сначала выписать релевантные цитаты**, а потом отвечать только на их основе:

```text
Сначала найди в документе фрагменты, которые относятся к вопросу, и выпиши их
дословно в <quotes>. Затем ответь на вопрос в <answer>, опираясь только на эти цитаты.
Если подходящих цитат нет — напиши в <answer> «в документе нет ответа».
```

Это сочетает два приёма из модуля 03 — рассуждение перед ответом и проверяемость. Модель сначала «собирает» нужное из длинного текста, а ты видишь, на чём основан ответ.

### Файлы вместо копипаста

В Claude Code почти никогда не нужно копировать текст в сообщение:
- `@report.md` — подставить файл целиком;
- «Найди в папке `contracts/` все упоминания штрафов» — Claude сам найдёт нужные файлы и фрагменты (tools Glob и Grep) и прочитает только их;
- для очень больших файлов — «прочитай только раздел 5» или «найди строки со словом …».

Преимущества: не теряется форматирование, нет ошибок копирования, Claude знает имя и путь файла (может сослаться на него и вернуться к нему), а в context попадает только нужное.

> **Почему так?** Чем больше документ, тем выше риск, что модель упустит деталь или «подмешает» правдоподобное. Цитаты сужают фокус до релевантного текста и делают ответ проверяемым. Работа с файлами экономит context: агент читает нужные части, а не всё подряд.

## 7. Prompt как переиспользуемый шаблон

К этому моменту у тебя есть удачные prompts: извлечение задач из заметок, классификация писем, цепочка анализа отчёта. Не теряй их в истории чатов — **собери библиотеку в файлах**:

```text
~/claude-practice/prompts/
  README.md                 ← оглавление: какой шаблон для чего
  meeting-tasks.md          ← заметки встречи → таблица задач
  email-triage.md           ← классификация писем (few-shot)
  report-chain-1-facts.md   ← цепочка анализа: шаг 1
  report-chain-2-analysis.md
  report-chain-3-memo.md
  weekly-status.md          ← твой шаблон из модуля 03
```

Как пользоваться в Claude Code:

```text
Выполни шаблон @prompts/meeting-tasks.md для заметок @notes/2026-10-08.txt
```

Правила хорошей библиотеки:
- **одна задача — один файл**, имя говорит, что делает шаблон;
- в начале файла — **когда использовать** и **что подставить**;
- места для данных отмечены одинаково (`{{ДАННЫЕ}}`);
- внизу — **история версий**: что поменял и почему (иначе через месяц не вспомнишь, зачем там странное правило).

Это прямая дорога к следующим модулям:
- постоянные правила проекта (формат, стиль, запреты) переедут в `CLAUDE.md` — **модуль 06**;
- самые полезные шаблоны станут **skills** — Claude Code сможет вызывать их командой `/имя` или сам, когда задача подходит, — **модуль 07**.

> **Почему так?** Хороший prompt — это знание о том, как правильно поставить задачу. В голове или в истории чата оно теряется; в файле его можно улучшать, делиться с коллегами и использовать повторно. Библиотека превращает разовые удачи в рабочий инструмент.

## Шпаргалка

**Приёмы**

| Ситуация | Приём | Фраза-заготовка |
|----------|-------|-----------------|
| большая задача | цепочка prompts, результаты в файлах | «Шаг 1: извлеки … в `facts.md`. Больше ничего не делай» |
| непонятно, что нужно | интервью | «Прежде чем делать, задай до 7 вопросов. Не начинай, пока не отвечу» |
| много изменений файлов | plan mode (Shift+Tab) | «Изучи … и предложи план. Какие файлы изменишь? Как проверишь?» |
| важно качество | критерии + самопроверка | «Проверь результат по каждому критерию (✅/❌), исправь ❌» |
| результат «не то» | конкретная обратная связь | «В абзаце N — проблема X. Сделай Y» |
| большой документ | документ сверху, цитаты, потом ответ | «Выпиши цитаты в `<quotes>`, ответь в `<answer>` только по ним» |
| повторяющаяся задача | шаблон в `prompts/` | «Выполни @prompts/… для @данные» |

**Context**

| Команда | Когда |
|---------|-------|
| `/context` | проверить, чем занят context |
| `/clear` | новая, не связанная задача; Claude запутался |
| `/compact [что сохранить]` | та же задача, история разрослась |
| новая сессия / `/resume` | новый день, другая задача; вернуться к старой |
| файлы `plan.md`, `decisions.md` | хранить состояние работы вне чата |

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| decomposition | разбиение большой задачи на шаги |
| prompt chaining | цепочка prompts, где выход шага — вход следующего |
| plan mode | режим Claude Code: только чтение и план, без изменений |
| критерии качества (success criteria) | явный список признаков хорошего результата |
| self-check | самопроверка модели по критериям |
| iteration | цикл «результат → обратная связь → улучшение» |
| context degradation | ухудшение ответов в длинной сессии из-за «шума» в context |
| `/compact` | сжатие истории сессии в резюме |
| auto-compaction | автоматическое сжатие истории при приближении к лимиту |
| prompt library | набор шаблонов prompts в файлах |
| skill | упакованный шаблон/процесс, который Claude Code вызывает командой или сам (модуль 07) |

## Вопросы для самопроверки

1. Почему цепочка из трёх prompts часто даёт лучший результат, чем один большой prompt? Когда цепочка не нужна?
2. Зачем в цепочке сохранять результат каждого шага в файл?
3. В каких ситуациях стоит попросить Claude сначала задать уточняющие вопросы?
4. Что Claude может и чего не может делать в plan mode? Что ты проверяешь в плане?
5. Почему самопроверка по критериям не заменяет твою проверку?
6. Чем отличаются `/clear`, `/compact` и новая сессия? Приведи ситуацию для каждого.
7. Почему длинная сессия может давать худшие ответы, даже если context window не заполнен?
