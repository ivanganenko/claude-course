# Модуль 07. Skills

> **Зачем:** упаковать повторяющиеся процессы — «сделай commit message», «подготовь отчёт», «проверь упражнение» — в skills, которые Claude выполняет одинаково хорошо каждый раз. **Время:** ~3–4 ч. **Нужно:** пройдены модули 05–06; todo-app под git с CLAUDE.md.

## Что ты будешь уметь

- Объяснять, из чего состоит skill и где он лежит.
- Создавать skills с frontmatter, аргументами и динамическим контекстом.
- Подключать к skill скрипты и шаблоны так, чтобы они не тратили context зря.
- Писать `description`, по которому Claude сам понимает, когда применить skill, и чинить его, когда skill не срабатывает.
- Выбирать между skill, CLAUDE.md и обычным prompt-шаблоном.

## 1. Что такое skill

Skill (навык) — это **папка с файлом `SKILL.md`**, в котором записана инструкция для Claude: как выполнить определённую задачу. Рядом могут лежать скрипты, шаблоны, примеры.

```text
.claude/skills/
  commit-message/
    SKILL.md            ← инструкция + frontmatter
  weekly-report/
    SKILL.md
    template.md         ← шаблон отчёта
    scripts/
      collect.py        ← скрипт, который считает цифры
```

Минимальный `SKILL.md`:

```markdown
---
name: meeting-protocol
description: Оформить протокол встречи из сырых заметок. Используй, когда пользователь присылает заметки, расшифровку или конспект встречи и просит протокол, итоги или список задач.
---

# Протокол встречи

1. Выдели участников, решения, задачи (кто — что — к какому сроку), открытые вопросы.
2. Если у задачи нет ответственного или срока — отметь «не указано», не придумывай.
3. Формат — Markdown, разделы: Участники, Решения, Задачи (таблица), Открытые вопросы.
```

Вызвать skill можно двумя способами:

- **Явно:** набрать `/meeting-protocol` в сессии Claude Code.
- **Автоматически:** Claude сам решает применить skill, если запрос подходит под `description`.

Живой пример — skills этого курса. Агент-преподаватель, с которым ты занимаешься, — это Claude Code с набором skills в `.claude/skills/` папки курса: `/lesson`, `/check`, `/hint`, `/quiz`. Когда ты пишешь «проверь упражнение», Claude по `description` понимает, что нужен skill `check`, и следует записанной в нём процедуре.

> **Почему так?** Хороший prompt для повторяющейся задачи — ценность, которую обидно терять в истории чатов. Skill превращает его в файл: его можно улучшать, хранить в git, делиться с командой — и Claude выполняет процесс одинаково, а не «как получится сегодня».

## 2. Где лежат skills

| Уровень | Путь | Кому доступен |
|---------|------|---------------|
| Project | `.claude/skills/<name>/SKILL.md` в проекте | всем, кто работает с проектом (через git) |
| Personal | `~/.claude/skills/<name>/SKILL.md` | тебе во всех проектах |

Старый формат — отдельные файлы `.claude/commands/<name>.md` (slash commands) — продолжает работать. Если встретишь его в чужом проекте, это то же самое по смыслу: Markdown-инструкция, вызываемая через `/name`. Новые вещи делай как skills: они умеют больше (папка с файлами, автоматический вызов).

> **Почему так?** Project skills описывают процессы конкретного проекта и должны ехать вместе с кодом — коллега клонирует репозиторий и сразу получает `/commit-message` с правилами команды. Личные привычки (например, твой формат заметок) — в personal, чтобы не навязывать их команде.

## 3. Frontmatter: настройки skill

Frontmatter — блок YAML (простой формат «ключ: значение») между `---` в начале `SKILL.md`.

| Поле | Что делает | Когда нужно |
|------|-----------|-------------|
| `name` | имя skill и команды: `/name`. Строчные латинские буквы, цифры, дефисы; обычно совпадает с именем папки | всегда |
| `description` | что делает skill и **когда** его применять. По нему Claude решает, вызывать ли skill автоматически | всегда; это самое важное поле |
| `argument-hint` | подсказка об аргументах, видна при наборе `/name` | если skill принимает аргументы |
| `allowed-tools` | tools, которые Claude может использовать без запроса разрешения, пока skill активен. Пример: `Bash(git *) Read` | когда skill выполняет известные безопасные команды |
| `disable-model-invocation: true` | skill вызывается **только** тобой через `/name`, Claude сам его не запустит | для действий с последствиями: коммит, отправка, деплой |
| `user-invocable: false` | наоборот: skill не виден как команда, его применяет только Claude по `description` | фоновое знание («как у нас оформляются отчёты») |

Пример — skill, который делает коммит и потому вызывается только вручную:

```markdown
---
name: commit
description: Создать git commit с сообщением по правилам проекта.
argument-hint: "[необязательное пояснение к изменениям]"
allowed-tools: Bash(git status *) Bash(git diff *) Bash(git add *) Bash(git commit *)
disable-model-invocation: true
---
```

> **Почему так?** `allowed-tools` убирает лишние подтверждения для команд, которые ты уже одобрил, когда писал skill, но только для них: `Bash(git diff *)` не разрешает `rm`. А `disable-model-invocation` защищает от ситуации, когда Claude «решил помочь» и сам закоммитил полуготовую работу.

## 4. Первый полезный skill: динамический контекст

Внутри `SKILL.md` можно выполнить команду **до** того, как Claude увидит инструкцию, и подставить её вывод. Синтаксис — восклицательный знак и команда в обратных кавычках:

```markdown
---
name: standup
description: Подготовить короткую сводку для утреннего стендапа по git-истории проекта за последние сутки. Используй, когда пользователь просит «что я сделал вчера», сводку для стендапа или отчёт о последних изменениях.
allowed-tools: Bash(git log *) Bash(git status *)
---

# Сводка для стендапа

## Коммиты за сутки
!`git log --since="1 day ago" --oneline`

## Незакоммиченная работа
!`git status --short`

## Правила
- Три раздела: «Сделано», «В работе», «Блокеры». Каждый — 1–4 пункта.
- Пиши для менеджера, не для разработчика: «исправлена сортировка задач», а не «fix sort key».
- «В работе» — по незакоммиченным файлам. Если их нет — так и напиши.
- Не выдумывай блокеры: если их не видно из данных — «нет».
```

Когда ты вызываешь `/standup`, Claude Code выполняет обе команды, вставляет их вывод на место строк `` !`...` `` и только потом отдаёт текст модели. Claude сразу видит актуальную историю — не нужно просить «посмотри git log».

Как проверить skill:

1. Сделай пару коммитов (или используй историю из модуля 05), затем `/standup`.
2. Посмотри, соблюдены ли правила.
3. Не соблюдены → правишь `SKILL.md` → вызываешь снова. Если кажется, что правка не подхватилась, — начни новую сессию (новый skill тоже надёжнее проверять в новой сессии).

> **Почему так?** Динамический контекст гарантирует, что Claude работает с **текущими** данными, а не с тем, что «помнит» из разговора. Это же экономит шаги: без него Claude сначала потратил бы вызов tool на `git diff`, и ты подтверждал бы его вручную.

## 5. Аргументы

Всё, что ты напишешь после имени skill, — аргументы:

```text
/explain-file models.py для бухгалтера
```

В теле `SKILL.md`:

| Переменная | Что подставится | Пример |
|-----------|-----------------|--------|
| `$ARGUMENTS` | вся строка аргументов | `models.py для бухгалтера` |
| `$0` | первый аргумент (нумерация с нуля) | `models.py` |
| `$1` | второй аргумент | `для` |

Пример:

```markdown
---
name: explain-file
description: Объяснить файл кода простыми словами для нетехнического читателя.
argument-hint: "<путь к файлу> [для кого объяснять]"
---

Объясни файл `$0` простыми словами.
Полный запрос пользователя: $ARGUMENTS
Если читатель не указан — объясняй для коллеги без опыта программирования.
1. Одним абзацем: зачем этот файл.
2. Главные функции — таблицей «функция → что делает → где вызывается».
3. Одна вещь, которую легко сломать при правке, и почему.
```

Если аргументы содержат пробелы («для бухгалтера» — два слова), надёжнее работать с `$ARGUMENTS` целиком и описать в тексте, как его разбирать. Точные правила разбора аргументов уточняй в docs — они могут меняться.

Что делать, если аргумент не передан? Пропиши это в инструкции: «Если `$ARGUMENTS` пусто — спроси пользователя…». Иначе Claude получит пустое место и начнёт угадывать.

> **Почему так?** Аргументы превращают skill из «одной задачи» в инструмент: один `/explain-file` работает для любого файла. А `argument-hint` подсказывает *тебе через месяц*, что туда передавать.

## 6. Скрипты, шаблоны и progressive disclosure

### Progressive disclosure: как skill расходует context

Progressive disclosure (постепенное раскрытие) — ключевая идея skills:

| Что | Когда попадает в context |
|-----|--------------------------|
| `name` и `description` всех skills | всегда, в начале каждой сессии — чтобы Claude знал, что есть |
| Тело `SKILL.md` | только когда skill вызван |
| Дополнительные файлы (`template.md`, `reference.md`) | только если Claude решит их прочитать по ссылке из `SKILL.md` |
| Скрипты | обычно не читаются — **выполняются**; в context попадает только их вывод |

Поэтому у тебя может быть 20 skills, и они почти не занимают context, пока не нужны. Сравни с CLAUDE.md, который загружается целиком всегда.

### Скрипты

Если в задаче есть точная часть — посчитать, отфильтровать, преобразовать формат, — отдай её скрипту:

```text
csv-summary/
  SKILL.md
  scripts/
    summarize.py      ← читает CSV, печатает число строк, суммы, пропуски
```

```markdown
---
name: csv-summary
description: Сводка по CSV-файлу — сколько строк, какие колонки, суммы и пропуски. Используй, когда пользователь просит описать, проверить или кратко summarize CSV-таблицу.
argument-hint: "<путь к CSV>"
allowed-tools: Bash(python .claude/skills/csv-summary/scripts/summarize.py *)
---

1. Запусти: `python .claude/skills/csv-summary/scripts/summarize.py $ARGUMENTS`
2. Не пересчитывай цифры сам — используй вывод скрипта.
3. На основе вывода напиши 3–5 наблюдений для руководителя: что важно, что подозрительно.
```

Путь к скрипту здесь указан от корня проекта — так работает project skill, если `claude` запущен в корне. Для personal skills путь будет другим (`~/.claude/skills/...`).

### Шаблоны и справочники

Длинные вещи — пример идеального отчёта, справочник терминов — вынеси в отдельные файлы и сошлись на них:

```markdown
Оформи отчёт строго по шаблону из файла template.md в папке этого skill.
```

> **Почему так?** LLM считает «в уме» ненадёжно: на 30 строках CSV он может ошибиться в сумме, и ты этого не заметишь. Скрипт считает одинаково каждый раз и стоит несколько строк в context вместо всей таблицы. Правило: детерминированное (точное) — скрипту, суждение и текст — Claude.

## 7. Автоматический вызов и хороший `description`

Claude видит только `name` и `description` каждого skill и по ним решает, подходит ли skill к запросу. Тело skill в этот момент он **не видит**. Значит, `description` должен ответить на два вопроса: **что** делает skill и **когда** его применять.

| Плохо | Хорошо |
|-------|--------|
| `Помогает с текстами.` | `Оформить протокол встречи из сырых заметок. Используй, когда пользователь присылает заметки, расшифровку или конспект встречи и просит протокол, итоги, решения или список задач.` |
| `Git helper` | `Предложить сообщение коммита для подготовленных изменений. Используй, когда пользователь просит придумать, написать или улучшить commit message.` |

Приёмы:

- **Слова пользователя.** Включи формулировки, которыми ты реально просишь: «протокол», «итоги встречи», «кто что делает».
- **Триггеры и контекст.** «Используй, когда…» — прямо называй ситуации.
- **Границы.** Если skill легко спутать с соседним — уточни: «Не для писем клиентам — для этого skill client-email».
- **Без воды.** Длинное описание тоже вредит: оно занимает context всегда, во всех сессиях.

### Отладка: skill не срабатывает

| Симптом | Что проверить |
|---------|---------------|
| Skill не виден в `/` | путь `.claude/skills/<name>/SKILL.md`, точное имя файла, корректный frontmatter (`---` сверху и снизу), сессия запущена в нужной папке |
| `/name` работает, а автоматически не вызывается | `description`: есть ли «когда» и слова из запроса; нет ли `disable-model-invocation: true` |
| Вызывается не тогда | `description` слишком общий — сузь, добавь границы |
| Вызывается, но делает не то | проблема в теле SKILL.md, а не в description |

Метод отладки — как A/B тест из модуля 06: набор из 3–5 тестовых фраз (подходящие и неподходящие), прогон в новой сессии, изменение `description`, повтор.

> **Почему так?** Автоматический вызов — это решение модели на основе текста. Как и любой prompt, `description` нужно проверять на примерах, а не «на глаз». И помни про последствия: всё, что делает необратимые действия, лучше закрыть `disable-model-invocation: true` — там удобство автоматики не стоит риска.

## 8. Skill, CLAUDE.md или prompt-шаблон?

| Инструмент | Загрузка | Лучше всего для |
|-----------|----------|-----------------|
| CLAUDE.md | всегда, целиком | короткие правила, которые нужны почти в каждой задаче проекта |
| Skill | description всегда, тело — по вызову | процессы и процедуры: «как сделать X» по шагам, со скриптами и шаблонами |
| Prompt-шаблон в файле (модуль 04) | вручную, когда вставишь | разовые или редкие задачи, эксперименты до того, как процесс устоялся |

Признаки, что пора делать skill:

- ты вставляешь один и тот же prompt третий раз;
- в CLAUDE.md появился длинный раздел «как делать отчёт» — он нужен в одной задаче из десяти;
- процессу нужны файлы: скрипт, шаблон, пример.

В модуле 09 появится ещё один вариант — subagent: отдельный агент со своим context. Skill добавляет инструкции в **текущий** разговор; subagent выполняет работу **отдельно** и возвращает результат.

### Skills в claude.ai и Claude Desktop

Skills есть не только в Claude Code: в claude.ai и Claude Desktop можно загрузить свой skill (та же идея — папка с `SKILL.md`) и использовать его в чате. Где включается и как загрузить — смотри актуальную справку: https://docs.claude.com и Help Center. Это удобно для нетехнических процессов: оформление документов по стандарту компании, проверка писем.

> **Почему так?** У каждого места своя цена: CLAUDE.md платит context всегда, skill — только по вызову, шаблон — твоим вниманием (нужно не забыть вставить). Выбор — это компромисс между «всегда под рукой» и «не мешает, когда не нужно».

## Шпаргалка

| Что | Как |
|-----|-----|
| Project skill | `.claude/skills/<name>/SKILL.md` |
| Personal skill | `~/.claude/skills/<name>/SKILL.md` |
| Старый формат | `.claude/commands/<name>.md` — работает |
| Вызвать | `/name аргументы` или автоматически по `description` |
| Все аргументы / по номеру | `$ARGUMENTS` / `$0`, `$1` |
| Вставить вывод команды | строка с `` !`команда` `` в теле SKILL.md |
| Разрешить команды без вопросов | `allowed-tools: Bash(git diff *) Read` |
| Только ручной вызов | `disable-model-invocation: true` |
| Только автоматический вызов | `user-invocable: false` |
| Точные вычисления | скрипт в папке skill, Claude запускает его и читает вывод |
| Отладка автовызова | набор тестовых фраз → новая сессия → правка `description` → повтор |

Шаблон `SKILL.md`:

```markdown
---
name: <имя-через-дефисы>
description: <Что делает>. Используй, когда <ситуации и слова пользователя>.
argument-hint: "<аргументы>"
---

# <Название>

Вход: $ARGUMENTS (если пусто — <что делать>)

## Шаги
1. ...

## Формат результата
...

## Не делай
- ... — потому что ...
```

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| skill | папка с `SKILL.md` и доп. файлами: инструкция для повторяющейся задачи |
| `SKILL.md` | главный файл skill: frontmatter + инструкция |
| frontmatter | блок настроек YAML между `---` в начале файла |
| `description` | описание «что и когда»; по нему Claude выбирает skill автоматически |
| slash command | вызов через `/name`; старый формат — `.claude/commands/*.md` |
| `$ARGUMENTS` | строка аргументов, переданных при вызове |
| динамический контекст | `` !`команда` `` — вывод команды подставляется в skill перед загрузкой |
| `allowed-tools` | tools, которые можно использовать без подтверждения, пока skill активен |
| progressive disclosure | загрузка по уровням: описание всегда, тело по вызову, файлы по необходимости |
| детерминированный | дающий один и тот же результат при одинаковом входе (скрипт, а не модель) |

## Вопросы для самопроверки

1. Что Claude видит о skill до того, как тот вызван? Почему это важно для `description`?
2. Чем skill отличается от раздела в CLAUDE.md с той же инструкцией? Когда что выбрать?
3. Зачем skill «commit» ставить `disable-model-invocation: true`?
4. Почему подсчёт сумм в CSV лучше отдать скрипту, а не просить Claude посчитать?
5. Что делает строка `` !`git diff --staged` `` в SKILL.md и когда она выполняется?
6. `/meeting-protocol` работает, но на фразу «оформи итоги встречи» Claude skill не применяет. Что будешь менять и как проверишь?
7. Как в skill обработать ситуацию, когда пользователь не передал аргумент?
8. Чем personal skill отличается от project skill и когда какой создать?
