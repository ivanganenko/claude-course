**Шаги:**
1. В папке курса открой (в редакторе или попроси учителя показать) `.claude/skills/check/SKILL.md` и `.claude/skills/hint/SKILL.md`.

## Упражнение 2. Skill `commit-message`  ·  ⏱ ~30 мин  ·  обязательное

**Цель:** создать project skill, который предлагает сообщение коммита по реальному diff.
**Зачем:** сообщения коммитов — ежедневная рутина, где важна единообразность. Это классический первый skill: короткий, полезный, легко проверить.

**Шаги:**
1. Создай `.claude/skills/commit-message/SKILL.md` в todo-app. Пиши сам — README, раздел 4, показывает механику на другом примере (`standup`).
2. Требования к skill:
   - получает изменения, подготовленные к коммиту, через динамический контекст (`` !`...` ``);
   - правила сообщения согласованы с твоим CLAUDE.md (язык, форма, длина) — и не дублируют его без нужды;
   - если подготовленных изменений нет — говорит, что нужно сделать `git add`, и не выдумывает сообщение;
   - если изменения несвязанные — предлагает разбить коммит;
   - только **предлагает** сообщение, коммит не делает;
   - `allowed-tools` разрешает только нужные команды git для чтения.
3. Проверь на трёх ситуациях в **новой** сессии:
   - A: `git add` одного небольшого изменения → `/commit-message`;
   - B: ничего не добавлено → `/commit-message`;
   - C: добавлены два несвязанных изменения (например, правка README и правка `todo.py`) → `/commit-message`.
4. Если что-то не так — поправь `SKILL.md` и повтори.
5. Откати тестовые изменения, закоммить skill.

**Что сдать на проверку:** `SKILL.md`; результаты A, B, C (что ответил Claude); что пришлось исправить после первых прогонов.

**Критерии готовности:**
- [ ] Skill лежит в `.claude/skills/commit-message/SKILL.md`, вызывается через `/commit-message`
- [ ] Используется динамический контекст с `git diff --staged`
- [ ] Ситуации B и C обработаны осмысленно
- [ ] `allowed-tools` не шире необходимого (нет `Bash(*)`, нет `git commit`)
- [ ] Skill закоммичен

## Упражнение 3. Skill с аргументами: `bug-report`  ·  ⏱ ~35 мин  ·  обязательное

**Цель:** создать skill, который по описанию симптома воспроизводит баг и оформляет bug report.
**Зачем:** аргументы превращают skill в инструмент для любого входа. А этот skill закрепляет цикл из модуля 05: сначала воспроизвести, потом чинить.

**Шаги:**
1. Создай `.claude/skills/bug-report/SKILL.md`. Вызов: `/bug-report <описание симптома своими словами>`.
2. Skill должен:
   - использовать `$ARGUMENTS` как описание симптома; при пустых аргументах — спросить, что случилось;
   - попытаться воспроизвести баг командами `todo.py` **на временном файле данных** (через `TODO_FILE`), а не на `todos.json`;
   - записать отчёт в `bugs/<короткое-имя>.md`: симптом, шаги, ожидаю/вижу, удалось ли воспроизвести, предполагаемое место в коде;
   - **не исправлять** код;
   - иметь `argument-hint`.
3. Внеси в код «свежий» баг для проверки: в отдельной сессии попроси Claude незаметно сломать вывод срока задачи в `format_task` и **не смотри**, что именно изменилось. Эту поломку не коммить — потом её откатишь.
4. Новая сессия → `/bug-report даты в списке задач выглядят странно`. Проверь отчёт: шаги воспроизводятся? Место в коде указано верно?
5. Вызови `/bug-report` без аргументов — что происходит?
6. Откати поломку (`git restore .`), удали тестовый отчёт или оставь как пример, закоммить skill.

**Что сдать на проверку:** `SKILL.md`; сгенерированный `bugs/*.md`; результат вызова без аргументов.

**Критерии готовности:**
- [ ] `$ARGUMENTS` используется, пустой вызов обработан
- [ ] Воспроизведение идёт на временном файле, `todos.json` не изменён
- [ ] Отчёт содержит шаги, ожидаю/вижу и результат воспроизведения
- [ ] Skill не исправляет код
- [ ] Есть `argument-hint`

## Упражнение 4. Skill со скриптом: `todo-report`  ·  ⏱ ~45 мин  ·  обязательное

**Цель:** создать skill, где цифры считает Python-скрипт, а текст пишет Claude.
**Зачем:** это главный паттерн для надёжных skills: детерминированную часть — коду, суждение — модели. Так отчёты не «плывут» от прогона к прогону.

**Шаги:**
1. Структура:
   ```text
   .claude/skills/todo-report/
     SKILL.md
     scripts/report.py
   ```
2. `report.py` (можно написать с Claude, но ты должен понимать каждую строку) читает файл задач (учитывая `TODO_FILE`) и печатает: всего / выполнено / открыто, открытые по приоритетам, список просроченных, список задач со сроком в ближайшие 7 дней. Если файла нет — понятное сообщение и ненулевой код выхода.
3. `SKILL.md`: запустить скрипт, на основе **только его вывода** написать отчёт для руководителя (3 вывода + таблица + «на что обратить внимание»), цифры не пересчитывать. `allowed-tools` — только запуск этого скрипта.
4. Сначала запусти скрипт сам в терминале — проверь цифры против `python todo.py stats`.
5. Новая сессия → `/todo-report`. Совпадают ли цифры в отчёте с выводом скрипта?
6. Проверь progressive disclosure: посмотри `/context` до вызова skill и после. Что изменилось?
7. Закоммить.

**Что сдать на проверку:** `SKILL.md`, `report.py`, вывод скрипта, отчёт Claude, наблюдение из шага 6.

**Критерии готовности:**
- [ ] Скрипт работает отдельно и учитывает `TODO_FILE`, обрабатывает отсутствие файла
- [ ] Цифры в отчёте совпадают с выводом скрипта
- [ ] `SKILL.md` прямо запрещает пересчитывать цифры
- [ ] `allowed-tools` ограничен запуском скрипта
- [ ] Студент объясняет, что из skill попадает в context и когда

## Упражнение 5. Отладка `description`  ·  ⏱ ~40 мин  ·  обязательное

**Цель:** добиться, чтобы skill надёжно срабатывал автоматически на нужные запросы и не срабатывал на чужие.
**Зачем:** автоматический вызов — главное удобство skills, и самая частая причина «skill не работает» — плохой `description`. Чинить его нужно экспериментом.

**Шаги:**
1. Создай папку `~/claude-practice/skills-lab`, скопируй туда `meeting-notes.txt` (см. «Где выполнять»).
2. Создай skill `.claude/skills/meeting-protocol/SKILL.md` с **намеренно плохим** описанием:
   ```markdown
   ---
   name: meeting-protocol
   description: Помогает с текстами.
   ---
   ```
   Тело напиши сам: как оформить протокол (участники, решения, задачи «кто — что — срок», открытые вопросы). Последней строкой инструкции добавь: «В конце протокола добавь строку `_Оформлено skill meeting-protocol_`» — это маркер, по которому ты увидишь, что skill сработал.
3. Составь 5 тестовых запросов, **не упоминая** имя skill:
   - 3 должны вызвать skill (например, «вот заметки со встречи @meeting-notes.txt — сделай итоги», «кто что должен сделать после этой планёрки?», свой вариант);
   - 2 не должны (например, «исправь опечатки в этом письме», «переведи заметки на английский»).
4. Прогон 1: каждый запрос — в новой сессии (или после `/clear`). Запиши: сработал skill или нет (есть маркер?).
5. Перепиши `description` по правилам из README, раздел 7.
6. Прогон 2: те же 5 запросов. Запиши результат.
7. Если остались ошибки — ещё одна итерация.

| Запрос | Должен сработать? | Прогон 1 | Прогон 2 |
|--------|-------------------|----------|----------|
| … | да | | |

**Что сдать на проверку:** таблица прогонов; плохой и итоговый `description`; что именно изменил и почему.

**Критерии готовности:**
- [ ] 5 тестовых запросов: 3 «да», 2 «нет», без имени skill
- [ ] Каждый запрос в чистой сессии
- [ ] Итоговый `description` описывает «что» и «когда», содержит слова из реальных запросов
- [ ] В прогоне 2 результат лучше; оставшиеся ошибки объяснены

## Упражнение 6. ⭐ Personal skill для своей рутины  ·  ⏱ ~60 мин  ·  со звёздочкой

**Цель:** создать личный skill для повторяющейся задачи из своей работы — со вспомогательным файлом.
**Зачем:** настоящая польза skills — в твоих собственных процессах. Personal skill будет работать во всех твоих проектах.

**Шаги:**
1. Выбери рутину, которую делаешь хотя бы раз в неделю: письмо-отчёт, разбор входящих, подготовка к встрече, проверка документа по чек-листу. Данные для тестов — только вымышленные.
2. Создай `~/.claude/skills/<name>/` с `SKILL.md` и минимум одним вспомогательным файлом (шаблон, чек-лист, пример идеального результата), на который `SKILL.md` ссылается.
3. Реши и обоснуй: нужен ли `disable-model-invocation`? нужны ли аргументы? нужен ли скрипт?
4. Проверь в двух разных папках (например, `skills-lab` и `scratch`): вызов через `/name` и автоматический вызов по 2 фразам.
5. Попроси Claude в новой сессии сделать ревью твоего skill: «Прочитай skill <name>. Что неоднозначно? В каких случаях он сработает не так?» Учти дельные замечания.

**Что сдать на проверку:** папка skill целиком; описание рутины; ответы на шаг 3; результаты проверки в двух папках.

**Критерии готовности:**
- [ ] Skill personal (`~/.claude/skills/`), работает в двух папках
- [ ] Есть вспомогательный файл, на который ссылается `SKILL.md`
- [ ] Решения о frontmatter обоснованы
- [ ] Автоматический вызов проверен минимум на 2 фразах
- [ ] Нет реальных персональных данных
