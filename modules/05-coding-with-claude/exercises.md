# Модуль 05 — практика

> Где выполнять: `~/claude-practice/todo-app` (Windows: `$HOME\claude-practice\todo-app`), отдельная сессия Claude Code в этой папке. Что скопировать: `practice/todo-app` из папки курса целиком (см. упражнение 1).

## Упражнение 1. Экскурсия по проекту  ·  ⏱ ~30 мин  ·  обязательное

**Цель:** разобраться в незнакомом проекте с помощью Claude и проверить своё понимание.
**Зачем:** почти любая работа с кодом начинается с чужого проекта. Умение за полчаса получить «карту» и проверить её — основа всего модуля.

**Шаги:**
1. Скопируй проект:
   ```powershell
   # Windows PowerShell, в папке курса
   Copy-Item -Recurse practice\todo-app $HOME\claude-practice\todo-app
   ```
   ```bash
   # macOS / Linux, в папке курса
   cp -r practice/todo-app ~/claude-practice/todo-app
   ```
2. Перейди в `~/claude-practice/todo-app`, создай и активируй venv, установи зависимости (README модуля, раздел 1). Запусти `python -m pytest` — тесты должны пройти.
3. Сам, без Claude, запусти: `python todo.py list`, `python todo.py stats`, `python todo.py --help`. Запиши, что увидел.
4. Запусти `claude` в папке проекта, включи **plan mode** (Shift+Tab). Задай минимум 4 вопроса по схеме из раздела 2: карта → путь данных команды `add` → непонятная конструкция → «задай мне 3 вопроса, чтобы проверить, что я понял».
5. Ответь на вопросы Claude. Попроси его оценить ответы.
6. Выбери одно утверждение Claude о коде (например, «функция X вызывается из Y») и проверь его сам, открыв файл.
7. Создай файл `NOTES.md` в папке проекта (можно попросить Claude, но текст — твоими словами): 5–7 пунктов «как устроен проект» и 1–2 вопроса, которые остались.

**Что сдать на проверку:** `NOTES.md`; список своих prompts; какое утверждение Claude ты проверил и как.

**Критерии готовности:**
- [ ] venv создан, `python -m pytest` проходит
- [ ] Задано ≥ 4 вопросов, включая «путь данных» для конкретной команды
- [ ] Экскурсия проходила в plan mode (или студент объясняет, почему без него)
- [ ] `NOTES.md` описывает роли трёх файлов и путь от команды до `todos.json` своими словами
- [ ] Хотя бы одно утверждение Claude проверено по коду

## Упражнение 2. Git: точка сохранения  ·  ⏱ ~20 мин  ·  обязательное

**Цель:** поставить проект под git и сделать первый коммит до любых изменений.
**Зачем:** дальше Claude будет менять код. Коммит «как было» — твоя гарантия, что любую правку можно увидеть и отменить.

**Шаги:**
1. Проверь git: `git --version`. Если git ещё не представлен — выполни `git config --global user.name ...` и `user.email ...` (README, раздел 3).
2. В папке проекта: `git init`.
3. Создай `.gitignore`, чтобы в git не попали `.venv/`, `__pycache__/`, `.pytest_cache/`. Можно попросить Claude — но проверь содержимое сам.
4. `git status` — убедись, что `.venv` **не** в списке. Если в списке — `.gitignore` не сработал, разберись почему.
5. `git add .` → `git commit -m "Исходная версия todo-app"`.
6. Эксперимент: попроси Claude поменять заголовок в `README.md` проекта. Посмотри `git status` и `git diff`. Отмени правку через `git restore README.md` и снова посмотри `git status`.
7. `git log --oneline` — должен быть один коммит.

**Что сдать на проверку:** вывод `git log --oneline` и `git status`; содержимое `.gitignore`; 1–2 предложения: что показал `git diff` в шаге 6 и что сделал `git restore`.

**Критерии готовности:**
- [ ] Репозиторий создан, первый коммит есть
- [ ] `.venv` и `__pycache__` не попали в коммит
- [ ] Студент своими словами объясняет, что показывают `status` и `diff`
- [ ] Правка отменена через `git restore`, рабочая копия чистая

## Упражнение 3. Три бага от пользователя  ·  ⏱ ~60 мин  ·  обязательное

**Цель:** пройти цикл «воспроизвести → найти → починить → проверить» трижды.
**Зачем:** это главный навык модуля. Бездумное «почини» даёт правку, которую нельзя проверить; цикл даёт исправление, в котором ты уверен.

Коллега Ольга из отдела закупок (вымышленная) пользуется todo-app и прислала жалобы:

> 1. «Отметила задачу выполненной — а она всё равно висит в `list`. Я думала, там только то, что осталось сделать. А с `--all` почему-то выполненные, наоборот, пропадают.»
> 2. «Удалила старую задачу, добавила новую — и теперь у меня две задачи с одним номером. Нажимаю `done` — закрывается не та.»
> 3. «Список отсортирован странно: задачи `low` стоят выше `medium`. Разве не должно быть по важности сверху вниз?»

**Шаги** (для каждого бага отдельно):
1. Воспроизведи баг сам командами `todo.py`. Запиши точные шаги, «ожидаю» и «вижу».
2. Напиши Claude bug report по шаблону из раздела 4 с явной просьбой: «найди причину, объясни, укажи файл и функцию, ничего не меняй».
3. Проверь объяснение: открой указанное место и убедись, что причина правдоподобна. Если сомневаешься — задай уточняющий вопрос.
4. Разреши минимальную правку. Спроси: «в каком случае твоё исправление может не сработать?»
5. Повтори шаги воспроизведения — баг ушёл. Запусти `python -m pytest`.
6. Прочитай `git diff`: изменено только нужное?
7. Закоммить: один баг — один коммит, сообщение описывает исправление.

Совет: если ты испортил `todos.json` экспериментами — `git restore todos.json`.

**Что сдать на проверку:** `git log --oneline` (≥ 3 новых коммита); таблица «баг → причина (файл/функция) → исправление → как проверил»; ответ Claude на вопрос про случаи, когда фикс может не сработать (хотя бы для одного бага).

**Критерии готовности:**
- [ ] Все три бага воспроизведены до исправления, шаги записаны
- [ ] Для каждого бага причина названа точно (файл, функция, в чём ошибка)
- [ ] Исправления минимальные, без посторонних изменений
- [ ] После исправлений баги не воспроизводятся, тесты проходят
- [ ] Три отдельных коммита с понятными сообщениями

## Упражнение 4. Тесты, которые ловят баги  ·  ⏱ ~45 мин  ·  обязательное

**Цель:** написать регрессионные тесты на три исправленных бага и доказать, что они ловят баг.
**Зачем:** тест — это способ для Claude (и для тебя) проверить работу автоматически. Тест, который не падает на сломанном коде, — бесполезен, поэтому проверяем и это.

**Шаги:**
1. Попроси Claude написать тесты в `tests/test_bugs.py`: минимум по одному на каждый баг. Требования передай явно: тесты не трогают настоящий `todos.json` (временный файл через `TODO_FILE`), имена тестов описывают поведение.
2. Прочитай тесты. Для каждого ответь себе: что именно он проверяет? Если не понимаешь строку — спроси Claude.
3. Запусти `python -m pytest -v` — всё зелёное.
4. **Проверка теста:** попроси Claude временно вернуть один из багов в коде, запустить тесты и показать, какой тест упал. Потом верни исправление (`git restore <файл>` или попроси Claude) и убедись, что `git status` показывает изменения только в `tests/`.
5. Проверь, что после запуска тестов `todos.json` не изменился (`git status`).
6. Закоммить тесты.

**Что сдать на проверку:** файл `tests/test_bugs.py`; вывод `python -m pytest -v`; вывод упавшего теста из шага 4.

**Критерии готовности:**
- [ ] Есть ≥ 3 теста, каждый связан с конкретным багом
- [ ] Тест на `list` проверяет поведение команды (вывод), а не только внутреннюю функцию
- [ ] Тесты изолированы: `todos.json` после запуска не изменён
- [ ] Показано, что хотя бы один тест падает при возвращённом баге
- [ ] Все тесты проходят, изменения закоммичены

## Упражнение 5. Фича через план  ·  ⏱ ~45 мин  ·  обязательное

**Цель:** добавить команду `edit` через цикл «план → проверка → реализация → тесты → diff → коммит».
**Зачем:** на фичах больше пары строк план экономит время: ошибку в плане исправить дешевле, чем в коде.

**Шаги:**
1. `git status` — рабочая копия чистая.
2. Включи plan mode. Опиши фичу: `python todo.py edit <id> [--title ...] [--priority ...] [--due ...]`. Перечисли крайние случаи (нет такой задачи, не передано ни одного поля, неверная дата) и требование про тесты. Формулировку придумай сам — пример в README, раздел 6, можно взять за основу, но не копируй дословно.
3. Прочитай план Claude. Внеси хотя бы **одну** правку или уточнение (что-то, что в плане упущено или сделано не так, как ты хочешь).
4. Одобри план, дай Claude реализовать.
5. Проверь руками: 3 разных вызова `edit`, включая ошибочный.
6. `python -m pytest -v` → `git diff` по чек-листу из раздела 7 → коммит.

**Что сдать на проверку:** твой prompt с описанием фичи; план Claude и твоя правка к нему; коммит; вывод тестов и трёх ручных проверок.

**Критерии готовности:**
- [ ] Использован plan mode, план прочитан и скорректирован до реализации
- [ ] `edit` меняет только переданные поля; ошибки обрабатываются (нет задачи → код 1)
- [ ] Есть тесты на `edit`, все тесты проходят
- [ ] Diff просмотрен, в коммите нет изменений вне задачи

## Упражнение 6. Ревью чужого изменения  ·  ⏱ ~30 мин  ·  обязательное

**Цель:** найти проблемы в чужом изменении до того, как оно попадёт в коммит.
**Зачем:** с Claude ты будешь чаще читать код, чем писать. Ревью diff — твоя последняя линия защиты, особенно в `acceptEdits`.

Коллега Павел (вымышленный) прислал изменение: команда `clear` удаляет все выполненные задачи.

**Шаги:**
1. `git status` — чисто.
2. Попроси Claude внести изменения **буквально**, ничего не исправляя (скажи, что это учебное ревью). Изменения Павла:
   - в `todo.py` добавить функцию:
     ```python
     def cmd_clear(args: argparse.Namespace) -> int:
         """Удалить выполненные задачи."""
         tasks = load_tasks()
         print("DEBUG", tasks)
         for task in tasks:
             if task.done == True:
                 tasks.remove(task)
         save_tasks(tasks)
         print("Готово")
         return 0
     ```
   - в `build_parser()` перед `return parser` добавить:
     ```python
         p = sub.add_parser("clear", help="удалить выполненные задачи")
         p.set_defaults(func=cmd_clear)
     ```
   - в `storage.py` в `json.dump(...)` убрать аргумент `ensure_ascii=False`.
3. Сам прочитай `git diff`. Пройди чек-лист из раздела 7 и выпиши все проблемы, которые нашёл, — **до** того как спрашивать Claude.
4. Проверь подозрения запуском: например, отметь выполненными несколько задач, идущих в файле подряд, и запусти `clear`. Посмотри `todos.json`.
5. Открой **новую** сессию (или `/clear`) и попроси Claude сделать ревью `git diff` (prompt из раздела 7). Сравни его список со своим.
6. Отмени изменения: `git restore .` → `git status` чистый.

**Что сдать на проверку:** твой список замечаний (шаг 3), результат проверки запуском (шаг 4), список Claude (шаг 5) и сравнение: что нашёл ты, что — Claude, что пропустили оба.

**Критерии готовности:**
- [ ] Найдено ≥ 3 проблемы самостоятельно, у каждой — «почему это плохо»
- [ ] Хотя бы одна проблема подтверждена запуском, а не только чтением
- [ ] Замечено изменение вне задачи (`storage.py`)
- [ ] Ревью Claude получено в чистом context, сделано сравнение
- [ ] Изменения отменены, рабочая копия чистая

## Упражнение 7. ⭐ Сначала тест, потом код + история проекта  ·  ⏱ ~60 мин  ·  со звёздочкой

**Цель:** реализовать фичу в стиле «тесты вперёд» и оформить историю проекта.
**Зачем:** когда тесты написаны до кода, у Claude есть чёткий критерий «готово», а у тебя — уверенность, что фича делает именно то, что ты описал. История коммитов превращается в документацию.

**Шаги:**
1. Фича: `python todo.py list --sort due` — сортировка по сроку (без срока — в конце), по умолчанию остаётся сортировка по приоритету.
2. **Сначала** попроси Claude написать только тесты для этой фичи (не трогая код) и показать, что они падают. Прочитай тесты: описывают ли они то, что ты хочешь? Поправь, если нет. Закоммить тесты отдельно.
3. Потом попроси реализовать фичу так, чтобы тесты прошли, **не меняя тесты**. Проверь по `git diff`, что `tests/` не изменён.
4. Закоммить фичу.
5. История: попроси Claude по `git log` составить `CHANGELOG.md` (разделы «Исправлено», «Добавлено»). Сверь с `git log --oneline` — ничего не выдумано?
6. Ответь с помощью `git log -p models.py`: в каком коммите изменилась функция генерации id и что именно поменялось? Сначала найди сам, потом можешь проверить у Claude.

**Что сдать на проверку:** два коммита (тесты, затем фича); `CHANGELOG.md`; ответ на вопрос из шага 6 с хешем коммита.

**Критерии готовности:**
- [ ] Тесты закоммичены раньше реализации и падали до неё
- [ ] Реализация не изменила тесты
- [ ] `CHANGELOG.md` соответствует реальной истории
- [ ] Хеш и суть изменения `next_id` найдены через `git log`
