# Модуль 05. Работа с кодом вместе с Claude

> **Зачем:** научиться безопасно работать с чужим кодом в паре с Claude: разобраться в проекте, починить баг, проверить исправление тестами и не потерять рабочую версию. **Время:** ~4 ч. **Нужно:** пройдены модули 02–04; установлены Claude Code, Python 3.11+ и Git.

## Что ты будешь уметь

- Быстро разбираться в незнакомом проекте с помощью Claude: структура, точки входа, путь данных.
- Чинить баги по циклу «воспроизвести → найти → починить → проверить».
- Давать Claude способ проверить себя: запускать и писать тесты на pytest.
- Читать diff и принимать изменения осознанно, а не «на доверии».
- Пользоваться минимумом git: `init`, `status`, `diff`, `add`, `commit`, `log`, `restore`.
- Планировать новую фичу через plan mode и доводить её до коммита.

## 1. Учебный проект todo-app

Весь модуль мы работаем с маленьким проектом `practice/todo-app` — менеджером задач для командной строки. Это ~200 строк Python в трёх файлах:

| Файл | Что делает |
|------|-----------|
| `todo.py` | CLI (command-line interface — программа, которой управляют командами в терминале): разбирает аргументы через `argparse`, вызывает нужную команду |
| `models.py` | dataclass `Task` (класс-«структура» с полями `id`, `title`, `priority`, `due`, `done`, `created_at`), выдача id, сортировка |
| `storage.py` | чтение и запись `todos.json` |
| `tests/` | несколько тестов pytest — «чтобы было с чего начать» |

Команды: `add`, `list [--all]`, `done <id>`, `delete <id>`, `stats`. В проекте **есть баги** — как в любом реальном коде. Какие именно, ты узнаешь из «жалоб пользователей» в упражнениях.

Скопируй проект в практическую папку (подробнее — в упражнении 1):

```powershell
# Windows PowerShell, из папки курса
Copy-Item -Recurse practice\todo-app $HOME\claude-practice\todo-app
```

```bash
# macOS / Linux, из папки курса
cp -r practice/todo-app ~/claude-practice/todo-app
```

### venv кратко

venv (virtual environment — изолированная «коробка» с Python-пакетами для одного проекта) нужен, чтобы `pytest` и другие библиотеки ставились не в системный Python, а в папку `.venv` внутри проекта.

```powershell
# Windows PowerShell
python -m venv .venv
.venv\Scripts\Activate.ps1      # в начале строки появится (.venv)
pip install -r requirements.txt
```

```bash
# macOS / Linux
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Если PowerShell пишет, что выполнение скриптов запрещено, — попроси Claude объяснить ошибку и варианты; не меняй политику безопасности вслепую.

> **Почему так?** Разные проекты требуют разные версии библиотек. Без venv они конфликтуют в одном системном Python, и «вчера работало, сегодня нет». Папка `.venv` — одноразовая: её можно удалить и пересоздать по `requirements.txt`, поэтому в git её не кладут.

## 2. Как Claude изучает незнакомый проект

Когда ты пишешь «объясни этот проект», Claude не «знает» его заранее. Он работает как новый сотрудник: смотрит список файлов, читает README, ищет точку входа, открывает файлы по одному. Для этого у Claude Code есть tools (инструменты — действия, которые модель может вызвать): поиск файлов по шаблону, поиск текста по проекту, чтение файла, запуск команд. Ты видишь эти вызовы в интерфейсе сессии.

Хорошая «экскурсия» идёт от общего к частному:

1. **Карта.** «Опиши структуру проекта: какие файлы, за что отвечает каждый, где точка входа».
2. **Путь данных.** «Проследи, что происходит, когда я запускаю `python todo.py add "Купить бумагу"`: какие функции вызываются по порядку, где данные сохраняются».
3. **Непонятные места.** «Объясни строку `@dataclass` и `field(default_factory=_now)` как человеку, который знает Python на уровне функций».
4. **Проверка понимания.** «Задай мне 3 вопроса по этому коду, чтобы проверить, что я понял».

Полезные приёмы:

- **Указывай файлы через `@`:** `объясни @models.py` — Claude сразу получает файл в context, без поиска.
- **Включай plan mode (Shift+Tab) для экскурсии.** В нём Claude только читает и рассуждает — ничего не изменит «случайно».
- **Проси уровень объяснения:** «как коллеге-аналитику», «построчно», «одним абзацем».
- **Проси ссылки на места в коде:** «укажи файл и функцию» — так ответ можно проверить, а не принять на веру.

> **Почему так?** Claude может ошибиться в объяснении так же, как в коде (вспомни hallucinations из модуля 01). Когда он ссылается на конкретную функцию, ты за 10 секунд открываешь её и проверяешь. Объяснение «вообще» проверить нельзя.

## 3. Git минимум: страховка перед изменениями

Git — система контроля версий: она хранит «снимки» (commits) проекта, и к любому снимку можно вернуться. Для работы с Claude это главный инструмент безопасности: Claude может за минуту изменить десяток файлов, и тебе нужен способ увидеть, что именно изменилось, и откатить лишнее.

| Команда | Что делает | Когда |
|---------|-----------|-------|
| `git init` | превращает папку в git-репозиторий | один раз на проект |
| `git status` | какие файлы изменены / новые / добавлены к коммиту | постоянно, перед каждым коммитом |
| `git diff` | построчно: что изменилось с последнего коммита | перед тем как принять работу Claude |
| `git add <файл>` / `git add .` | положить изменения «в корзину» следующего коммита | перед коммитом |
| `git commit -m "сообщение"` | сохранить снимок с описанием | после каждой законченной задачи |
| `git log --oneline` | история коммитов, кратко | посмотреть, что было |
| `git restore <файл>` | отменить незакоммиченные изменения файла | когда правка не понравилась |

Первый раз на компьютере git попросит представиться — это подпись в коммитах, не логин:

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "you@example.com"
```

Типичный рабочий цикл с Claude:

```bash
git status                    # чисто? значит, есть точка возврата
# ... Claude вносит изменения ...
git diff                      # читаю, что он сделал
python -m pytest              # проверяю
git add .
git commit -m "Исправить сортировку по приоритету"
```

Команды git можно запускать прямо из сессии Claude Code через `!` (bash mode): `!git status`. Или попросить Claude: «покажи git diff и объясни каждое изменение».

### Файл .gitignore

`.gitignore` — список того, что git не должен отслеживать: `.venv/`, `__pycache__/`, личные файлы. Без него в историю попадут тысячи файлов библиотек.

```gitignore
.venv/
__pycache__/
.pytest_cache/
```

> **Почему так?** Коммит *до* большого изменения — это бесплатная кнопка «отменить всё». Rewind в Claude Code (Esc Esc) тоже откатывает правки, но он привязан к сессиям Claude и, как правило, не откатывает изменения, сделанные вручную или командами в терминале (подробности — в docs). Git видит всё и хранит историю годами. Используй оба: rewind — для быстрого «ой», git — как надёжную точку сохранения.

## 4. Цикл исправления бага

Самая частая ошибка — сразу сказать «почини баг». Claude починит *что-то*, но не обязательно то, что нужно, и ты не узнаешь, сработало ли. Надёжный цикл из четырёх шагов:

| Шаг | Вопрос | Что делаешь |
|-----|--------|-------------|
| 1. Воспроизвести | Как именно проявляется баг? | Точные шаги и команды, ожидаемый и фактический результат |
| 2. Найти причину | Где в коде ошибка и почему? | Просишь Claude найти и **объяснить** до правки |
| 3. Починить | Минимальная правка | Одна причина — одно изменение, без «заодно отрефакторил» |
| 4. Проверить | Баг ушёл? Ничего не сломалось? | Повторяешь шаги из п.1, запускаешь тесты, читаешь diff |

Хороший bug report (описание бага) для Claude — пример из другого, вымышленного проекта учёта счетов:

```text
Баг: отчёт за февраль падает с ошибкой.

Шаги:
1. python invoices.py report --month 2
2. (январь, --month 1, работает нормально)

Ожидаю: таблицу счетов за февраль.
Вижу: KeyError: '2026-02-30' и трассировку (полный текст ниже).
<вставить текст ошибки>

Сначала найди причину и объясни её мне, укажи файл и функцию.
Ничего не меняй, пока я не подтвержу.
```

Обрати внимание на последнюю строку: она отделяет диагностику от правки. Ты успеваешь проверить, что причина найдена верно, — иначе Claude может «починить» симптом (например, проверять дубликаты при выводе) вместо причины.

Подсказки:

- **Работай на копии данных.** Баги проще воспроизводить, когда не жалко `todos.json`. Он в git — испортил, сделал `git restore todos.json`.
- **Один баг — один коммит.** Так в истории видно, что и зачем менялось, и любой фикс можно отменить отдельно.
- **Проси объяснить фикс.** «Почему твоё исправление решает проблему? В каком случае оно может не сработать?» — второй вопрос часто находит краевые случаи.

> **Почему так?** Шаг «воспроизвести» превращает расплывчатое «что-то не так» в проверяемый факт. Без него ты не можешь доказать ни себе, ни Claude, что баг исправлен, — остаётся только «вроде работает».

## 5. Тесты: дай Claude способ проверить себя

Тест — маленькая программа, которая вызывает твой код и проверяет результат. pytest (популярная библиотека для тестов на Python) находит в папке `tests/` файлы `test_*.py`, запускает функции `test_*` и сообщает, какие прошли.

```python
# tests/test_models.py
from datetime import date
from models import Task

def test_done_task_is_never_overdue():
    task = Task(id=1, title="Сдать отчёт", due="2026-01-10", done=True)
    assert task.is_overdue(today=date(2030, 1, 1)) is False
```

`assert` — «утверждаю, что…». Если условие ложно, тест падает и pytest показывает, что ожидалось и что получилось.

Запуск (в активированном venv, из папки проекта):

```bash
python -m pytest          # все тесты
python -m pytest -v       # с именем каждого теста
python -m pytest -k sort  # только тесты, в имени которых есть "sort"
```

### Почему тесты особенно важны при работе с Claude

Claude не видит, работает ли код, пока не запустит его. Если у проекта есть тесты и ты попросишь «после правки запусти тесты и добейся, чтобы все прошли», Claude получает **обратную связь**: видит ошибку, исправляет, запускает снова. Это превращает «я написал код, наверное работает» в «я написал код, и 12 проверок подтверждают».

Хороший prompt для тестов:

```text
Напиши тест в tests/test_bugs.py, который воспроизводит баг с дубликатом id.
Сначала запусти его на текущем коде и покажи, что он ПАДАЕТ.
Тест не должен трогать настоящий todos.json — используй временный файл
(переменная окружения TODO_FILE).
```

Три важные детали в этом prompt:

1. **Тест сначала падает.** Тест, который проходит и на сломанном коде, ничего не проверяет.
2. **Изоляция данных.** Тесты не должны портить рабочие данные. В pytest для этого есть `tmp_path` (временная папка) и `monkeypatch.setenv` (временная переменная окружения).
3. **Конкретное место.** Указано, в какой файл писать.

Осторожно с «зелёными» тестами любой ценой: если попросить «сделай так, чтобы тесты прошли», Claude иногда меняет сам тест или ожидание в нём. Поэтому смотри diff тестов так же внимательно, как diff кода.

> **Почему так?** Тест — это записанное ожидание, которое можно проверять бесконечно и бесплатно. Через месяц, когда ты (или Claude) поменяешь сортировку ради новой фичи, регрессионный тест (regression test — тест на уже исправленный баг) сразу скажет, если старый баг вернулся.

## 6. Новая фича через план

Для фичи больше пары строк используй цикл из модуля 04: **план → проверка → выполнение**.

1. `git status` — рабочая копия чистая, есть точка возврата.
2. Shift+Tab до **plan mode**. Опиши фичу: что пользователь делает, что видит, крайние случаи.
3. Claude исследует код и предлагает план. Ты читаешь и правишь: «не меняй формат todos.json», «добавь тесты», «выводи ошибку, если задачи нет».
4. Подтверждаешь план → Claude реализует. Для небольшой фичи можно перейти в `acceptEdits`, но только когда план тебе понятен.
5. Тесты → `git diff` → коммит.

Пример описания фичи:

```text
Хочу команду edit: python todo.py edit 3 --title "Новый текст" --priority high --due 2026-11-01
- менять можно любое подмножество полей;
- если ни одного поля не передано — понятная ошибка;
- если задачи нет — сообщение и код возврата 1, как в done/delete;
- добавь тесты; формат todos.json не меняй.
Сначала план, код потом.
```

> **Почему так?** Ошибку в плане исправить дёшево — это одна фраза. Ошибку в уже написанном коде на 5 файлов — дорого: нужно читать весь diff и объяснять, что переделать. Plan mode переносит обсуждение туда, где оно дешевле.

## 7. Ревью diff: принимай изменения осознанно

Diff — запись «что было → что стало». В выводе `git diff` строки с `-` удалены, с `+` добавлены, остальные — контекст:

```diff
--- a/todo.py
+++ b/todo.py
@@ -38,7 +38,7 @@ def format_task(task: Task) -> str:
     """Одна строка для вывода задачи в терминал."""
     mark = "x" if task.done else " "
-    due = f"  до {task.due}" if task.due else ""
+    due = f"  срок: {task.due}" if task.due else ""
     overdue = "  (просрочено!)" if task.is_overdue() else ""
```

`@@ -38,7 +38,7 @@` — с какой строки начинается фрагмент и сколько строк в нём «до» и «после». Здесь изменена одна строка: подпись «до» заменена на «срок:».

Чек-лист ревью — пройди по нему перед каждым `git commit`:

| Вопрос | Почему важно |
|--------|-------------|
| Изменено только то, о чём я просил? | «Заодно» переписанный файл трудно проверить и легко сломать |
| Понимаю ли я каждую строку? | Если нет — спроси Claude «зачем эта строка?» до принятия |
| Не изменились ли тесты «под код»? | Ослабленный тест прячет баг |
| Нет ли удалённых проверок и обработки ошибок? | Код «работает», пока не придут странные данные |
| Нет ли секретов, отладочных `print`, лишних файлов? | В git они останутся в истории навсегда |
| Тесты проходят? | Последний и обязательный шаг |

Можно поручить первую часть ревью Claude, но в **новой сессии** или после `/clear`:

```text
Сделай ревью изменений в git diff как строгий старший разработчик.
Ищи: ошибки логики, необработанные случаи, изменения вне задачи.
Для каждого замечания: файл, строка, проблема, почему это плохо.
```

> **Почему так?** В той же сессии, где Claude писал код, он «помнит» свои намерения и склонен считать код правильным. Свежий context смотрит на diff как посторонний ревьюер. Но последнее слово всё равно за тобой: в `acceptEdits` правки применяются без вопросов, и `git diff` — единственное место, где ты видишь всё целиком.

## 8. История: git log как память проекта

Когда коммиты маленькие и с понятными сообщениями, история отвечает на вопросы «когда сломалось?» и «зачем эта строка?».

```bash
git log --oneline            # список коммитов
git log -p models.py         # все изменения одного файла с diff
git show <hash>              # один коммит целиком
```

Хорошее сообщение коммита: первая строка — **что** сделано в повелительном наклонении («Исправить дубликат id после удаления»), при необходимости ниже — **почему**. Плохое: «fix», «правки», «wip».

Claude хорошо работает с историей: «по git log найди коммит, в котором поменялась сортировка, и объясни изменение» или «составь CHANGELOG.md по истории коммитов».

> **Почему так?** Через месяц ты не вспомнишь, зачем менялась строка. Сообщение коммита — единственная записка «почему», которая живёт рядом с кодом и находится одной командой. Claude тоже читает её — и лучше понимает проект.

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| CLI | программа, которой управляют командами и аргументами в терминале |
| venv | изолированное окружение Python-пакетов для одного проекта |
| bug report | описание бага: шаги, ожидаемый и фактический результат |
| reproduce | воспроизвести баг по шагам, чтобы он проявился гарантированно |
| test / pytest | код, который проверяет код / библиотека для запуска тестов |
| assert | проверка в тесте: если условие ложно, тест падает |
| regression test | тест на уже исправленный баг, чтобы он не вернулся |
| fixture | заготовка для тестов в pytest, например `tmp_path` — временная папка |
| git / repository | система версий / папка проекта с историей |
| commit | сохранённый снимок изменений с сообщением |
| diff | построчная разница между двумя версиями |
| staging (`git add`) | отбор изменений в следующий коммит |
| `.gitignore` | список файлов, которые git не отслеживает |
| code review | чтение чужих изменений с целью найти проблемы до принятия |
