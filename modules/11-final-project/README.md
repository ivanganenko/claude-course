# Модуль 11. Финальный проект

> **Зачем:** собрать всё, чему ты научился, в один набор инструментов для **своей** реальной задачи — и уметь объяснить каждое решение. **Время:** ~6–10 ч, удобно растянуть на 1–2 недели. **Нужно:** пройдены модули 01–10 (обязательные упражнения приняты).

## Что ты будешь уметь

- Превращать рабочую рутину в чёткую постановку задачи для Claude-инструментов.
- Выбирать подходящий механизм для каждой части задачи: CLAUDE.md, skill, subagent, MCP server, hook — и обосновывать выбор.
- Планировать проект этапами с проверяемыми результатами.
- Защищать свои решения: отвечать на вопрос «почему так, а не иначе».
- Оценивать результат честно: что сработало, что нет, что сделаешь по-другому.

Новой теории в модуле нет. Этот README — **бриф проекта** (описание задачи и правил игры). Этапы оформлены как упражнения в `exercises.md`.

---

## 1. Что нужно сделать

Собрать в папке `~/claude-practice/final-project/` (или в своём рабочем репозитории — см. раздел 5 о данных) **рабочую среду Claude Code для одной своей задачи**: настроенный проект, в котором Claude знает контекст, умеет выполнять твои повторяющиеся процессы, имеет доступ к нужным данным и защищён от ошибок.

Критерий успеха простой: **ты (или коллега) реально пользуешься этим** и делаешь задачу быстрее или качественнее, чем раньше.

> **Почему так?** Курсовой проект «для галочки» забывается через неделю. Проект на своей задаче остаётся с тобой как инструмент — и каждая следующая доработка закрепляет навык. Кроме того, на реальной задаче вылезают настоящие проблемы (грязные данные, неясные требования), которых нет в учебном todo-app.

---

## 2. Варианты тем

Выбери одну из тем или предложи свою. Главное — задача должна **повторяться** (раз в неделю или чаще) и быть **твоей**.

### Вариант А. Ассистент для рабочей рутины

Примеры:
- **Разбор входящих писем/заявок.** Папка с выгруженными письмами (`.txt`/`.eml`) → классификация, черновики ответов по шаблонам компании, сводка «что срочно».
- **Еженедельный отчёт.** Таблицы с цифрами (CSV/Excel-выгрузки) → сводка, сравнение с прошлой неделей, текст для руководителя.
- **Протоколы встреч.** Сырые заметки → структурированный протокол, список задач с ответственными, письмо-итог.

Типичный набор: skills для каждого вида документа, subagent-«проверяющий» (сверяет цифры/факты), MCP server к папке/таблице с данными, hook, защищающий исходники от правки.

### Вариант Б. Инструменты разработчика для todo-app (или своего кода)

Примеры:
- Полный цикл фичи: skill «новая команда CLI», subagents test-writer и code-reviewer, hooks тестов и защиты данных, MCP server к `todos.json` (tools «задачи на сегодня», «просроченные»).
- Свой небольшой скрипт с работы (обработка файлов, выгрузка) — то же самое, но на реальном коде.

Типичный набор: CLAUDE.md с командами и конвенциями, skills (commit-message, release-notes), 2 subagents, MCP к данным, hooks PreToolUse + PostToolUse.

### Вариант В. MCP к своим данным

Примеры:
- Свой MCP server к таблице заказов/клиентов (**обезличенной**), чтобы спрашивать Claude «какие заказы задерживаются» и получать ответ из данных, а не из догадок.
- MCP server к личной базе знаний (папка заметок/инструкций) с tools поиска и resources.

Типичный набор: свой FastMCP server с 3+ tools, skill «отчёт по данным», subagent-аналитик, hook, запрещающий запись в исходные данные.

### Своя тема

Подойдёт, если в ней есть повторяющийся процесс, данные и место для каждого обязательного компонента. Согласуй тему с учителем на этапе 1.

> **Почему так?** Три варианта покрывают типичные роли студентов курса: офисная работа, работа с кодом, работа с данными. Но рамка одна: процесс + данные + инструменты + защита. Если для темы не находится места для какого-то компонента — это сигнал, что тема слишком узкая, а не что компонент «не нужен».

## 3. Обязательные компоненты

| Компонент | Минимум | Зачем в проекте (модуль) |
|-----------|---------|--------------------------|
| `CLAUDE.md` | 1, краткий (≤ 60 строк) | постоянный контекст: что за проект, команды, правила, «почему» (06) |
| Skills | ≥ 2 | упакованные повторяющиеся процессы; хотя бы один с аргументами или скриптом (07) |
| Subagent | ≥ 1 | изолированная роль: проверка, анализ, разведка; tools ограничены по роли (09) |
| MCP server | ≥ 1 (готовый или свой) | доступ к данным/системе, которых нет в Claude Code (08) |
| Hook | ≥ 1 | автоматика или защита, которая должна срабатывать всегда (10) |
| `README.md` проекта | 1 | что это, как установить/запустить, **почему** выбраны именно такие решения |

Плюс по умолчанию: проект под **git**, `.claude/settings.json` с осмысленными permissions, секреты — только в переменных окружения.

Не обязательно, но засчитывается как плюс: headless-скрипт (`claude -p`), plugin, второй subagent, свой MCP server вместо готового.

> **Почему так?** Каждый компонент решает свой класс проблем: CLAUDE.md — «Claude не знает контекста», skill — «каждый раз объясняю одно и то же», subagent — «context засоряется / нужен независимый взгляд», MCP — «нет доступа к данным», hook — «нужна гарантия, а не просьба». Требование «хотя бы по одному» заставляет тебя на реальной задаче найти, где каждый из них действительно нужен, — это и есть главный навык курса.

### Как понять, что компонент «настоящий», а не для галочки

Для каждого компонента ты должен ответить на три вопроса:
1. **Какую проблему он решает** в твоей задаче? (конкретный пример)
2. **Почему именно этот механизм**, а не другой? (почему skill, а не строчка в CLAUDE.md; почему hook, а не deny)
3. **Как ты проверил**, что он работает? (демонстрация, тест, сравнение «до/после»)

Эти ответы войдут в README проекта и в защиту.

Пример хорошего ответа для одного компонента (вымышленный проект «еженедельная сводка по заявкам»):

| Вопрос | Слабый ответ | Сильный ответ |
|--------|--------------|---------------|
| Какую проблему решает hook `protect_data`? | «защищает данные» | «Claude дважды пытался "почистить" CSV с заявками перед подсчётом — а это исходник, второй копии нет» |
| Почему hook, а не другой механизм? | «так надо по заданию» | «Правило в CLAUDE.md — просьба, он его нарушил. deny тоже подошёл бы, но hook объясняет Claude, что результаты писать в `reports/`, — и он сразу так и делает» |
| Как проверил? | «работает» | «вручную: JSON с `data/tickets.csv` → exit 2; в сессии: попросил "исправь опечатку в CSV" → блок и запись в `reports/`» |

Обрати внимание: сильный ответ всегда содержит **конкретный случай** и **отвергнутую альтернативу**.

## 4. Этапы и чекпоинты

Проект идёт пятью этапами. На каждом — **чекпоинт**: ты показываешь результат учителю (`/check 11.N`) и получаешь ОК, прежде чем идти дальше.

| Этап | Результат | Упражнение | Время |
|------|-----------|-----------|-------|
| 1. Идея | `BRIEF.md`: задача, пользователь, данные, критерий успеха | 1 | ~1 ч |
| 2. План | `PLAN.md`: компоненты, их роли, порядок работы, риски | 2 | ~1 ч |
| 3. Реализация | CLAUDE.md, skills, subagent, MCP, hook — по частям | 3, 4 | ~3–5 ч |
| 4. Демо | `README.md` проекта + сценарий демо + запись результатов | 5 | ~1 ч |
| 5. Ретро и защита | `RETRO.md` + ответы на вопросы учителя | 5 | ~1 ч |
| ⭐ | упаковка в plugin / передача коллеге | 6 | ~1–2 ч |

> **Почему так?** Чекпоинты ловят ошибки, пока они дешёвые. Неудачную тему лучше заменить на этапе 1 (час работы), чем после реализации (десять часов). Это тот же принцип, что plan mode и «покажи план перед реализацией» (модули 04, 09), применённый к тебе самому.

### Этап 1. Идея

Опиши задачу так, будто ставишь её новому коллеге (модуль 03): кто пользователь, что он делает сейчас, сколько времени это занимает, что болит, какие данные на входе и что на выходе, как понять, что стало лучше.

→ **Упражнение 1** (см. exercises.md)

### Этап 2. План

Разложи задачу на компоненты. Для каждого — роль и обоснование. Нарисуй (текстом) поток: что делает пользователь → что вызывается → какие данные откуда. Отметь риски: что может сломаться, где Claude может ошибиться, какие данные чувствительны.

Используй Claude в plan mode как партнёра: пусть задаст тебе уточняющие вопросы (модуль 04). Но решения — твои.

→ **Упражнение 2** (см. exercises.md)

### Этап 3. Реализация

Делай по слоям, **коммить после каждого**:
1. Фундамент: git, CLAUDE.md, settings.json, тестовые данные.
2. Skills — по одному, каждый проверить вызовом.
3. MCP server — подключить, проверить `/mcp`, проверить tools.
4. Subagent — создать, проверить вызов и ограничения.
5. Hook — проверить вручную, потом в сессии.

→ **Упражнение 3** (фундамент и skills)
→ **Упражнение 4** (MCP, subagent, hook)

> **Почему так?** Слои добавляются от простого к сложному и от независимого к зависимому: skill может использовать MCP tool, hook защищает данные, которые читает MCP. Если собирать всё сразу и что-то не работает, непонятно, где искать. Коммит после слоя — точка отката.

### Этап 4. Демо

Подготовь сценарий на 5–10 минут: реальная задача от начала до конца с использованием твоих инструментов. Запиши, что получилось (вывод, файлы, время), — лучше на свежей сессии (`/clear`), чтобы было видно, что работает «из коробки», а не на накопленном контексте.

### Этап 5. Ретро и защита

**Ретро** (ретроспектива — честный разбор после проекта): что сработало, что нет, что удивило, что сделаешь иначе, что доработаешь дальше.

**Защита**: учитель задаёт вопросы «почему ты сделал так?» по каждому компоненту. Готовься объяснять компромиссы, а не только «что сделано».

→ **Упражнение 5** (см. exercises.md)

### ⭐ После защиты: передать инструмент другим

Если проект полезен не только тебе — упакуй его в plugin (модуль 10) и попробуй установить в чистой папке или у коллеги. Это лучший тест: всё ли в проекте объяснено и самодостаточно.

→ **Упражнение 6** ⭐ (см. exercises.md)

## 5. Данные и безопасность

Это проект на **твоей реальной задаче** — значит, рядом реальные данные. Правила:

- **Никаких реальных персональных данных клиентов и коллег** в проекте, prompts, CLAUDE.md и примерах. Используй обезличенные или выдуманные данные той же структуры: «ООО Ромашка», «Иван Тестов», заказ №0001.
- **Секреты** (токены, пароли, ключи API) — только в переменных окружения, `.env` в `.gitignore`, deny на чтение `.env`.
- **Политика работодателя.** Прежде чем подключать рабочие системы (почту, CRM, базу), убедись, что это разрешено правилами компании. Если сомневаешься — делай на выгрузке с фейковыми данными.
- **Исходные данные — только на чтение.** Hook или deny, запрещающий Claude менять «сырьё». Результаты — в отдельную папку.

> **Почему так?** Всё, что попадает в prompt или читается Claude, уходит в модель как часть context. Обезличенные данные той же структуры дают тот же учебный эффект без риска. А разделение «сырьё read-only / результаты отдельно» — это страховка от самой обидной ошибки: агент «улучшил» исходную таблицу, и оригинала больше нет.

## 6. Критерии оценки

Итог — 100 баллов. Проект принят при **≥ 70 баллах и наличии всех обязательных компонентов**.

| Блок | Баллы | Что оценивается |
|------|-------|-----------------|
| Постановка (BRIEF, PLAN) | 10 | реальная повторяющаяся задача; измеримый критерий успеха; риски названы |
| CLAUDE.md | 10 | кратко; команды, правила, «почему»; нет того, что видно из кода; нет секретов |
| Skills (≥ 2) | 15 | точные `description`; хотя бы один с аргументами/скриптом; проверены вызовом |
| Subagent (≥ 1) | 10 | понятная роль; tools ограничены по роли; формат ответа; проверен |
| MCP server (≥ 1) | 10 | подключён правильным scope; tools работают; безопасность (токены через env, доверие) |
| Hook (≥ 1) | 10 | решает реальную проблему; проверен вручную и в сессии; быстрый и устойчивый |
| Безопасность и git | 5 | permissions, `.env`, данные read-only, история коммитов по этапам |
| README проекта | 10 | установка и запуск; **почему** каждый компонент; ограничения |
| Демо | 10 | сценарий выполняется на свежей сессии; есть «до/после» |
| Ретро и защита | 10 | честный разбор; уверенные ответы «почему» на вопросы учителя |

Плюсы (до +10 сверх 100, не компенсируют отсутствие обязательного): headless-скрипт, plugin, свой MCP server, второй subagent, реальное использование коллегой.

> **Почему так?** Больше всего баллов — у того, что требует решений (skills, README с «почему», защита), а не у того, что можно скопировать. Порог 70 позволяет иметь слабые места — проект на реальной задаче никогда не идеален, — но не позволяет пропустить компонент: цель курса — чтобы ты уверенно владел каждым механизмом.

## 7. Частые ловушки

- **Слишком большая тема.** «Автоматизировать весь отдел продаж» не помещается в 10 часов. Сузь до одного процесса: «еженедельная сводка по просроченным счетам».
- **Компоненты ради компонентов.** Subagent, который делает то же, что skill. Если не можешь ответить «почему subagent, а не skill» — пересмотри.
- **Раздутый CLAUDE.md.** Всё подряд «на всякий случай». Каждая строка тратит context в каждой сессии (модуль 06).
- **Без проверки «из коробки».** Всё работает в сессии, где ты два часа настраивал, но не в новой. Демо — на `/clear` или новой сессии.
- **Hook, который мешает.** Тесты на каждый чих по 2 минуты. Фильтруй события.
- **Реальные данные в git.** Проверь `git log -p` перед тем, как кому-то показывать репозиторий.
- **Claude сделал всё за тебя.** Пусть Claude пишет код — это нормально. Но решения (что, зачем, почему так) — твои, и на защите ты должен их объяснить.

> **Почему так?** Почти все ловушки — об одном: проект перестаёт служить задаче и начинает служить чек-листу. Хороший фильтр для любого решения — вопрос «что сломается или станет хуже, если это убрать?». Если ответа нет — компонент лишний или поставлен не туда.

## Шпаргалка: какой механизм выбрать

| Проблема | Механизм | Где |
|----------|----------|-----|
| Claude не знает, что это за проект и как здесь принято | `CLAUDE.md` | `./CLAUDE.md`, `.claude/rules/*.md` |
| Каждый раз объясняю один и тот же процесс | skill | `.claude/skills/<name>/SKILL.md` |
| Процесс нужен с параметром | skill + `$ARGUMENTS` | `/name аргументы` |
| Нужна независимая проверка / разведка без засорения context | subagent | `.claude/agents/<name>.md`, `/agents` |
| Нужны данные/система, недоступные Claude | MCP server | `claude mcp add ...`, `.mcp.json`, `/mcp` |
| Действие должно происходить **всегда** | hook | `settings.json` → `hooks`, `/hooks` |
| Действие **никогда** не должно происходить | deny или PreToolUse hook | `settings.json` → `permissions.deny` |
| Частые безопасные команды без вопросов | allow | `settings.json` → `permissions.allow` |
| Запуск из скрипта / по расписанию | headless | `claude -p "..."`, `--output-format json` |
| Поделиться набором с коллегой | plugin | `.claude-plugin/plugin.json`, `/plugin` |

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| бриф (brief) | краткое описание задачи: кто, что, зачем, критерий успеха |
| чекпоинт (checkpoint) | точка проверки результата этапа перед переходом к следующему |
| критерий успеха | измеримый признак того, что проект помог (время, ошибки, объём ручной работы) |
| демо (demo) | показ работы проекта на реальном сценарии |
| ретро (retrospective) | разбор после проекта: что сработало, что нет, что изменить |
| защита | ответы на вопросы о причинах решений |
| обезличенные данные | данные той же структуры, но без реальных людей и компаний |

## Вопросы для самопроверки

1. Какую задачу ты выбрал и почему она подходит для автоматизации с Claude (как часто повторяется, сколько времени занимает)?
2. Для каждого обязательного компонента: какую проблему он решает в твоём проекте?
3. Где в твоём проекте ты выбрал skill, а не subagent (или наоборот), и почему?
4. Почему для твоего hook нужен именно hook, а не правило в CLAUDE.md или deny?
5. Какие данные в проекте чувствительны и как ты их защитил?
6. Как ты проверил, что проект работает на свежей сессии, а не только на накопленном контексте?
7. Что в проекте было бы сделано иначе, если бы им пользовалась команда из 5 человек?
