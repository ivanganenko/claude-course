# Модуль 11 — практика

> Где выполнять: `~/claude-practice/final-project/` — новая папка под git, отдельная сессия Claude Code (терминал «Практика»). Если проект живёт в твоём рабочем репозитории — дай учителю доступ через `/add-dir <путь>` и убедись, что в нём нет реальных персональных данных (README, раздел 5).
> Из `practice/` можно переиспользовать что угодно: `todo-app/` (вариант Б), `mcp-server/` (вариант В), `hooks/`, `agent-loop/`.
>
> Каждый этап сдаётся отдельно (`/check 11.N`). Не переходи к следующему этапу без ОК — так ошибки ловятся, пока они дешёвые.
>
> Создание папки:
> - Windows PowerShell: `New-Item -ItemType Directory $HOME\claude-practice\final-project; cd $HOME\claude-practice\final-project; git init`
> - macOS / Linux: `mkdir -p ~/claude-practice/final-project && cd ~/claude-practice/final-project && git init`

## Упражнение 1. Идея и бриф  ·  ⏱ ~60 мин  ·  обязательное

**Цель:** выбрать задачу и описать её в `BRIEF.md` так, чтобы по брифу можно было начать работу.
**Зачем:** хорошая постановка — половина результата (модуль 03). Слишком широкая или «не твоя» тема — главная причина, по которой финальные проекты не доводятся до конца.

**Шаги:**
1. Выпиши 3 кандидата — повторяющиеся задачи из своей работы или учёбы (или варианты А/Б/В из README). Для каждого: как часто, сколько времени занимает, что раздражает.
2. Выбери одну. Критерии: повторяется ≥ раз в неделю; есть данные на входе; результат можно проверить; помещается в ~10 часов работы.
3. Попроси Claude провести с тобой «интервью» (модуль 04):
   ```
   Я хочу сделать набор инструментов Claude Code для задачи: <одна фраза>.
   Задай мне по одному 5–7 уточняющих вопросов, чтобы составить бриф
   (пользователь, входные данные, результат, критерий успеха, ограничения).
   Не предлагай решений, пока не закончишь вопросы.
   ```
4. Напиши `BRIEF.md` (сам, Claude — только как собеседник) с разделами:
   - **Задача** — 2–3 предложения;
   - **Пользователь** — кто и в какой ситуации пользуется;
   - **Как сейчас** — шаги, время, боли;
   - **Входные данные** — какие, откуда, формат, **чувствительны ли** и как обезличишь;
   - **Результат** — что на выходе;
   - **Критерий успеха** — измеримо: «сводка за 5 мин вместо 40», «0 ручных копирований»;
   - **Вне рамок** — что сознательно НЕ делаешь.
5. Подготовь тестовые данные (обезличенные) — 3–10 примеров входа в папке `data/` или `samples/`. Закоммить.

**Что сдать на проверку:** `BRIEF.md`, папка с тестовыми данными, первый коммит.
**Критерии готовности:**
- [ ] Задача повторяющаяся и твоя (или явно согласована с учителем).
- [ ] Критерий успеха измеримый.
- [ ] Есть раздел «Вне рамок».
- [ ] Тестовые данные есть и не содержат реальных персональных данных.

## Упражнение 2. План и архитектура  ·  ⏱ ~60 мин  ·  обязательное

**Цель:** спроектировать набор компонентов и записать план с обоснованием каждого решения.
**Зачем:** план — дешёвое место для ошибок. Перенести skill в subagent на бумаге — минута, в коде — час.

**Шаги:**
1. Включи plan mode. Дай Claude прочитать `BRIEF.md` и попроси предложить архитектуру: какие компоненты (CLAUDE.md, skills, subagents, MCP, hooks) и зачем. Попроси **2 альтернативы** с плюсами и минусами.
2. Выбери и доработай сам. Запиши `PLAN.md`:
   - **Компоненты** — таблица: компонент | имя | что делает | почему этот механизм, а не другой;
   - **Поток** — по шагам: что делает пользователь → что вызывается → какие данные откуда и куда;
   - **Permissions** — что разрешить, что запретить;
   - **Риски** — минимум 3 (Claude ошибётся в цифрах, MCP server недоступен, prompt injection в данных…) и как снижаешь каждый;
   - **Порядок реализации** — слои и что проверяешь после каждого;
   - **Демо-сценарий** — черновик.
3. Проверь план по чек-листу: все обязательные компоненты есть? Для каждого ответ «почему именно он»? Нет ли компонента «для галочки»?
4. Закоммить.

**Что сдать на проверку:** `PLAN.md`.
**Критерии готовности:**
- [ ] Все обязательные компоненты в плане (CLAUDE.md, ≥2 skills, ≥1 subagent, ≥1 MCP, ≥1 hook).
- [ ] Для каждого — обоснование выбора механизма с альтернативой.
- [ ] ≥ 3 риска с мерами.
- [ ] Порядок реализации послойный, с проверками.
- [ ] В заметках видно, что предложение Claude было доработано, а не принято как есть.

## Упражнение 3. Реализация: фундамент и skills  ·  ⏱ ~2 ч  ·  обязательное

**Цель:** создать фундамент проекта (CLAUDE.md, settings, .gitignore) и минимум два skills.
**Зачем:** фундамент определяет, как Claude «понимает» проект в каждой сессии; skills — основная рабочая сила для повторяющихся процессов.

**Шаги:**
1. `.gitignore` (`.env`, `__pycache__/`, `.venv/`, `CLAUDE.local.md`, `.claude/settings.local.json`, папка результатов — по ситуации).
2. `CLAUDE.md` (≤ 60 строк): что за проект, структура папок, команды, правила работы с данными (сырьё — только чтение), стиль результатов, «почему» для неочевидных правил. Можно начать с `/init` и **сократить**.
3. `.claude/settings.json` с permissions по `PLAN.md`.
4. Skill 1 и skill 2 по плану. Хотя бы один — с `$ARGUMENTS` или со скриптом. `description` — «когда использовать».
5. Проверь каждый skill:
   - явный вызов `/name аргументы` на тестовых данных;
   - автоматический вызов — фразой, похожей на реальный запрос, **без** имени skill (в новой сессии);
   - запиши результат в `TESTING.md` (что вызвал, что получил, что исправил).
6. Проверь CLAUDE.md: `/clear`, задай вопрос, ответ на который требует правила из CLAUDE.md. Следует ли Claude?
7. Коммит после каждого пункта (или хотя бы после 3 и после 5).

**Что сдать на проверку:** `CLAUDE.md`, `.claude/settings.json`, `.claude/skills/*`, `TESTING.md`, история коммитов.
**Критерии готовности:**
- [ ] CLAUDE.md краткий, без секретов и без того, что видно из кода.
- [ ] 2+ skills; хотя бы один с аргументами или скриптом.
- [ ] Каждый skill проверен явным вызовом; хотя бы один срабатывает автоматически.
- [ ] Permissions соответствуют плану; `.env` (если есть) закрыт.
- [ ] Коммиты по шагам.

## Упражнение 4. Реализация: MCP, subagent, hook  ·  ⏱ ~2–3 ч  ·  обязательное

**Цель:** подключить MCP server, создать subagent и hook по плану и проверить их связку.
**Зачем:** это компоненты, которые дают Claude данные (MCP), независимый взгляд (subagent) и гарантии (hook). Без них проект — просто набор prompts.

**Шаги:**
1. **MCP server.** Готовый или свой (FastMCP, на основе `practice/mcp-server/`). Выбери scope осознанно (local / project через `.mcp.json`) и запиши почему. Токены — через `--env`/переменные окружения. Проверь `/mcp` и вызов каждого tool фразой на естественном языке.
2. **Subagent.** `.claude/agents/<name>.md`: роль, `description` («когда»), `tools` — минимум для роли, `model` — с обоснованием, формат ответа. Проверь явный вызов и что ограничения tools работают. Если агенту нужен MCP tool — проверь, что он ему доступен (имя `mcp__<server>__<tool>`).
3. **Hook.** Скрипт в `.claude/hooks/`, подключение в `settings.json`. Проверь **вручную** (подать JSON на stdin, посмотреть exit code), потом в сессии (`/hooks` + реальное срабатывание).
4. **Связка.** Прогони целиком один реальный сценарий из `PLAN.md`: skill → данные через MCP → проверка subagent → hook срабатывает при попытке тронуть сырьё. Запиши в `TESTING.md`.
5. Обнови `PLAN.md`, если в реализации что-то пошло иначе, — с пометкой «изменено, потому что…».
6. Закоммить.

**Что сдать на проверку:** `.mcp.json` или команда подключения (в README), код MCP server (если свой), `.claude/agents/*`, `.claude/hooks/*`, обновлённые `settings.json`, `TESTING.md`, `PLAN.md`.
**Критерии готовности:**
- [ ] MCP server подключён, tools вызываются; секретов нет в файлах.
- [ ] Subagent с ограниченными tools и форматом ответа; вызов проверен.
- [ ] Hook проверен вручную (exit code) и в сессии.
- [ ] Сквозной сценарий прогнан и описан.
- [ ] Отклонения от плана зафиксированы с причинами.

## Упражнение 5. README, демо, ретро и защита  ·  ⏱ ~2 ч  ·  обязательное

**Цель:** оформить проект так, чтобы его понял и запустил другой человек, показать демо на свежей сессии, провести ретро и защитить решения.
**Зачем:** инструмент, который понимает только автор, умирает, когда автор занят. А умение объяснить «почему» — это проверка, что решения действительно твои.

**Шаги:**
1. **README.md проекта:**
   - что это и для кого (1 абзац);
   - что нужно установить; как запустить (команды для Windows и macOS/Linux, если различаются); какие переменные окружения задать (без значений!);
   - **компоненты и почему** — таблица: компонент | что делает | почему этот механизм;
   - как пользоваться — 2–3 примера запросов;
   - ограничения и известные проблемы.
2. **Демо.** Новая сессия (или `/clear`). Пройди демо-сценарий от начала до конца. Сохрани результат (файлы результата + `DEMO.md`: запросы, что произошло, сколько времени, сравнение с «как было» из `BRIEF.md`).
3. **Ретро** — `RETRO.md`:
   - достигнут ли критерий успеха из брифа (с цифрами);
   - что сработало лучше ожиданий / хуже;
   - что удивило в поведении Claude;
   - 3 вещи, которые сделал бы иначе;
   - что доработаешь в следующие 2 недели.
4. Проверь безопасность: `git log -p | findstr /i "token key password"` (PowerShell/cmd) или `git log -p | grep -iE "token|key|password"` (bash) — нет ли секретов в истории; нет реальных персональных данных.
5. **Защита.** Скажи учителю «готов к защите 11.5». Учитель задаст 5–8 вопросов «почему так?» по компонентам. Отвечай про компромиссы и альтернативы.

**Что сдать на проверку:** `README.md`, `DEMO.md`, `RETRO.md`, результаты демо; устная защита.
**Критерии готовности:**
- [ ] README позволяет запустить проект человеку, который его не видел.
- [ ] Таблица «компонент — почему» заполнена для всех компонентов.
- [ ] Демо проведено на свежей сессии, результат сохранён, есть сравнение с «как было».
- [ ] Ретро честное, с цифрами по критерию успеха.
- [ ] Секретов и персональных данных в истории git нет.
- [ ] Защита пройдена: на каждый вопрос «почему» есть содержательный ответ.

## Упражнение 6 ⭐. Передать инструмент другим  ·  ⏱ ~1–2 ч  ·  необязательное

**Цель:** сделать так, чтобы твоим инструментом воспользовался кто-то другой (коллега или ты сам в чистом окружении).
**Зачем:** настоящая проверка инструмента — человек без твоего контекста. Всё, что «и так понятно» автору, всплывает при первой установке у другого.

**Шаги:**
1. Выбери способ: plugin (модуль 10, упражнение 6) **или** чистый git-репозиторий с инструкцией.
2. Установи в **чистой** папке (или у коллеги), строго следуя своему README. Записывай каждое место, где пришлось сделать что-то, не описанное в README.
3. Исправь README/plugin по найденным пробелам.
4. Если есть коллега — попроси его выполнить одну реальную задачу твоим инструментом и дать обратную связь (3 вопроса: что понятно, что нет, стал бы пользоваться?).
5. Добавь раздел в `RETRO.md`: что выяснилось при передаче.
6. (Плюс) Добавь headless-сценарий: скрипт с `claude -p`, который выполняет основную задачу без интерактивной сессии (например, по расписанию).

**Что сдать на проверку:** обновлённые README/plugin, раздел ретро о передаче, (если есть) отзыв коллеги без персональных данных.
**Критерии готовности:**
- [ ] Установка в чистом окружении прошла по README без «устных» подсказок.
- [ ] Найденные пробелы исправлены.
- [ ] Выводы записаны в ретро.
