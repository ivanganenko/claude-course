# Модуль 06 — практика

> Где выполнять: `~/claude-practice/todo-app` (проект из модуля 05, под git), отдельная сессия Claude Code. Для упражнения 4 понадобится ещё пустая папка `~/claude-practice/scratch`. Из `practice/` ничего копировать не нужно.

Перед каждым упражнением: `git status` — рабочая копия чистая. Так любой эксперимент можно откатить.

## Упражнение 1. `/init` и критика результата  ·  ⏱ ~25 мин  ·  обязательное

**Цель:** сгенерировать CLAUDE.md для todo-app и оценить, что в нём полезно, а что — нет.
**Зачем:** `/init` — самый быстрый старт, но его результат нужно уметь критиковать. Навык «отличить полезное правило от пересказа кода» пригодится в каждом проекте.

**Шаги:**
1. В папке todo-app запусти `claude` и выполни `/init`.
2. Переименуй результат в `CLAUDE.generated.md` (можно попросить Claude или сделать вручную) — он нужен для сравнения в следующем упражнении.
3. Прочитай файл и разметь **каждый** пункт одной из меток:
   - ✅ полезно — без этого Claude ошибётся;
   - 🗑 очевидно — Claude увидит это из кода за секунду;
   - ❓ неточно — проверь (запусти команду, открой файл).
4. Запусти все команды, упомянутые в файле. Работают ли они на твоём компьютере (Windows/macOS)?
5. Составь список того, чего в файле **нет**, но что знаешь ты после модуля 05 (минимум 3 пункта). Подсказка: вспомни, что ты повторял Claude несколько раз.
6. Посмотри `/context`: сколько места занимает memory?

**Что сдать на проверку:** `CLAUDE.generated.md` с твоей разметкой (метки можно поставить прямо в файле); список «чего не хватает»; результат проверки команд.

**Критерии готовности:**
- [ ] Каждый пункт сгенерированного файла размечен
- [ ] Команды из файла реально запущены, неработающие отмечены
- [ ] ≥ 3 пункта «чего не хватает» — знание, которого нет в коде
- [ ] Студент объясняет, почему «очевидные» пункты вредны (context, внимание)

## Упражнение 2. Свой CLAUDE.md для todo-app  ·  ⏱ ~30 мин  ·  обязательное

**Цель:** написать короткий CLAUDE.md, который содержит только полезное.
**Зачем:** CLAUDE.md — prompt, который будет работать в каждой сессии. Хорошо написанный экономит твоё время ежедневно; плохой — тратит context и путает.

**Шаги:**
1. Напиши `CLAUDE.md` в корне todo-app **сам** (Claude можно попросить покритиковать, но не написать). Ограничение: **не больше 40 строк**.
2. Обязательно включи:
   - одну строку «что это за проект»;
   - команды запуска и тестов (проверенные в упр. 1);
   - ≥ 3 правила с причиной («…потому что…»);
   - ≥ 1 запрет с альтернативой («не делай X, вместо этого Y»).
3. Пройди по каждой строке тестом «если удалить, Claude начнёт ошибаться?» — удали лишнее.
4. Попроси Claude в **новой сессии**: «Прочитай CLAUDE.md. Какие правила тебе непонятны или противоречат коду?» Исправь, если есть замечания по делу.
5. Удали `CLAUDE.generated.md`, закоммить `CLAUDE.md`.

**Что сдать на проверку:** `CLAUDE.md`; что ты удалил на шаге 3 и почему; ответ Claude из шага 4.

**Критерии готовности:**
- [ ] ≤ 40 строк, нет пересказа структуры кода
- [ ] Команды точные и работают
- [ ] ≥ 3 правила с причиной, ≥ 1 запрет с альтернативой
- [ ] Нет секретов, личных путей, общих советов «пиши хороший код»
- [ ] Закоммичено

## Упражнение 3. A/B тест правила  ·  ⏱ ~40 мин  ·  обязательное

**Цель:** экспериментально доказать, что правило из CLAUDE.md меняет поведение Claude.
**Зачем:** «Claude прочитал файл» не значит «Claude следует правилу». Без эксперимента ты не знаешь, работает ли твоя память, — и не узнаешь, когда она перестанет работать.

**Шаги:**
1. Выбери правило с **наблюдаемым** эффектом, которое Claude по умолчанию, скорее всего, не выполнит. Примеры: «каждая новая команда CLI печатает подсказку `Подробнее: python todo.py <команда> --help` при ошибке»; «все новые функции — с docstring на русском, начинающимся с глагола»; «сообщения коммитов — на русском, в повелительном наклонении, ≤ 50 символов». Можно своё.
2. Придумай задачу-prompt, в которой правило должно проявиться, но **не упоминай** его. Например: «Добавь команду `count`, которая печатает число невыполненных задач, и закоммить».
3. **Вариант A (без правила):** убедись, что правила нет в CLAUDE.md. Новая сессия → prompt → запиши результат (`git diff` / `git log -1`) → откати изменения: `git restore .`. Если в задаче был коммит, понадобится `git reset --hard HEAD~1` — эта команда безвозвратно удаляет последний коммит и все незакоммиченные правки, поэтому сначала попроси Claude объяснить её и запускай, только когда понимаешь, что произойдёт.
4. **Вариант B (с правилом):** добавь правило в CLAUDE.md, закоммить. Новая сессия → **тот же** prompt → запиши результат → откати изменения задачи.
5. Повтори каждый вариант ещё хотя бы раз.
6. Заполни таблицу и сделай вывод.

| Прогон | Правило в CLAUDE.md | Выполнено? | Что именно увидел |
|--------|--------------------|-----------|-------------------|
| A1 | нет | | |
| A2 | нет | | |
| B1 | да | | |
| B2 | да | | |

**Что сдать на проверку:** формулировка правила; prompt задачи; заполненная таблица; вывод в 2–3 предложения. Если правило не сработало в B — что ты изменил в формулировке и результат повторного прогона.

**Критерии готовности:**
- [ ] Правило проверяемое (результат видно в diff/выводе)
- [ ] Prompt одинаковый в A и B и не содержит подсказки о правиле
- [ ] Каждый прогон — в новой сессии или после `/clear`
- [ ] ≥ 2 прогона на вариант
- [ ] Вывод опирается на таблицу; при провале B — есть попытка улучшить формулировку

## Упражнение 4. Личная память  ·  ⏱ ~25 мин  ·  обязательное

**Цель:** настроить user-level CLAUDE.md и `CLAUDE.local.md` и проверить, где что действует.
**Зачем:** личные предпочтения повторяются во всех проектах; записав их один раз, ты перестаёшь повторять их в каждом prompt.

**Шаги:**
1. Создай `~/.claude/CLAUDE.md` (README, раздел 6) с 3–6 личными предпочтениями. Хотя бы одно должно быть легко наблюдаемым (например, «в конце каждого ответа — строка `Следующий шаг: …`» или «сначала вывод одной фразой, потом детали»).
2. Создай папку `~/claude-practice/scratch`, запусти там `claude` и задай любой вопрос. Проявилось ли наблюдаемое предпочтение? Выполни `/memory` — какие файлы видны?
3. В todo-app создай `CLAUDE.local.md` с одной-двумя личными заметками (например, путь к своему тестовому файлу данных). Добавь `CLAUDE.local.md` в `.gitignore`. Проверь `git status`: файл не должен появиться как новый.
4. В todo-app выполни `/memory` и `/context`. Сколько memory files загружено и сколько они занимают?
5. Ответь себе: какое из твоих предпочтений было бы **ошибкой** положить в project CLAUDE.md и почему?

**Что сдать на проверку:** текст `~/.claude/CLAUDE.md`; наблюдение из шага 2; `.gitignore` и вывод `git status` из шага 3; список memory files из шага 4; ответ на шаг 5.

**Критерии готовности:**
- [ ] User CLAUDE.md содержит только личное, без правил конкретного проекта
- [ ] Наблюдаемое предпочтение проверено в другой папке
- [ ] `CLAUDE.local.md` не отслеживается git
- [ ] Студент перечисляет, какие memory files загружены в todo-app, и объясняет откуда каждый

## Упражнение 5. Imports и rules  ·  ⏱ ~30 мин  ·  обязательное

**Цель:** вынести часть правил в отдельные файлы и проверить, что они подхватываются.
**Зачем:** на реальных проектах правил становится много. Imports и rules позволяют держать CLAUDE.md коротким, а тематические правила — там, где они нужны.

**Шаги:**
1. Создай `docs/testing.md` — короткий документ для людей: как запускать тесты, что такое `TODO_FILE`, как писать новый тест (5–10 строк). Подключи его в CLAUDE.md через `@docs/testing.md`, убрав дублирующиеся строки из CLAUDE.md.
2. Создай `.claude/rules/tests.md` с frontmatter `paths:`, указывающим на файлы тестов, и 2–3 правилами для тестов. Одно правило сделай наблюдаемым (например, «каждый тест начинается с комментария `# Проверяет: …`»).
3. Новая сессия → `/memory`: видны ли новые файлы? Что показывает `/context`?
4. Попроси Claude добавить тест для команды `stats`. Выполнено ли наблюдаемое правило из rules?
5. Попроси Claude поправить текст в `README.md`. Упоминал ли он правила тестов? (Ожидаем, что нет — они к README не относятся.)
6. Закоммить.

**Что сдать на проверку:** `CLAUDE.md` с import; `docs/testing.md`; `.claude/rules/tests.md`; наблюдения из шагов 3–5.

**Критерии готовности:**
- [ ] Import работает (файл подгружается, видно в `/memory` или по поведению)
- [ ] Rules-файл с корректным frontmatter `paths:`
- [ ] Наблюдаемое правило проверено на задаче с тестами
- [ ] Нет дублирования между CLAUDE.md и импортируемым файлом

## Упражнение 6. ⭐ CLAUDE.md для своей рабочей папки  ·  ⏱ ~60 мин  ·  со звёздочкой

**Цель:** применить навык к своей реальной (или реалистичной) работе — не к коду.
**Зачем:** CLAUDE.md полезен не только программистам. Папка с отчётами, шаблонами писем или таблицами тоже выигрывает от постоянных правил.

**Шаги:**
1. Создай `~/claude-practice/my-work` и положи туда 3–5 файлов, похожих на твою работу (документы, CSV, шаблоны писем). **Только вымышленные или обезличенные данные** — никаких реальных клиентов и коллег.
2. Напиши CLAUDE.md (≤ 30 строк): что это за папка, кто аудитория результатов, стиль и формат, ≥ 3 правила с причинами, что запрещено (например, «не изменяй исходные файлы в `input/` — результаты пиши в `output/`»).
3. Придумай 3 типовые задачи для этой папки. Выполни каждую в новой сессии и оцени по своим правилам: соблюдено / нет.
4. Для несоблюдённых правил — переформулируй и перепроверь.
5. Сравни через `/context`, сколько занимает memory. Сожми CLAUDE.md так, чтобы он стал короче хотя бы на 20 %, и перепроверь одну задачу.

**Что сдать на проверку:** CLAUDE.md (до и после сжатия); 3 задачи и таблица «правило → соблюдено?»; что изменил в формулировках.

**Критерии готовности:**
- [ ] Только вымышленные/обезличенные данные
- [ ] CLAUDE.md описывает аудиторию, формат и запреты с причинами
- [ ] 3 задачи проверены в новых сессиях, результат зафиксирован
- [ ] Есть итерация: правило переформулировано и перепроверено
- [ ] Сжатая версия не потеряла работающих правил
