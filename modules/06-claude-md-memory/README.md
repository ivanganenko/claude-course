# Модуль 06. CLAUDE.md и память

> **Зачем:** перестать объяснять Claude одно и то же в каждой сессии — записать правила проекта и личные предпочтения в файлы, которые Claude читает сам. **Время:** ~3 ч. **Нужно:** пройден модуль 05; проект `~/claude-practice/todo-app` под git, баги исправлены.

## Что ты будешь уметь

- Объяснять, как устроена memory (память) в Claude Code и почему это просто файлы.
- Выбирать правильный уровень: user, project, local, rules.
- Генерировать CLAUDE.md через `/init` и критически его редактировать.
- Писать короткий CLAUDE.md, который реально меняет поведение Claude.
- Проверять, что Claude следует правилу, — экспериментом, а не на глаз.
- Разбивать память на части через `@imports` и `.claude/rules/`.

## 1. Почему Claude «забывает» и что такое memory

Из модуля 01: модель stateless (без состояния) — каждая новая сессия начинается с чистого листа. В модуле 05 ты, скорее всего, несколько раз повторял Claude одно и то же: «запускай тесты через `python -m pytest`», «не трогай `todos.json`», «отвечай по-русски».

Memory в Claude Code — это **обычные Markdown-файлы** с именем `CLAUDE.md`. В начале сессии Claude Code находит их и добавляет в context (контекст — всё, что модель «видит» в текущем разговоре). Никакой магии: это как если бы ты сам вставлял этот текст первым сообщением в каждую сессию.

Пример `CLAUDE.md` для вымышленного проекта — скрипта, который собирает еженедельный отчёт по продажам:

```markdown
# sales-report

Скрипт собирает еженедельный отчёт по продажам из CSV-выгрузок CRM в Excel.

## Команды
- Запуск: `python report.py data/week.csv`
- Тесты: `python -m pytest`

## Правила
- Суммы считай в копейках (int), не в float — иначе копейки «плывут» при округлении.
- Не меняй формат выходного Excel: его читает макрос бухгалтерии.
- Папку data/ не коммить: там выгрузки с данными клиентов.
```

Ты уже видел такой файл в действии: курс работает именно так. `CLAUDE.md` в папке курса превращает обычный Claude Code в преподавателя.

> **Почему так?** Файлы прозрачны: их можно прочитать, поправить, положить в git и обсудить с командой. «Скрытая» память внутри модели была бы непредсказуемой — ты не знал бы, что Claude «помнит» и почему. Цена — каждая строка CLAUDE.md занимает место в context window в каждой сессии.

## 2. Уровни памяти

Claude Code собирает memory из нескольких мест:

| Уровень | Файл | Для чего | В git? |
|---------|------|----------|--------|
| User (пользователь) | `~/.claude/CLAUDE.md` | личные предпочтения для **всех** проектов: язык, стиль ответов | нет, это твоя домашняя папка |
| Project (проект) | `./CLAUDE.md` или `./.claude/CLAUDE.md` | правила проекта для всей команды | да |
| Local (личное в проекте) | `./CLAUDE.local.md` | твои заметки по этому проекту: пути на твоём компьютере, личные эксперименты | нет — добавь в `.gitignore` |
| Rules | `./.claude/rules/*.md` | правила проекта, разбитые по темам; можно ограничить путями файлов | да |

`~` — домашняя папка: на Windows `C:\Users\<имя>`, на macOS `/Users/<имя>`.

Дополнительно Claude Code подгружает `CLAUDE.md` из **родительских папок** той, где ты запустил `claude`. Именно поэтому упражнения курса делаются в `~/claude-practice`, а не внутри папки курса: иначе CLAUDE.md учителя попал бы в твою практическую сессию.

Как распределять:

| Пример правила | Куда | Почему |
|----------------|------|--------|
| «Отвечай по-русски, коротко» | user | это про тебя, а не про проект |
| «Тесты: `python -m pytest`» | project | нужно всем, кто работает с проектом |
| «Мой тестовый файл данных — `D:\tmp\todo-test.json`» | local | путь есть только на твоём компьютере |
| «В тестах используй `tmp_path`» | rules с `paths: tests/**` | важно только при работе с тестами |

Если правила разных уровней противоречат друг другу, результат непредсказуем. Не полагайся на «кто главнее» — устраняй противоречия.

> **Почему так?** Разделение повторяет реальность: есть правила команды, есть твои привычки, есть твои локальные обстоятельства. Если смешать их в одном файле, коллеги получат твои личные пути, а ты — не сможешь держать свои предпочтения во всех проектах сразу.

## 3. `/init`: быстрый старт и его ограничения

Команда `/init` просит Claude изучить проект и сгенерировать `CLAUDE.md`: структуру, команды сборки и тестов, обнаруженные конвенции.

```text
/init
```

Это хорошая отправная точка, но не результат. Типичные проблемы сгенерированного файла:

- **Пересказ очевидного.** «`models.py` содержит класс Task» — Claude и так это увидит, открыв файл.
- **Нет «почему» и нет запретов.** Claude не знает, что `todos.json` — живые данные пользователя, а не тестовая фикстура. Это знаешь только ты.
- **Длина.** Каждая строка оплачивается context в каждой сессии.
- **Догадки.** Если чего-то в коде нет явно, Claude может предположить. Проверь каждую команду из файла — запусти её.

Подход: `/init` → прочитать → удалить очевидное → добавить то, что знаешь только ты → проверить команды → закоммитить.

> **Почему так?** Ценность CLAUDE.md — в знании, которого нет в коде: решения, договорённости, запреты, ловушки. Модель может извлечь из кода только то, что в нём уже есть, поэтому сгенерированный файл почти всегда нужно дополнить человеку.

## 4. Что писать в CLAUDE.md, а чего не писать

| Писать | Не писать |
|--------|-----------|
| Команды: запуск, тесты, линтер — точно, как их запускать | То, что видно из кода за секунду: список файлов, сигнатуры функций |
| Конвенции, которые не очевидны: язык сообщений, стиль коммитов | Общие советы «пиши чистый код», «будь внимателен» |
| Архитектурные решения **с причиной** | Секреты: пароли, токены, ключи API — никогда |
| Запреты и ловушки: «не трогай X, потому что Y» | Огромные тексты: спецификации, документацию API целиком |
| Как проверить работу: «после правок — `python -m pytest`» | Устаревшее: правила, которые уже не действуют |

### Краткость

Ориентир — десятки строк, а не сотни. Каждая строка:

1. Занимает tokens в **каждой** сессии, даже когда не нужна.
2. Конкурирует за внимание с остальными правилами. Чем длиннее файл, тем выше шанс, что важное правило «утонет».

Тест для каждой строки: «Если удалить её, Claude начнёт ошибаться?» Если нет — удаляй.

### Правило с причиной работает лучше

```markdown
# Плохо
- Не редактируй todos.json.

# Хорошо
- Не редактируй todos.json напрямую: это живые данные пользователя.
  Для экспериментов — TODO_FILE=test.json, в тестах — tmp_path.
```

Во втором варианте Claude понимает цель и правильно поступает в ситуации, которую правило явно не описывает (например, не станет «чистить» файл от тестовых задач).

### Формулируй позитивно и конкретно

Из модуля 03: «делай X» работает лучше, чем «не делай Y». «Используй `python -m pytest`» лучше, чем «не запускай pytest напрямую». Конкретные примеры лучше абстракций.

> **Почему так?** CLAUDE.md — это prompt, который ты пишешь один раз и используешь сотни раз. Все правила хорошего prompt из модулей 03–04 работают и здесь, а ошибки умножаются на число сессий.

## 5. Как проверить, что Claude следует CLAUDE.md

Что загружено в сессию:

- `/memory` — показывает файлы памяти, которые использует сессия, и позволяет открыть их для редактирования.
- `/context` — показывает, сколько места в context занимают разные части, включая memory files.

Но «загружено» не значит «соблюдается». Правило проверяют экспериментом — **A/B тестом**:

1. Выбери правило с наблюдаемым эффектом. Плохо: «пиши аккуратно». Хорошо: «сообщения коммитов — на русском, в повелительном наклонении», «в каждой новой функции — docstring на русском».
2. **A (без правила):** закомментируй или убери правило, начни новую сессию (или `/clear`), дай задачу.
3. **B (с правилом):** верни правило, новая сессия, **тот же** prompt.
4. Сравни результаты. Из-за недетерминированности (модуль 01) повтори каждый вариант 2–3 раза.

Важно: в prompt не должно быть подсказки о правиле. Если просишь «напиши функцию с docstring на русском», ты проверяешь prompt, а не CLAUDE.md.

После правки CLAUDE.md начинай новую сессию или делай `/clear`: memory читается в начале сессии.

> **Почему так?** Без сравнения ты не отличишь «Claude следует правилу» от «Claude и так бы так сделал». A/B тест — тот же принцип, что «тест сначала должен падать» из модуля 05: эффект виден только на контрасте.

## 6. Личная память: user-level и CLAUDE.local.md

`~/.claude/CLAUDE.md` подгружается во **всех** проектах. Хорошие кандидаты:

```markdown
# Мои предпочтения

- Отвечай на русском; технические термины оставляй на английском.
- Я не разработчик: перед командой, меняющей файлы, кратко объясни, что она сделает.
- Если задача неоднозначна — сначала задай 1–3 уточняющих вопроса.
- Предпочитаю короткие ответы: сначала вывод, потом детали.
```

Создать файл (папка `.claude` в домашней папке может ещё не существовать):

```powershell
# Windows PowerShell
New-Item -ItemType Directory -Force $HOME\.claude
notepad $HOME\.claude\CLAUDE.md
```

```bash
# macOS / Linux
mkdir -p ~/.claude
nano ~/.claude/CLAUDE.md      # или открой в своём редакторе
```

Можно и через `/memory` в сессии Claude Code — она предложит, какой файл открыть.

`CLAUDE.local.md` — для личного в конкретном проекте: «мои тестовые данные лежат в …», «сейчас я экспериментирую с …». Обязательно добавь его в `.gitignore`.

Чего **не** класть в user-level: правила конкретного проекта. Они «протекут» в другие проекты, где неуместны.

> **Почему так?** Личные предпочтения повторяются во всех проектах — логично написать их один раз. Но user-level файл ты не видишь в папке проекта, поэтому про него легко забыть: если Claude ведёт себя странно в новом проекте, первым делом проверь `/memory`.

## 7. Структура: `@imports` и `.claude/rules/`

Когда правил становится много, один файл трудно поддерживать.

### Imports

Внутри CLAUDE.md можно подключить другой файл через `@путь`:

```markdown
# todo-app
Краткое описание и главные правила...

Подробности о тестах: @docs/testing.md
```

Содержимое `docs/testing.md` загрузится вместе с CLAUDE.md. Удобно, когда документ уже существует для людей (например, `docs/testing.md` читают и коллеги), — Claude получает ту же версию, без дублирования.

### Rules

Папка `.claude/rules/` — набор тематических файлов. У каждого можно указать во frontmatter (блок настроек между `---` в начале файла) поле `paths:` — тогда правило будет относиться только к работе с подходящими файлами:

```markdown
---
paths:
  - "tests/**/*.py"
---
# Правила для тестов
- Каждый тест использует временный файл данных (tmp_path + TODO_FILE), не todos.json.
- Имя теста описывает поведение: test_list_hides_done_tasks_by_default.
```

Rules без `paths:` действуют всегда, как обычный CLAUDE.md. Точное поведение загрузки может меняться — проверь `/memory` и https://code.claude.com/docs.

| Способ | Когда |
|--------|-------|
| Один CLAUDE.md | маленький проект, до нескольких десятков строк |
| `@imports` | есть готовые документы для людей, которые нужны и Claude |
| `.claude/rules/` с `paths:` | правила касаются только части проекта (тесты, фронтенд, миграции) |

> **Почему так?** Rules с `paths:` экономят context: правила для тестов не нужны, когда ты правишь README. Imports убирают дублирование: одна правда для людей и для Claude. Но не дроби без нужды — пять файлов по три строки сложнее поддерживать, чем один на пятнадцать.

## 8. Auto memory и что дальше

В новых версиях Claude Code есть **auto memory** — Claude может сам сохранять заметки о проекте и твоих предпочтениях между сессиями. Детали (где хранятся заметки, как включить или выключить) зависят от версии: смотри `/memory` и https://code.claude.com/docs.

Отношение к auto memory — как к черновику: периодически просматривай, что там накопилось, и переноси важное в CLAUDE.md, где правило явное, проверяемое и общее для команды.

Для сравнения: в claude.ai похожую роль играют Projects (инструкции и файлы проекта) и memory чата — идея та же: постоянный контекст, который не нужно повторять.

Хороший CLAUDE.md — живой документ. Повод его обновить:

- ты второй раз поправил Claude в одном и том же → это правило;
- правило ни разу не пригодилось за месяц → кандидат на удаление;
- в проекте поменялись команды → обнови сразу, устаревшее правило хуже отсутствующего.

> **Почему так?** Auto memory удобна, но непрозрачна для команды и может запомнить случайное. Явный CLAUDE.md в git — договорённость, которую видят все и которую можно проверить A/B тестом.

→ **Упражнение 6** ⭐ (см. exercises.md)

## Шпаргалка

| Что | Как |
|-----|-----|
| Сгенерировать CLAUDE.md | `/init`, затем отредактировать руками |
| Посмотреть/открыть memory files | `/memory` |
| Сколько memory занимает в context | `/context` |
| Личные предпочтения для всех проектов | `~/.claude/CLAUDE.md` |
| Правила проекта для команды | `./CLAUDE.md` или `./.claude/CLAUDE.md` (в git) |
| Личное в проекте | `./CLAUDE.local.md` + строка в `.gitignore` |
| Правила для части файлов | `.claude/rules/<тема>.md` с `paths:` во frontmatter |
| Подключить документ | `@docs/testing.md` внутри CLAUDE.md |
| Применить изменения | новая сессия или `/clear` |
| Проверить правило | A/B: без правила vs с правилом, тот же prompt, 2–3 повтора |

Мини-шаблон project CLAUDE.md:

```markdown
# <проект> — одна строка, что это

## Команды
- Запуск: ...
- Тесты: ...

## Правила (с причинами)
- ...

## Не делай
- ... — потому что ...
```

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| memory | файлы, которые Claude Code автоматически добавляет в context каждой сессии |
| CLAUDE.md | основной memory file проекта или пользователя |
| user memory | `~/.claude/CLAUDE.md`, действует во всех проектах |
| project memory | `CLAUDE.md` в корне проекта, общий для команды |
| `CLAUDE.local.md` | личная memory в проекте, не коммитится |
| rules | тематические файлы в `.claude/rules/`, можно ограничить `paths:` |
| frontmatter | блок настроек в начале Markdown-файла между `---` |
| import (`@путь`) | подключение другого файла в CLAUDE.md |
| `/init` | генерация стартового CLAUDE.md по коду проекта |
| auto memory | заметки, которые Claude сохраняет сам между сессиями |
| A/B тест | сравнение поведения с правилом и без при одинаковом prompt |

## Вопросы для самопроверки

1. Почему CLAUDE.md надо держать коротким, если context window большой?
2. Ты хочешь, чтобы Claude всегда отвечал по-русски во всех проектах. Какой файл? А правило «тесты запускать через `python -m pytest`» в todo-app?
3. Чем полезна причина («…потому что…») в правиле CLAUDE.md?
4. Почему `/init` не заменяет ручную работу над CLAUDE.md?
5. Как убедиться, что Claude следует конкретному правилу, а не делает так «случайно»?
6. Ты поправил CLAUDE.md, а Claude продолжает вести себя по-старому. Что проверишь в первую очередь?
7. Что нельзя класть в CLAUDE.md ни при каких условиях и почему?
8. Когда стоит вынести правила в `.claude/rules/` с `paths:`, а когда достаточно одного файла?
