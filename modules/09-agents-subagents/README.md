## 1. Что такое agent

В модуле 01 мы говорили, что LLM (large language model — большая языковая модель) умеет одно: по тексту предсказывать продолжение. Сама по себе модель не может открыть файл, запустить тест или заглянуть в интернет. Она только пишет текст.

**Agent** (агент) — это модель плюс две вещи:

1. **Tools** (инструменты) — функции, которые программа вокруг модели умеет выполнять: прочитать файл, найти текст, запустить команду, отредактировать файл.
2. **Цикл** — программа раз за разом спрашивает модель «что дальше?», выполняет то, что модель попросила, и показывает ей результат.

Этот цикл называют **agent loop**:

```
        ┌─────────────────────────────────────────────┐
        ▼                                             │
  [1. Думать] → нужен tool? ──да──► [2. Вызвать tool] │
        │                              │              │
        нет                            ▼              │
        │                     [3. Увидеть результат] ─┘
        ▼
  [4. Ответить пользователю]
```

Пример из жизни. Ты просишь Claude Code: «Почему `python todo.py list` показывает выполненные задачи?» Внутри происходит примерно так:

| Шаг | Мысль модели | Tool | Результат |
|-----|--------------|------|-----------|
| 1 | Надо понять структуру проекта | `Glob` (поиск файлов по шаблону) | `todo.py`, `models.py`, `storage.py`, … |
| 2 | Команда `list` — в `todo.py` | `Read todo.py` | текст файла |
| 3 | Вижу функцию вывода, фильтр по `done` странный | `Grep "done"` | 4 совпадения |
| 4 | Проверю на практике | `Bash python todo.py list` | в выводе есть `[x]` задачи |
| 5 | Причина найдена | — | ответ тебе |

Модель **не знала заранее**, сколько шагов понадобится. Каждый следующий шаг она выбирает, глядя на результат предыдущего. В этом отличие agent от простого чата: в чате ты сам копируешь файл и вставляешь ошибку; agent делает это сам.

> **Почему так?** Задачи в реальном мире редко решаются «за один ход»: нужно сначала посмотреть, потом попробовать, потом проверить. Цикл позволяет модели собирать недостающую информацию и исправлять себя по ходу — как человек, который не пишет отчёт вслепую, а сначала открывает данные. Цена — каждый шаг стоит tokens и времени, поэтому длинные циклы дороже.

**Claude Code — это agent.** Всё, что ты видел в прошлых модулях — чтение файлов, предложения правок, запуск `pytest`, — шаги одного agent loop. Запросы разрешения (permission prompts) — это момент, когда цикл останавливается перед шагом 2 и ждёт твоего «да».

## 2. Tool use под капотом

Как модель «вызывает» tool, если она умеет только писать текст? Через **tool use** (вызов инструментов) — специальный формат API:

1. Программа отправляет модели сообщения **и список tools** — у каждого есть `name`, `description` и схема параметров (`input_schema`). Кода функции модель не видит — только описание.
2. Если модель решает, что нужен tool, она отвечает не текстом, а блоком «хочу вызвать `read_file` с `path="todo.py"`». Признак — `stop_reason == "tool_use"`.
3. Программа **сама** выполняет функцию и отправляет результат обратно как блок `tool_result`.
4. Модель получает всю историю + результат и решает, что дальше. Когда задача решена, она отвечает обычным текстом — цикл заканчивается.

Минимальный цикл на Python (упрощённо, полный пример — `practice/agent-loop/agent.py`):

```python
messages = [{"role": "user", "content": task}]
while True:
    response = client.messages.create(model=MODEL, max_tokens=1024,
                                      tools=TOOLS, messages=messages)
    if response.stop_reason != "tool_use":
        print(response.content[0].text)   # модель закончила
        break
    messages.append({"role": "assistant", "content": response.content})
    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = run_tool(block.name, block.input)     # выполняем МЫ, не модель
            results.append({"type": "tool_result",
                            "tool_use_id": block.id, "content": output})
    messages.append({"role": "user", "content": results})
```

Три вывода, которые пригодятся дальше:

- **Описание tool — это prompt.** Модель выбирает tool по `description`. Плохое описание → tool не вызывается или вызывается не к месту. Это то же самое, что `description` у skills (модуль 07) и docstring у MCP tools (модуль 08).
- **История растёт.** Каждый результат tool (например, весь текст прочитанного файла) остаётся в `messages`. Это и есть context window агента — и он заполняется быстро.
- **Выполняет программа, а не модель.** Значит, именно программа решает, что разрешено. В Claude Code эту роль играют permissions и hooks (модуль 10).

> **Почему так?** Разделение «модель просит — программа выполняет» — главный механизм безопасности агентов. Модель может ошибиться или поддаться обманному тексту в файле, но реальное действие происходит только через код, который можно ограничить, залогировать или поставить на подтверждение.

> Писать свой agent loop **не обязательно** для курса: для этого нужен API key и платный API. Но если хочешь увидеть механику своими глазами — сделай упражнение ⭐ в конце модуля. → **Упражнение 6** (необязательное, можно сделать в конце)

## 3. Subagents: зачем они нужны

**Subagent** (субагент, «помощник») — отдельный экземпляр agent, которого основная сессия Claude Code запускает для конкретной подзадачи. У subagent:

- **свой, чистый context window** — он не видит вашу длинную переписку, только задание от основной сессии;
- **свой system prompt** (системная инструкция — «должностная инструкция» агента);
- **свой набор tools** — можно ограничить, например, только чтением;
- **своя модель** — можно выбрать быструю и дешёвую для простых задач.

Когда subagent закончил, основная сессия получает **только его итоговый ответ**, а не всё, что он прочитал по дороге.

Аналогия из офиса: ты руководитель проекта. Можно самому перечитать 40 договоров, чтобы найти пункт о штрафах, — и потом весь день держать их в голове. А можно поручить юристу: он прочитает всё и принесёт одну страницу выводов. Твоя «голова» (context) осталась свободной для главного.

Три причины использовать subagents:

| Причина | Что даёт | Пример |
|---------|----------|--------|
| **Изоляция контекста** | основная сессия не засоряется «сырыми» данными | поиск по 50 файлам → возвращается 10 строк выводов |
| **Специализация** | узкая инструкция и инструменты → стабильнее результат | ревьюер, который *не может* править код, только комментировать |
| **Параллельность** | несколько независимых задач одновременно | три Explore изучают три разные части проекта сразу |

> **Почему так?** В модуле 04 ты видел, что длинная сессия деградирует: чем больше в context лишнего, тем хуже модель следует инструкциям и тем дороже каждый шаг. Subagent — способ сделать «грязную» работу (много чтения, много попыток) в отдельной комнате и вынести оттуда только результат. Компромисс: subagent не знает того, что обсуждалось в основной сессии, — всё нужное придётся передать в задании явно.

Обрати внимание на компромисс: **subagent стоит дороже**, чем сделать то же самое в основной сессии, если задача маленькая. Он заново читает файлы, которые основная сессия, возможно, уже видела, и тратит tokens на собственный старт. Выигрыш появляется, когда «сырого» материала много, а итог короткий.

## 4. Встроенные subagents

В Claude Code уже есть несколько subagents. Их не нужно создавать — основная сессия может вызвать их сама или по твоей просьбе.

| Subagent | Для чего | Особенность |
|----------|----------|-------------|
| **Explore** | быстро изучить код: найти файлы, понять, где что лежит | работает только на чтение, ничего не меняет |
| **Plan** | собрать информацию для плана (используется в plan mode) | исследует проект, пока основная сессия составляет план |
| **general-purpose** | многошаговые задачи, где нужно и искать, и действовать | универсальный, с широким набором tools |

Как увидеть их в работе: попроси явно.

```
Используй subagent Explore, чтобы выяснить, как в этом проекте устроено
хранение задач (какой файл, какой формат, где задаётся путь).
Верни краткую сводку: 5–7 пунктов со ссылками на файлы и функции.
```

В интерфейсе ты увидишь, что запущен subagent, и сколько tool-вызовов он сделал. В основной сессии останется только его сводка.

Параллельный запуск:

```
Запусти параллельно три Explore subagents:
1) как устроен CLI (todo.py), 2) как устроено хранение (storage.py),
3) что покрыто тестами (tests/). Каждый — сводка до 5 пунктов.
Потом объедини в одну схему проекта.
```

> **Почему так?** Explore ограничен чтением, потому что разведка не должна иметь побочных эффектов: ты просишь «посмотри», а не «поменяй». Это же делает его безопасным для параллельного запуска — три читателя не помешают друг другу, а три редактора одного файла — помешали бы.

Набор и поведение встроенных subagents может меняться между версиями — актуальный список смотри в `/agents` и в https://code.claude.com/docs.

## 5. Свои subagents

Свой subagent — это **один Markdown-файл** с frontmatter (служебный заголовок между `---`) и телом.

Где лежат:

| Путь | Кому доступен | Когда использовать |
|------|---------------|--------------------|
| `.claude/agents/<name>.md` | этому проекту (можно положить в git для команды) | агент знает специфику проекта |
| `~/.claude/agents/<name>.md` | тебе во всех проектах | универсальный помощник, например «редактор текстов» |

Пример — ревьюер кода, который **не может** ничего менять:

```markdown
---
name: code-reviewer
description: Ревью изменений в Python-коде. Используй после любых правок кода, перед коммитом, или когда пользователь просит "проверь код", "сделай ревью".
tools: Read, Grep, Glob
model: sonnet
---

Ты — внимательный ревьюер Python-кода в небольшом CLI-проекте.

Задача: найти проблемы в указанных файлах или изменениях и объяснить их.

Проверяй по порядку:
1. Корректность: логические ошибки, граничные случаи (пустой список, неверный id).
2. Данные: не может ли изменение повредить todos.json.
3. Читаемость: имена, длина функций, docstrings.
4. Тесты: есть ли тест на изменённое поведение.

Формат ответа:
- Таблица: файл:строка | серьёзность (критично / важно / мелочь) | проблема | почему это плохо | как исправить.
- В конце — вердикт: «можно коммитить» или «нужно исправить».

Ты не правишь файлы — только читаешь и комментируешь.
Если не уверен, что это ошибка, пометь «под вопросом» и объясни, что проверить.
```

Поля frontmatter:

| Поле | Что значит | Совет |
|------|-----------|-------|
| `name` | имя агента (латиница, через дефис) | совпадает с именем файла |
| `description` | **когда** использовать агента | по нему основная сессия решает, звать ли агента сама — как у skills |
| `tools` | список tools через запятую | давай минимум, нужный для роли. Если поле не указать, агент обычно получает все инструменты основной сессии — проверь в `/agents` |
| `model` | `sonnet`, `opus`, `haiku` или `inherit` (как в основной сессии) | `haiku` — для быстрых простых задач, `opus` — для сложного анализа |

Тело файла — это **system prompt** агента: роль, порядок работы, формат ответа, границы.

> **Почему так?** Ограничение `tools` — не формальность, а гарантия. Если в ревьюере написать «не правь файлы», модель *скорее всего* послушается. Если не дать ему `Edit` и `Write`, он *не сможет* править физически. Правило в prompt — просьба; ограничение tools — замок. Для ролей, где ошибка дорога, выбирай замок.

### Как создать

- **Руками:** создай файл `.claude/agents/code-reviewer.md` (можно попросить Claude создать по твоему описанию).
- **Через меню:** команда `/agents` открывает менеджер, где можно посмотреть, создать, отредактировать агентов и выбрать им tools.

Если агент создан файлом во время сессии и не появился в `/agents` — перезапусти Claude Code (`claude -c`, чтобы продолжить ту же сессию).

### Как вызвать

1. **Явно** — лучший способ, пока учишься:
   ```
   Используй subagent code-reviewer, чтобы проверить изменения в todo.py.
   ```
2. **Автоматически** — основная сессия сама решит позвать агента, если задача совпадает с его `description`. Поэтому в `description` пишут не «что это», а «когда звать»: «Используй после правок кода…».

> **Почему так?** Механика та же, что у skills: в context основной сессии всегда лежат только короткие `description` всех агентов, а полный system prompt нужен только самому агенту при запуске. Чем точнее `description`, тем реже агента зовут не к месту и тем реже забывают позвать.

→ **Упражнение 3** (см. exercises.md)

### Агент, который действует

Ревьюер только читает. Агенту, который пишет тесты, нужно больше: создавать файлы и запускать `pytest`.

```markdown
---
name: test-writer
description: Пишет pytest-тесты для todo-app. Используй, когда нужно покрыть тестами новую или изменённую функцию.
tools: Read, Grep, Glob, Write, Edit, Bash
model: sonnet
---
Ты пишешь тесты, но НЕ меняешь код приложения (todo.py, models.py, storage.py).
...
```

Здесь ограничение «не трогай код приложения» уже нельзя выразить через `tools` (Edit нужен для тестов), поэтому оно в prompt. Вывод: где замок невозможен — пишем чёткую просьбу, а результат проверяем (diff, `git status`). В модуле 10 увидишь, как hooks превращают такую просьбу в замок.

## 6. Как писать system prompt для subagent

Хороший system prompt агента похож на хорошее поручение новому сотруднику (модуль 03), но с одной особенностью: **агент не видит вашей переписки**. Он знает только свой prompt и текст задания.

Структура, которая работает:

1. **Роль и контекст** — кто ты, в каком проекте. «Ты пишешь тесты для CLI-приложения задач на Python».
2. **Цель** — какой результат считать успехом.
3. **Порядок работы** — шаги. «Сначала прочитай код, потом существующие тесты, потом пиши».
4. **Границы** — что нельзя. «Не меняй код приложения. Не трогай todos.json».
5. **Формат ответа** — что вернуть основной сессии. Это важно: ответ агента — всё, что останется в основном context.
6. **Что делать при неопределённости** — «если поведение неясно, опиши вопрос, а не угадывай».

Частая ошибка — агент возвращает «простыню»: весь код, все логи. Тогда изоляция context теряет смысл. Проси короткий, структурированный итог: «до 15 строк», «таблица», «список файлов, которые изменил».

> **Почему так?** Ответ subagent целиком попадает в context основной сессии. Если он длиннее, чем то, что агент прочитал, — делегировать было бессмысленно. Формат ответа — это «интерфейс» между агентами, как формат отчёта между отделами.

## 7. Паттерны: цепочки агентов

Типичная цепочка для изменения кода повторяет работу команды разработчиков:

```
researcher  →  planner  →  implementer  →  reviewer
(Explore)      (Plan /       (основная      (code-reviewer)
               plan mode)    сессия)
   │              │             │                │
 «что есть»    «что делать»  «сделать»     «проверить»
```

Кто передаёт результат от одного агента другому? **Основная сессия.** Она — «менеджер»: вызывает первого агента, читает его вывод, формулирует задание второму. Ты можешь попросить это одним сообщением:

```
Задача: добавить команду `search <текст>` в todo-app.
1. Используй Explore, чтобы понять, как устроены команды CLI.
2. Составь план и покажи мне перед реализацией.
3. После моего ОК реализуй.
4. Используй test-writer, чтобы покрыть новую команду тестами.
5. Используй code-reviewer для ревью всех изменений.
6. Исправь замечания с серьёзностью «критично» и «важно».
```

**Передача через файлы.** Если результат этапа большой (план на 2 страницы), удобнее, чтобы агент записал его в файл (`plan.md`), а следующему агенту сказать «прочитай plan.md». Файл переживёт `/clear`, его можно открыть и поправить руками.

> **Почему так?** Разделение ролей даёт «вторую пару глаз»: ревьюер со свежим context не «влюблён» в решение, которое только что написал исполнитель, и замечает то, что пропустила основная сессия. Пауза «покажи план» оставляет за тобой ключевое решение до того, как потрачено время на реализацию. Альтернатива — один агент делает всё — быстрее для мелочей, но хуже ловит собственные ошибки.

## 8. Когда агенты НЕ нужны

Subagents — инструмент, а не цель. Не используй их, когда:

- **Задача маленькая.** «Переименуй переменную в одном файле» — основная сессия сделает это за 2 шага. Subagent потратит больше на старт, чем на работу.
- **Нужен весь контекст разговора.** Если вы 20 минут обсуждали тонкости требований, subagent их не знает. Пересказывать дороже, чем сделать самому.
- **Важна скорость реакции.** Цепочка из 4 агентов — это минуты. Для быстрых правок это лишнее.
- **Бюджет ограничен.** Каждый агент — отдельные tokens. Параллельные агенты расходуют лимит подписки или деньги API быстрее.
- **Ты не знаешь, что хочешь.** Агенты усиливают ясное поручение. Неясное поручение они размножат в N неясных результатов. Сначала уточни задачу (модуль 04).

Простое правило: **сначала попробуй в основной сессии**. Если видишь, что context забивается сырыми данными или нужна независимая проверка — тогда выноси в subagent.

> **Почему так?** Каждый уровень автоматизации добавляет стоимость (tokens, время) и сложность (больше мест, где что-то пошло не так). Окупается это только на повторяющихся или объёмных задачах. Это тот же принцип, что «не пиши skill для задачи, которую делаешь раз в год».

## 9. Subagent, skill, CLAUDE.md, MCP — что выбрать

К этому модулю у тебя четыре механизма. Их легко перепутать.

| Механизм | Что это | Где работает | Когда выбирать |
|----------|---------|--------------|----------------|
| `CLAUDE.md` | постоянные правила проекта | всегда в context основной сессии | факты и правила, нужные почти в каждой задаче |
| **Skill** | инструкция/процесс, загружается по требованию | **в той же** сессии, в общем context | повторяемый процесс: «как писать commit message» |
| **Subagent** | отдельный исполнитель со своим context и tools | **в отдельном** context, возвращает итог | объёмная работа или независимая роль (ревью, разведка) |
| **MCP server** | новые tools и данные извне | подключается к сессии (и к агентам) | нужен доступ к системе, которой нет в Claude Code |

Пример выбора для задачи «проверять код перед коммитом»:
- Правило «перед коммитом запускай pytest» → `CLAUDE.md` (коротко, нужно всегда).
- Чек-лист ревью → можно skill, но если ревью длинное и ты хочешь «свежий взгляд» — subagent.
- Доступ к задачам в трекере команды → MCP server.

> **Почему так?** Ключевое различие skill и subagent — **чей context**. Skill добавляет знания в текущий разговор (быстро, но context растёт). Subagent работает в стороне (чище, но не знает разговора и стоит отдельного старта). Это выбор между «научить себя» и «поручить другому».

## Шпаргалка

| Что | Как |
|-----|-----|
| Agent loop | думать → tool → результат → повторить, пока не готово |
| Признак вызова tool в API | `stop_reason == "tool_use"` → выполнить → вернуть `tool_result` |
| Встроенные subagents | Explore (чтение кода), Plan (исследование для плана), general-purpose |
| Свой агент (проект) | `.claude/agents/<name>.md` |
| Свой агент (личный) | `~/.claude/agents/<name>.md` |
| Frontmatter | `name`, `description`, `tools: Read, Grep, Glob`, `model: sonnet\|opus\|haiku\|inherit` |
| Управление агентами | `/agents` |
| Вызов явно | «Используй subagent code-reviewer, чтобы…» |
| Параллельно | «Запусти параллельно три Explore subagents: …» |
| Read-only агент | `tools: Read, Grep, Glob` |
| Цепочка | Explore → план (plan mode) → реализация → test-writer → code-reviewer |
| Передача между этапами | через основную сессию или файл (`plan.md`) |
| Не нужен агент | маленькая задача, нужен контекст разговора, важна скорость/бюджет |

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| agent | LLM + tools + цикл, в котором модель сама выбирает следующий шаг по результатам предыдущего |
| agent loop | цикл «думать → вызвать tool → увидеть результат → повторить» |
| tool use | формат API, в котором модель просит вызвать инструмент, а программа выполняет и возвращает результат |
| `stop_reason` | поле ответа API: почему модель остановилась (`tool_use` — просит tool, иначе — закончила) |
| `tool_result` | блок с результатом выполнения tool, который программа отправляет модели |
| subagent | отдельный экземпляр agent со своим context, system prompt, tools и моделью |
| system prompt | системная инструкция, задающая роль и правила агента; у subagent — тело его `.md` файла |
| Explore | встроенный subagent для чтения и изучения кода |
| Plan | встроенный subagent для сбора информации при планировании |
| general-purpose | встроенный универсальный subagent для многошаговых задач |
| оркестрация | управление цепочкой агентов: кто кого вызывает и что передаёт; в Claude Code это делает основная сессия |
| изоляция контекста | работа в отдельном context, из которого в основной возвращается только итог |

## Вопросы для самопроверки

1. Чем agent отличается от «просто LLM» в чате? Назови три составные части.
2. Кто на самом деле выполняет tool — модель или программа вокруг неё? Почему это важно для безопасности?
3. Что попадает в context основной сессии после работы subagent, а что — нет?
4. Почему ограничение `tools` надёжнее, чем фраза «не редактируй файлы» в system prompt?
5. Зачем писать в `description` агента «когда использовать», а не «что это за агент»?
6. Приведи две ситуации, когда subagent хуже, чем сделать задачу в основной сессии.
7. В цепочке researcher → planner → implementer → reviewer: кто передаёт результаты между этапами и какие есть способы передачи?
8. Чем subagent отличается от skill, если оба можно описать Markdown-файлом?
