# Модуль 03. Prompt engineering: основы

> **Зачем:** качество ответа Claude на 80% определяется тем, как поставлена задача. В этом модуле ты научишься писать prompts, которые с первого раза дают нужный результат: понятная цель, контекст, структура, примеры, формат. **Время:** ~3–4 ч. **Нужно:** модули 01–02; Claude Code установлен; папка `~/claude-practice`.

## Что ты будешь уметь

- формулировать задачу так, чтобы её понял «новый коллега без контекста»;
- задавать аудиторию, цель, ограничения и формат ответа;
- разделять инструкции и данные с помощью XML-тегов;
- использовать few-shot examples для стабильной классификации и извлечения данных;
- просить Claude рассуждать перед ответом и честно говорить «не знаю»;
- собирать переиспользуемый шаблон prompt для своей рабочей задачи.

## 1. Ясность и прямота: правило нового коллеги

**Prompt** (запрос к модели) — это постановка задачи. Лучший тест для prompt:

> Покажи его умному новому коллеге, который ничего не знает о твоём проекте. Поймёт ли он, что сделать, для кого и как будет выглядеть хороший результат?

Claude — как раз такой коллега: очень способный, но без контекста. Он не знает, что «отчёт» — это квартальный отчёт для директора, что «как в прошлый раз» — это таблица, что «покороче» — это полстраницы.

Сравни:

```text
Плохо:  Напиши письмо клиенту про задержку.
```

```text
Лучше:  Напиши письмо клиенту о задержке поставки 4 МФУ.
        Клиент: логистическая компания, работаем с ней 3 года.
        Причина: поставщик сдвинул отгрузку, новая дата — 15 октября (на неделю позже).
        Цель письма: сохранить доверие; предложить бесплатную доставку как компенсацию.
        Тон: деловой, тёплый, без канцелярита. Длина: до 120 слов. Подпись: Павел, менеджер.
```

Во второй версии нет никакой «магии» — только факты, которые были у автора в голове, но не попали в первую.

Признаки неясного prompt:
- оценочные слова без расшифровки: «получше», «покрасивее», «профессионально», «кратко»;
- ссылки на то, чего Claude не видел: «как обычно», «по нашему шаблону», «тот файл»;
- несколько задач в одной фразе без приоритетов.

> **Почему так?** Модель предсказывает продолжение по тексту перед ней (модуль 01). Всё, чего нет в тексте, она заполняет «средним» правдоподобным вариантом. Средний вариант редко совпадает с тем, что нужно именно тебе. Чем меньше модели приходится угадывать, тем меньше разброс и ошибок.

## 2. Контекст: аудитория, цель, ограничения

Хороший prompt почти всегда отвечает на четыре вопроса:

| Вопрос | Пример |
|--------|--------|
| **Что** сделать? | составить резюме отчёта |
| **Для кого** результат? | генеральный директор, 5 минут на чтение, финансист по образованию |
| **Зачем** — что будет дальше с результатом? | на встрече он решит, нанимать ли людей в поддержку |
| **Какие ограничения?** | не больше 1 страницы; только цифры из отчёта; на русском |

Особенно недооценено «**зачем**». Сравни два prompt к одному отчёту:

```text
Сделай резюме отчёта.
```

```text
Сделай резюме отчёта для генерального директора. На встрече в пятницу он решает,
выделять ли бюджет на 2 новых сотрудников поддержки. Покажи цифры, которые важны
для этого решения, и риски, если ничего не делать.
```

Первый даст пересказ всего подряд. Второй — отберёт нужное: время ответа поддержки, отток, жалобы клиентов.

Объясняй и **причины** правил. «Не используй сокращения» — хуже, чем «не используй сокращения: текст будет зачитан голосовым ассистентом, и он их не произнесёт». Зная причину, Claude правильно поступит и в случаях, которые ты не предусмотрел.

> **Почему так?** Контекст — это критерий отбора. Из отчёта можно сделать десяток «правильных» резюме; цель и аудитория говорят, какое из них нужно тебе. А объяснение причин даёт модели не просто правило, а понимание — и она обобщает его на новые ситуации.

## 3. Формат вывода

Говори, **как должен выглядеть** результат: структура, длина, язык, стиль.

| Хочешь | Скажи явно |
|--------|-----------|
| таблицу | «Таблица Markdown с колонками: Задача, Ответственный, Срок» |
| данные для Excel | «CSV с разделителем `;`, первая строка — заголовки, без пояснений до и после» |
| данные для программы | «Только JSON по схеме: `{"category": "...", "urgent": true/false}`» |
| короткий ответ | «Ответь одним словом из списка: …» / «Не больше 3 предложений» |
| текст определённого стиля | «Деловой стиль, без канцелярита, короткие абзацы, без списков» |

Приёмы:

- **Покажи шаблон** результата — это надёжнее описания словами:
  ```text
  Ответ дай в формате:
  ## Итог
  <1–2 предложения>
  ## Цифры
  - <показатель>: <было> → <стало>
  ## Что предлагаю
  <1 абзац>
  ```
- **Попроси сохранить в файл** (в Claude Code): «Запиши результат в `summary.md`». Тогда результат — артефакт, который можно открыть, проверить и переиспользовать, а не текст, потерянный в чате.
- **Стиль prompt влияет на стиль ответа.** Prompt, написанный сплошными маркированными списками, чаще получает ответ списками. Хочешь связный текст — пиши prompt связным текстом.

> **Почему так?** Формат — тоже часть «правильного ответа». Таблицу из чата не вставить в Excel, если в ней лишние пояснения; JSON не прочитает программа, если перед ним «Конечно! Вот ваш JSON:». Явный формат экономит время на переделку и делает результат пригодным для следующего шага.

## 4. XML-теги: отделяем инструкции от данных

Когда в prompt есть и **инструкции**, и **данные** (письмо, заметки, таблица), их легко перепутать — особенно если данные сами содержат что-то похожее на инструкции («сделайте до пятницы!»). Решение — обернуть части prompt в **XML-теги** (метки вида `<имя>…</имя>`):

```text
Извлеки из заметок встречи все задачи.

<instructions>
- Для каждой задачи укажи: что сделать, кто отвечает, срок.
- Если срок или ответственный не названы явно — напиши «не указан».
- Если срок менялся по ходу встречи — укажи последний вариант и отметь изменение.
</instructions>

<notes>
планерка 1.10 (чт) — сайт + поддержка
были: Ольга, Тимур, Света...
</notes>

Результат — таблица Markdown с колонками: Задача | Ответственный | Срок | Комментарий.
```

Правила:
- Названия тегов — любые понятные: `<notes>`, `<email>`, `<report>`, `<example>`, `<rules>`. Специальных «волшебных» тегов нет.
- Используй одни и те же названия последовательно и **ссылайся на них** в инструкциях: «по тексту в `<report>`».
- Несколько документов — каждый в свой тег: `<document name="report.md">…</document>`.
- Можно просить ответ тоже в тегах: «Рассуждения — в `<thinking>`, итог — в `<answer>`» — так удобно отделить итог.

В Claude Code для файлов есть альтернатива: `@meeting-notes.txt` подставит содержимое файла, и Claude будет знать, где начинаются и заканчиваются данные. Теги всё равно полезны, когда ты вставляешь текст прямо в сообщение.

> **Почему так?** Модель видит prompt как один поток текста. Теги создают однозначные границы: вот задача, вот данные, вот примеры. Это снижает риск, что Claude примет фразу из письма клиента за твою инструкцию (позже, в модуле 10, ты узнаешь, что это ещё и вопрос безопасности — prompt injection).

## 5. Few-shot examples: покажи, а не рассказывай

**Few-shot examples** (несколько примеров) — 2–5 образцов «вход → правильный выход» в prompt. Это самый надёжный способ добиться стабильного формата и правильных решений в пограничных случаях.

```text
Классифицируй письмо клиента. Категории: billing, sales, tech, complaint, cancel, feedback.
Ответ — одна строка: <категория> | <срочность: high/normal> | <суть в 5–8 словах>

<examples>
<example>
<email>Счёт выставлен на 15 пачек бумаги, а привезли 12. Исправьте счёт.</email>
<answer>billing | normal | расхождение количества в счёте и поставке</answer>
</example>
<example>
<email>Третью неделю не можем дождаться инженера, если так дальше — уйдём к другим.</email>
<answer>complaint | high | долгое ожидание инженера, угроза ухода</answer>
</example>
<example>
<email>Сканер МФУ сохраняет файлы пустыми, печать работает.</email>
<answer>tech | normal | сканер сохраняет пустые файлы</answer>
</example>
</examples>

<email>{{текст письма}}</email>
```

Как выбирать примеры:
- **разнообразные** — разные категории, разная длина, разный стиль писем;
- **пограничные** — примеры на трудные случаи, где категорию легко перепутать (во втором примере жалоба на сервис с угрозой ухода — `complaint`, а не `tech`);
- **одинаковые по формату ответа** — модель скопирует формат точно;
- **не слишком похожие на реальные данные** — иначе модель может «подгонять» ответ под пример.

Few-shot особенно полезен для: классификации, извлечения данных, единого стиля (например, тексты карточек товаров), перевода терминов «как у нас принято».

> **Почему так?** Описать словами границу между «жалобой» и «технической проблемой» трудно, а показать на двух примерах — легко. Модель отлично улавливает закономерности из примеров: это прямое следствие того, что она обучена продолжать тексты по образцу. Цена — примеры занимают tokens и могут «перетянуть» модель к своему частному стилю, поэтому их подбирают разнообразными.

## 6. Роль: когда помогает, а когда нет

**Role prompting** (задание роли) — фраза вида «Ты — опытный финансовый аналитик» в начале prompt. В API роль обычно задают в **system prompt** — отдельной служебной инструкции перед диалогом. В claude.ai и Claude Code ты пишешь роль прямо в сообщении (а постоянные инструкции в Claude Code живут в `CLAUDE.md` — модуль 06).

Роль **помогает**, когда задаёт полезную точку зрения и стандарты:
- «Ты — редактор деловых текстов. Твоя задача — сократить письмо, сохранив все факты» → понятно, *что* считать хорошей работой;
- «Ты — юрист, который проверяет договор со стороны покупателя» → понятно, *с какой стороны* смотреть.

Роль **не помогает**, когда она — просто комплимент:
- «Ты — лучший в мире эксперт с 30-летним опытом» не добавляет знаний, которых у модели нет, и не заменяет цель, контекст и формат.

Хорошая роль = **позиция + аудитория + стандарт качества**:

```text
Ты — аналитик продаж, который готовит материалы для еженедельной встречи
с менеджерами. Менеджеры не любят длинные отчёты: им нужны 3–4 вывода
с цифрами и один вопрос для обсуждения.
```

> **Почему так?** Роль сдвигает модель к определённому стилю, словарю и приоритетам — это полезно, если сдвиг в нужную сторону. Но модель от роли не становится умнее: она всё так же не знает твоих данных и целей. Поэтому роль — дополнение к контексту, а не замена ему.

## 7. Говори, что делать, а не только чего не делать

Prompt из одних запретов («не пиши длинно, не будь формальным, не используй списки») оставляет модель гадать, что же *нужно*. Переформулируй запреты в позитивные инструкции:

| Вместо | Лучше |
|--------|-------|
| Не пиши длинно | Не больше 5 предложений |
| Не будь формальным | Пиши как коллеге, с которым давно работаешь: на «вы», но без канцелярита |
| Не используй списки | Пиши связными абзацами по 2–3 предложения |
| Не придумывай цифры | Используй только цифры из `<report>`; если нужной цифры нет — напиши «нет данных» |
| Не упоминай внутренние проблемы | Объясни задержку причиной «высокая нагрузка в сезон» и сосредоточься на решении для клиента |

Запреты уместны как *дополнение* для действительно важных границ (например, «не обещай сроки, которых нет в тексте»), особенно с объяснением причины.

> **Почему так?** Запрет описывает огромное пространство «всего остального», и модель выбирает из него что-то среднее. Позитивная инструкция указывает точку. Кроме того, упоминание нежелательного (например, «не используй слово X») само по себе может подтолкнуть модель к нему.

## 8. Просить рассуждать перед ответом

Для задач, где нужно несколько шагов (анализ, расчёт, сравнение вариантов, поиск противоречий), попроси Claude **сначала рассуждать, потом отвечать**:

```text
Проанализируй продажи из <data> и ответь: какой регион нужно обсудить на встрече в первую очередь?

Сначала в <thinking> посчитай выручку по регионам, сравни их и отметь аномалии
(возвраты, пропущенные значения). Затем в <answer> дай ответ в 3–4 предложениях.
```

Почему это работает: модель генерирует ответ по token, и каждый следующий опирается на предыдущие. Если первым словом будет вывод («Регион Юг…»), дальше модель будет его *обосновывать*. Если сначала идут расчёты, вывод опирается на них.

Когда **не** нужно: простые задачи (перевести фразу, исправить опечатки, классифицировать очевидное) — рассуждения только удлинят ответ.

Бонус: рассуждения можно **прочитать** и найти, где модель ошиблась, — это полезно для отладки prompt.

Ещё лучше для точных расчётов — **попросить код**. В Claude Code: «Посчитай с помощью Python-скрипта и покажи результат» — Claude напишет и выполнит скрипт (с твоего разрешения), и цифры будут посчитаны, а не «предсказаны».

> **Почему так?** У модели нет «внутреннего черновика» помимо текста, который она пишет. Рассуждение вслух — это и есть её черновик: промежуточные шаги становятся частью контекста и улучшают итог. Компромисс — больше tokens и времени, поэтому используй для задач, где это окупается.

## 9. Право сказать «не знаю»

Claude обучен быть полезным — и иногда это толкает его дать *какой-нибудь* ответ, даже когда данных нет. Дай явное разрешение и инструкцию, что делать в этом случае:

```text
Ответь на вопросы по отчёту в <report>.
Используй только информацию из отчёта. Если ответа в отчёте нет или он
неоднозначен — напиши «В отчёте нет данных» и объясни, чего не хватает.
Для каждого ответа приведи дословную цитату из отчёта.
```

Три элемента:
1. **Источник** — «только по документу».
2. **Разрешение** — «если не знаешь — так и скажи» и *как* именно сказать (удобно, чтобы фразу можно было найти поиском).
3. **Проверяемость** — цитата, номер раздела, строка таблицы.

Это особенно важно для вопросов, где «похожий» ответ опаснее отсутствия ответа: цифры, сроки, условия договора, юридические и финансовые вопросы.

> **Почему так?** Hallucinations (модуль 01) возникают, когда модель «достраивает» правдоподобное. Явное разрешение не знать делает честный ответ «правильным продолжением» prompt, а требование цитат делает любую выдумку заметной при проверке.

## 10. Собираем всё вместе: шаблон prompt

Не каждый prompt требует всех элементов. Но для повторяющихся задач удобно держать **шаблон** — структуру, в которую подставляются данные:

```text
<!-- Роль (если помогает) -->
Ты — <позиция>, который готовит <результат> для <аудитория>.

<!-- Задача и цель -->
Задача: <что сделать>. Результат нужен, чтобы <что будет дальше>.

<!-- Контекст и ограничения -->
<context>
- <важный факт 1>
- <ограничение: длина, язык, что можно/нельзя, с причинами>
</context>

<!-- Примеры (для классификации, извлечения, единого стиля) -->
<examples>…</examples>

<!-- Данные -->
<data>
{{ВСТАВИТЬ ДАННЫЕ}}
</data>

<!-- Как думать и что делать при нехватке данных -->
Сначала <рассуждение/шаги>. Если <данных не хватает> — <что написать>.

<!-- Формат результата -->
Формат: <шаблон ответа>. Сохрани в <файл>, если работаешь в Claude Code.
```

Порядок, который хорошо работает: роль и задача → контекст → примеры → **данные** → вопрос/инструкции по формату. Когда данных много (длинный документ), ставь их **выше** вопроса, а вопрос — в конце: так инструкция не «теряется» под большим текстом.

Шаблон — это первый шаг к автоматизации. В модуле 04 ты соберёшь библиотеку таких шаблонов в файлах, а в модуле 07 превратишь лучшие из них в skills, которые вызываются одной командой.

> **Почему так?** Шаблон фиксирует удачную постановку задачи. Без него ты каждый раз пишешь prompt с нуля и каждый раз забываешь что-то своё (то формат, то ограничение). С шаблоном качество становится повторяемым, а улучшение одного шаблона улучшает все будущие запуски.

|---|--------|-----------|
| 1 | Понятно, **что** сделать и **зачем**? | добавь цель и что будет с результатом |
| 2 | Есть **контекст**, которого у Claude нет? | аудитория, ограничения, факты |
| 3 | Задан **формат**, длина, стиль, язык? | покажи шаблон ответа |
| 4 | Инструкции и данные **разделены**? | XML-теги или `@файл` |
| 5 | Нужны **примеры**? | 2–5 разнообразных few-shot examples |
| 6 | Понятно, **как проверить** качество? | критерии, цитаты, «если не знаешь — скажи» |
| 7 | Нет **лишнего**: противоречий, «воды», одних запретов? | переформулируй позитивно |

**Приёмы одной строкой**

| Приём | Фраза-заготовка |
|-------|-----------------|
| цель | «Результат нужен, чтобы …» |
| аудитория | «Читать будет …, у него … минут, ему важно …» |
| формат | «Ответ в формате: …» / «Только JSON, без пояснений» |
| теги | «Текст письма — в `<email>`» |
| примеры | `<examples><example>…</example></examples>` |
| рассуждение | «Сначала в `<thinking>` …, потом в `<answer>` …» |
| не знаю | «Если ответа нет в тексте — напиши "нет данных"» |
| цитаты | «Для каждого вывода приведи дословную цитату» |

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| prompt engineering | навык постановки задач для LLM |
| system prompt | служебная инструкция перед диалогом (в API); задаёт роль и правила |
| role prompting | задание роли/позиции модели в prompt |
| few-shot examples | несколько примеров «вход → выход» в prompt |
| zero-shot | prompt без примеров, только инструкция |
| XML-теги | метки `<имя>…</имя>` для разделения частей prompt |
| output format | требования к виду ответа: структура, длина, формат данных |
| CSV / JSON | табличный и структурированный форматы данных для программ |
| grounding | опора ответа на предоставленный источник |
| chain of thought | рассуждение по шагам перед ответом |
| шаблон prompt (prompt template) | prompt с местами для подстановки данных |

## Вопросы для самопроверки

1. Что такое «правило нового коллеги» и почему оно работает для Claude?
2. Почему в prompt важно указать не только «что сделать», но и «зачем»? Приведи пример, где это меняет результат.
3. Зачем оборачивать данные в XML-теги, если Claude и так «понимает», где письмо?
4. Как подобрать few-shot examples, чтобы они помогали, а не мешали?
5. В каких случаях роль («Ты — …») полезна, а в каких бесполезна?
6. Перепиши запрет «Не пиши слишком сложно» в позитивную инструкцию.
7. Почему просьба «сначала рассуждай, потом ответь» улучшает ответы в аналитических задачах? Когда она не нужна?
