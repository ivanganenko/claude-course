# Рубрика модуля 04

> Для агента-преподавателя. Файлы студента — в `~/claude-practice/04-context/`.
> Главное в модуле: студент **управляет процессом** — разбивает задачу, проверяет план и промежуточные результаты, хранит состояние в файлах и осознанно выбирает `/clear` / `/compact` / новую сессию.
> Справка по данным (`report.md`, `sales.csv`, `meeting-notes.txt`) — в начале `.teacher/rubrics/03.md`.
> Поведение `/compact`, plan mode и auto-compaction может отличаться между версиями Claude Code. Если наблюдения студента расходятся с README — не спорь, попроси свериться с `/help` и засчитывай честные наблюдения.

## Упражнение 1. Цепочка из 3 prompts

**Критерии**
- Обязательные: три шага с `/clear`, каждый читает только файл предыдущего; в `1-facts.md` цитаты и нет выводов; в `2-analysis.md` найдены оба противоречия; `3-memo.md` адресована директору с решениями; сравнение с одношаговой версией по конкретике.
- Желательные: студент проверил цифры в `1-facts.md`; в шаге 2 причины ссылаются на факты; заметил, что ошибку проще локализовать в цепочке.

**Эталон / пример хорошего решения**

`chain/prompts.md`:

```text
## Шаг 1 — извлечение
Извлеки из @report.md факты по темам: выручка, регионы, клиенты, поддержка, инциденты, персонал, проекты, риски.
Для каждого факта: короткая формулировка, цифры, дословная цитата в кавычках, номер раздела.
Не делай выводов и оценок — только то, что написано. Если в разных разделах одна величина указана по-разному,
выпиши оба места. Сохрани в chain/1-facts.md с заголовками по темам.

## Шаг 2 — анализ
Работай только с @chain/1-facts.md (сам отчёт не открывай).
1. Главные проблемы квартала (3–5), по каждой — факты-основания (ссылка на пункт из facts).
2. Вероятные причины — только если они следуют из фактов; иначе «причина не ясна из данных».
3. Противоречия и неточности внутри отчёта.
4. Решения, которые требуются от руководства, с аргументами.
Сохрани в chain/2-analysis.md.

## Шаг 3 — записка
По @chain/2-analysis.md напиши служебную записку генеральному директору. У него 5 минут;
он принимает решения о найме и бюджете. Структура: 1) суть в 2 предложениях; 2) три проблемы с цифрами;
3) «Нужны решения» — нумерованный список: что решить, до какого срока, цена бездействия;
4) примечание о расхождениях в отчёте. Не больше 1 страницы, деловой стиль без канцелярита.
Используй только факты из анализа. Сохрани в chain/3-memo.md.
```

Ожидаемое содержание анализа: (1) поддержка перегружена: время ответа 3,2 → 5,9 ч, CSAT 4,5 → 4,1, SLA «Премиум» выполнено для 71% обращений; штат 6 человек не менялся, обращений +22%; (2) отток 3,1% → 4,4%, главная причина в опросе — долгий ответ (7 упоминаний из 11 опрошенных); (3) «Запад» без роста, один менеджер на ~60 клиентов. Противоречия: «рост 12%» vs 9,8%; «поддержка стабильна» vs метрики. Решения: найм 2 сотрудников поддержки (до конца октября), вакансия «Запад» (до 15 ноября).

Типичное сравнение: одношаговая версия часто повторяет «рост 12%» из резюме и не замечает противоречия про поддержку; цепочка — находит, потому что на шаге 1 факты выписаны рядом.

**Частые ошибки**
- *Без `/clear` между шагами.* Тогда шаг 2 «видит» отчёт в истории, и эксперимент теряет смысл. **Почему важно:** цель — убедиться, что файл переносит всё нужное, и context остаётся чистым. Попроси повторить шаги 2–3.
- *В шаге 1 уже есть выводы («продажи на Западе плохие»).* Наведи: «Что в этом пункте написано в отчёте, а что — интерпретация?» Смешивание извлечения и анализа ломает проверяемость.
- *Шаг 2 читает `report.md`, а не facts.* Нарушение цепочки; напомни про явное «только по @chain/1-facts.md».
- *Сравнение «цепочка лучше» без примеров.* Попроси две конкретные разницы.

## Упражнение 2. Интервью

**Критерии**
- Обязательные: prompt запрещает начинать до ответов и ограничивает число вопросов; сохранён диалог; найдены скрытые предположения; вывод о применимости.
- Желательные: правило «если не знаю — предложи вариант по умолчанию и пометь»; вопросы отсортированы по важности.

**Эталон / пример хорошего решения**

Prompt:

```text
Мне нужно составить регламент работы отдельной очереди поддержки для клиентов «Сервис Премиум»
(контекст — разделы 5 и 10 в @report.md). Регламент будут читать сотрудники поддержки,
поэтому он должен быть конкретным: кто, что, в какие сроки.

Прежде чем писать, задай мне до 7 вопросов, без ответа на которые регламент получится общим.
Самые важные — первыми. Не начинай писать, пока я не отвечу.
Если на какой-то вопрос я отвечу «не знаю» — предложи разумный вариант по умолчанию и пометь его [по умолчанию].
```

Хорошие вопросы Claude: часы работы очереди и выходные; кто дежурит (2 из 6 сотрудников? ротация?); что считается «первым ответом» (автоответ не считается?); каналы (почта, телефон); эскалация при нарушении 2 часов; как клиент попадает в очередь (метка в системе); метрики и отчётность; что делать при пиках.

Скрытые предположения версии без интервью (пример): «очередь работает 24/7» (нереально при штате 6 человек); «выделить 3 сотрудников» (без учёта найма); «первый ответ — автоматическое письмо» (формально выполняет SLA, но не решает проблему клиентов).

Вывод: интервью — для задач, где у меня есть важный контекст, который я не догадался сообщить (регламенты, планы, документы для людей); не нужно — для коротких и однозначных задач.

**Частые ошибки**
- *Claude задал вопросы и сразу же написал регламент.* Prompt не запретил явно — попроси добавить «не начинай, пока я не отвечу». **Почему:** без явного запрета модель старается быть «полезной» сразу.
- *Ответы студента — «на твоё усмотрение» на всё.* Тогда интервью бессмысленно. Попроси ответить по существу хотя бы на 4–5 вопросов (опираясь на отчёт и заметки).
- *Не нашёл скрытых предположений.* Наведи: «Какие числа и правила в `without.md` взялись не из отчёта?»

## Упражнение 3. Plan mode

**Критерии**
- Обязательные: план в plan mode с файлами, шагами, проверкой и предположениями; минимум одна правка плана с причиной; выполнение и независимая проверка; A — отмечены возврат и пустой менеджер; B — нет выдуманных фактов.
- Желательные: студент читал diff при выполнении; в плане явно описана обработка аномалий (не удалять строки молча).

**Эталон / пример хорошего решения**

Вариант A — `plan.md` (после правки):

```markdown
# План: sales_report.py

Цель: из sales.csv получить sales-summary.md для встречи отдела продаж.

Файлы: создаётся sales_report.py и sales-summary.md; sales.csv не изменяется.

Шаги:
1. Прочитать sales.csv модулем csv (кодировка UTF-8), без внешних библиотек.
2. Посчитать выручку по регионам, менеджерам, категориям и общий итог (по колонке revenue).
3. Аномалии: строки с units < 0 (возвраты) — учитывать в сумме, но вывести списком;
   пустой manager — учитывать под «(не указан)» и вывести списком. Строки не удалять.
4. Записать sales-summary.md: таблицы + раздел «Аномалии».
5. Проверка: запустить скрипт; сверить итог (сумма revenue) с независимым подсчётом.

Предположения: revenue уже учитывает скидку; возврат относится к сентябрю.

Правка плана: в первой версии Claude предлагал «очистить данные — удалить строки с отрицательным количеством и пустым менеджером». Попросил не удалять, а учитывать и выводить списком: удаление исказит итог и скроет проблему от руководителя.
```

Ожидаемые числа в `sales-summary.md`: итог 1 909 674; Центр 858 300; Юг 371 220; Север 369 950; Запад 310 204; аномалии S-1016 (нет менеджера), S-1020 (возврат −39 900).

Пример минимального скрипта (для сравнения, после принятия):

```python
"""Сводка продаж из sales.csv в sales-summary.md."""
import csv
from collections import defaultdict

by_region, by_manager, by_category = defaultdict(float), defaultdict(float), defaultdict(float)
anomalies, total = [], 0.0

with open("sales.csv", encoding="utf-8", newline="") as f:
    for row in csv.DictReader(f):
        revenue = float(row["revenue"])
        manager = row["manager"] or "(не указан)"
        total += revenue
        by_region[row["region"]] += revenue
        by_manager[manager] += revenue
        by_category[row["category"]] += revenue
        if int(row["units"]) < 0:
            anomalies.append(f"{row['order_id']}: возврат, {revenue:,.0f} ₽")
        if not row["manager"]:
            anomalies.append(f"{row['order_id']}: не указан менеджер")

def table(title, data):
    lines = [f"## {title}", "", "| | Выручка, ₽ |", "|---|---:|"]
    lines += [f"| {k} | {v:,.0f} |" for k, v in sorted(data.items(), key=lambda x: -x[1])]
    return "\n".join(lines) + "\n"

with open("sales-summary.md", "w", encoding="utf-8") as out:
    out.write(f"# Продажи за сентябрь\n\nИтого: {total:,.0f} ₽\n\n")
    for title, data in [("Регионы", by_region), ("Менеджеры", by_manager), ("Категории", by_category)]:
        out.write(table(title, data) + "\n")
    out.write("## Аномалии\n\n" + "\n".join(f"- {a}" for a in anomalies) + "\n")
```

Вариант B — план: 4 файла в `onboarding/`; источники для каждого (разделы отчёта, заметки); правило «только факты из источников, неизвестное — [уточнить]»; проверка — сверка фактов. Правка плана (пример): Claude хотел придумать «контакты руководителей» — попросил оставить заглушки `[контакт]`, т.к. реальных данных нет и выдуманные контакты вредны.

**Частые ошибки**
- *План без шага проверки.* Самая частая. Наведи: «Как ты узнаешь, что скрипт посчитал правильно?» **Почему:** «дай Claude способ проверить себя» — центральная идея модуля 05.
- *«Правка плана» косметическая* (поменял имя файла). Засчитывай, если есть причина; но предложи поискать содержательную проблему (обработка аномалий, лишние изменения).
- *Студент не вышел из plan mode и удивляется, что Claude ничего не создаёт.* Объясни: в plan mode изменения запрещены — это и есть смысл режима.
- *Удалены «плохие» строки данных.* Обсуди: исчезновение возврата меняет итог на 39 900 ₽, а руководитель не узнает о проблеме.

## Упражнение 4. Критерии качества, самопроверка и обратная связь

**Критерии**
- Обязательные: проверяемые критерии; самопроверка Claude по каждому; независимая проверка студента; две конкретные обратные связи; v3 соответствует критериям без лишних обещаний.
- Желательные: студент нашёл случай, где самопроверка Claude была слишком мягкой; сформулировал правку для шаблона.

**Эталон / пример хорошего решения**

`quality/criteria.md`:

```markdown
1. Первое предложение — признание проблемы (нарушен срок ответа по договору), без оправданий.
2. Упомянуты все 3 меры: отдельная очередь с 1 ноября, бесплатный месяц обслуживания, звонок руководителя поддержки сегодня.
3. Нет обещаний, кроме этих трёх (никаких «больше не повторится», «ответ за 15 минут»).
4. Не длиннее 120 слов.
5. Извинение — не больше одного раза.
6. Обращение по имени («Руслан»), подпись — менеджер, без внутренних деталей о штате.
```

`quality/v3.md` (пример):

```text
Руслан, добрый день!

Вы правы: мы нарушили срок первого ответа, который гарантирует ваш договор «Премиум». Приносим извинения.

Сегодня с вами свяжется руководитель поддержки, чтобы решить ваш вопрос.
С 1 ноября для клиентов «Премиум» начинает работать отдельная очередь поддержки — обращения будут обрабатываться в первую очередь.
В качестве компенсации мы добавим вам месяц обслуживания бесплатно.

Спасибо, что сообщили нам о проблеме.

Павел, менеджер по работе с клиентами
«Полярная Сова»
```

`quality/feedback.md` (пример): 1) «Во втором абзаце фраза "из-за высокой нагрузки на наших специалистов" — это оправдание и внутренняя деталь. Убери, оставь только решение» → убрано. 2) «"Мы гарантируем, что подобное больше не повторится" — обещание, которого нет в фактах (критерий 3). Замени на описание очереди» → заменено.

Наблюдение: самопроверка Claude отметила критерий 3 как ✅, хотя в тексте было «больше не повторится» — модель не считает это «обещанием». В шаблон навсегда: список запрещённых формулировок-обещаний.

**Частые ошибки**
- *Непроверяемые критерии* («тон дружелюбный», «письмо хорошее»). Попроси переформулировать так, чтобы два человека одинаково оценили ✅/❌. **Почему:** иначе и самопроверка, и твоя оценка — субъективны.
- *Студент согласился с самопроверкой Claude без своей проверки.* Главная ошибка: попроси проверить самому. Объясни, что модель склонна оценивать свой текст мягко.
- *Обратная связь «сделай теплее/лучше».* Попроси формат «что — где — каким должно быть».

## Упражнение 5. `/compact` vs `/clear` vs новая сессия

**Критерии**
- Обязательные: замеры `/context` до/после `/compact`; `/compact` с инструкциями; ответы на 3 вопроса во всех точках; вывод про файлы.
- Желательные: студент заметил, что детали, не указанные в инструкциях `/compact` (вопрос «в»), сохранились частично или потерялись.

**Эталон / пример хорошего решения**

| Момент | Context | (а) суммы | (б) встреча | (в) выбор сводки |
|--------|---------|-----------|-------------|------------------|
| до `/compact` | ≈ X (много) | — | — | — |
| после `/compact` | заметно меньше X | ✅ | ✅ | частично: «выбрали первый вариант», без причины |
| после `/clear` | базовая нагрузка | ❌ не знает | ❌ | ❌ |
| `/clear` + `@decisions.md` | база + файл | ✅ | ✅ | ❌ (не было в файле) |
| `claude -c` (после `/clear`) | | ❌ — продолжилась уже очищенная история (или ✅, если студент сделал `/clear` в другой сессии — уточни) | | |
| новая сессия | база | ❌ | ❌ | ❌ |

Примечание к `claude -c`: результат зависит от того, что было последним в сессии. Если последняя сессия была после `/clear` — Claude «помнит» только то, что было после очистки. Засчитывай любое честное наблюдение с корректным объяснением.

Вывод (пример): «`/compact` сохраняет то, что я попросил, и сжимает остальное — детали теряются. `/clear` стирает всё. Надёжно переживает любые очистки и новые сессии только файл. Поэтому: решения и договорённости — в `decisions.md`; `/compact` — когда задача та же, но история разрослась; `/clear` — при смене задачи; новая сессия — новый день или работа, которую хочу сохранить отдельно».

**Частые ошибки**
- *`/compact` без инструкций.* Попроси повторить с инструкциями и сравнить. **Почему:** без инструкций сжатие само решает, что важно, — это и есть риск потери деталей.
- *Мало «истории» — `/compact` почти ничего не изменил.* Попроси добавить задач с чтением файлов.
- *Вывод «`/compact` лучше `/clear`».* Это разные инструменты для разных ситуаций. Попроси пример, где `/clear` правильнее (переход к несвязанной задаче).

## Упражнение 6. Своя библиотека prompts

**Критерии**
- Обязательные: ≥ 4 шаблона в едином формате; `prompts/README.md` с таблицей; проверка двух шаблонов на новых данных в чистой сессии; минимум одно улучшение с причиной.
- Желательные: новые тестовые данные содержат «ловушки» (изменённые сроки, пограничные письма); шаблоны не содержат зашитых данных из `practice/texts`.

**Эталон / пример хорошего решения**

`prompts/README.md`:

```markdown
# Библиотека prompts

Как вызывать в Claude Code: «Выполни шаблон @prompts/<файл> для @<данные>».

| Файл | Для чего | Вход | Выход |
|------|----------|------|-------|
| meeting-tasks.md | заметки встречи → задачи, решения, открытые вопросы | текст заметок | meeting-tasks.md (таблица) |
| email-triage.md | классификация писем клиентов | файл с письмами | CSV: номер;категория;срочность;суть |
| report-chain-1-facts.md | цепочка анализа отчёта, шаг 1 | отчёт | facts.md |
| report-chain-2-analysis.md | шаг 2 | facts.md | analysis.md |
| report-chain-3-memo.md | шаг 3 | analysis.md | memo.md |
| client-reply.md | ответ клиенту по фактам и критериям | письмо + факты | ответ + самопроверка |
| weekly-status.md | еженедельный статус проекта | заметки недели | статус ≤ 12 строк |
```

Пример единого заголовка шаблона:

```markdown
# Заметки встречи → задачи

**Когда использовать:** после любой встречи, где раздавались поручения.
**Что подставить:** {{ЗАМЕТКИ}} — текст или @файл; {{ДАТА_ВСТРЕЧИ}} — чтобы перевести «до пятницы» в дату.

## Шаблон
…

## История версий
- v1 (модуль 03): базовые правила.
- v2: на новых заметках модель включила в задачи «обсудили корпоратив». Добавил определение задачи: «действие после встречи с исполнителем».
```

**Частые ошибки**
- *Шаблоны содержат конкретные данные* (имена Тимура и Светы, «1 октября»). Тогда шаблон не переиспользуется. Попроси заменить на `{{...}}`.
- *Проверка на тех же данных, что и при создании.* Не выявляет хрупкость. **Почему:** шаблон «подогнан» под исходный пример; настоящая проверка — новые данные.
- *Папка `prompts/` из модуля 03 не скопировалась* (не было упр. 6 модуля 03 или другой путь). Помоги найти файл или начать библиотеку с шаблонов модуля 04.

## Упражнение 7. ⭐ Большой документ: сначала цитаты

**Критерии**
- Обязательные: верный самостоятельный эталон; дословные цитаты в B; оценка по 6 вопросам для A, B, B-повтора; вывод по типам вопросов.
- Желательные: студент заметил, что «цитаты сначала» сильнее всего помогают на вопросах 4–6 (сопоставление и «нет данных»), а на простых фактах (вопрос 3, первая часть) разницы почти нет.

**Эталон / пример хорошего решения**

`quotes/answers-key.md`:

| № | Эталонный ответ |
|---|-----------------|
| 1 | 29% (условие выполнено для 71%). Связь: главная причина ухода в опросе — «долгое время ответа поддержки» (7 упоминаний, опрошены 11 из 18). Но отчёт **не** говорит, что ушедшие были клиентами «Премиум» — прямую связь утверждать нельзя |

```text

Ответь на вопросы ниже по документу.
```

## Quiz

1. **Почему цепочка prompts часто лучше одного большого prompt?**
   → Каждый шаг — одна цель и только нужные данные; промежуточные результаты проверяемы; ошибку видно на том шаге, где она возникла.
   → *Почему:* студент должен назвать и фокус, и проверяемость.
2. **Что Claude делает и чего не делает в plan mode?**
   → Читает файлы, исследует, предлагает план; не изменяет файлы и не выполняет изменяющие действия.
   → *Почему:* понимание гарантии «во время обсуждения ничего не сломается».
3. **Чем `/compact` отличается от `/clear`?**
   → `/compact` сжимает историю в резюме и продолжает (можно указать, что сохранить); `/clear` полностью очищает историю. Файлы не меняются ни в одном случае.
   → *Почему:* частая путаница; уточни про файлы.
4. **Почему длинная сессия деградирует, даже если окно не заполнено?**
   → В context копятся устаревшие файлы, отменённые решения, другие задачи — это размывает внимание модели и сбивает её на старые договорённости.
   → *Почему:* связь с модулем 01 («влезает ≠ хорошо работает»).
5. **Ситуация: ты два часа работаешь над отчётом, Claude начал путать версии таблиц и «забывать» договорённости. Что сделаешь?**
   → Запишу договорённости и текущее состояние в файл (`decisions.md`, `plan.md`), затем `/compact` с инструкциями или `/clear` и продолжу, указав файлы.
   → *Почему:* правильный ответ включает «сохранить состояние в файл», а не только команду.
6. **Ситуация: тебе нужно написать положение о премировании, но ты не уверен, какие пункты важны. Как начнёшь работу с Claude?**
   → Попрошу интервью: до N вопросов, не начинать до ответов; если не знаю — вариант по умолчанию с пометкой.
   → *Почему:* интервью выявляет недостающий контекст до выполнения.
7. **Ситуация: Claude проверил свой текст по критериям и поставил везде ✅, но тебе ответ не нравится. Что сделаешь?**
   → Проверю сам по критериям; если критерии непроверяемые — переформулирую; дам конкретную обратную связь (что, где, каким должно быть); повторяющуюся правку перенесу в шаблон.
   → *Почему:* самопроверка не заменяет проверку человеком.
8. **Ситуация: нужно ответить на вопрос по договору на 80 страниц. Как поставишь задачу в Claude Code?**
   → Файл, а не копипаст (`@договор` или попросить найти нужные разделы); документ — сверху, вопрос — в конце; сначала дословные цитаты, потом ответ только по ним; «если нет — скажи».
   → *Почему:* проверяет связку приёмов для больших документов.

## Ответы на «Вопросы для самопроверки» из README

1. Каждый шаг решает одну задачу с нужными данными — модель фокусируется лучше; промежуточные результаты можно проверить и перезапустить по отдельности. Не нужна для коротких задач, которые стабильно решаются с первого раза.
2. Файл переносит состояние между шагами без накопления истории: можно сделать `/clear`, перезапустить шаг, поправить промежуточный результат руками, вернуться позже.
3. Когда у тебя есть важный контекст, который ты не сформулировал, или ты сам не до конца понимаешь требования: регламенты, планы, документы для людей, задачи с множеством вариантов.
4. Может: читать файлы, искать, исследовать, предлагать план. Не может: изменять файлы и выполнять изменяющие действия. В плане проверяю: понятна ли цель, какие файлы будут изменены, есть ли шаг проверки, нет ли лишнего, какие предположения сделаны.
5. Модель склонна мягко оценивать свой текст и может не заметить собственную фактическую ошибку или трактовать критерий удобно для себя. Самопроверка ловит часть ошибок, но решение принимает человек.
6. `/clear` — полностью очищает историю (пример: закончил отчёт, переходишь к письмам). `/compact` — сжимает историю в резюме, продолжая ту же задачу (пример: долгая работа над одним отчётом, история разрослась). Новая сессия — чистый старт с возможностью вернуться к старой через `/resume` (пример: новый день, другая задача).
7. В context накапливаются устаревшие файлы, отменённые попытки и посторонние темы. Модель учитывает всё, и «шум» размывает внимание, а старые договорённости конфликтуют с новыми.
8. Документ — в начале, вопрос и инструкции — в конце; попросить сначала выписать дословные цитаты, потом ответить только по ним; разрешить «нет данных»; в Claude Code — работать с файлом через `@`/поиск, а не копипаст.
