## Справка для преподавателя: три намеренных бага todo-app

Студенту причины не раскрывай — только симптомы (они в упражнении 3).

| # | Симптом | Где | Причина | Эталонное исправление |
|---|---------|-----|---------|----------------------|
| 1 | `list` показывает выполненные задачи; `list --all`, наоборот, их прячет | `todo.py`, `build_parser()` | `--all` объявлен с `action="store_false"` → по умолчанию `args.all == True` | `action="store_true"` |
| 2 | после `delete` новая задача получает уже существующий id | `models.py`, `next_id()` | `return len(tasks) + 1` — после удаления длина списка меньше максимального id | `return max((t.id for t in tasks), default=0) + 1` |
| 3 | сортировка: high → low → medium | `models.py`, `sort_tasks()` | ключ сортировки — строка `t.priority`, сравнение по алфавиту | ключ `-PRIORITIES.index(t.priority)` (или словарь `{"high": 0, "medium": 1, "low": 2}`) |

Воспроизведение на исходных данных (`todos.json` из practice):
- Баг 1: `python todo.py list` → видны задачи 3 и 5 с `[x]`; `python todo.py list --all` → они исчезают.
- Баг 2: `python todo.py delete 2` → `python todo.py add "Тест"` → «Добавлена задача 6» → `list` показывает две задачи с id 6; `done 6` закрывает первую найденную.
- Баг 3: `python todo.py list` → `low` выше `medium`.

Нюанс бага 2: эталонный фикс `max(id)+1` после удаления *последней* задачи переиспользует её id (удалили 6 → новая тоже 6). Дубликата нет, это допустимо. Если студент заметил это сам — похвали и обсуди, что строгое решение — хранить счётчик в файле (но это меняет формат `todos.json` и усложняет код; для учебного проекта избыточно).

- *`.venv` попал в коммит* (создан `.gitignore` после `git add`). → Объясни, почему это плохо (тысячи файлов, зависимость от ОС). Самый простой путь для новичка — удалить `.git` и начать заново (с согласия, это учебный проект); `git rm --cached` — только с объяснением.

- *Сделал `git init` в `~/claude-practice`, а не в `todo-app`.* → Объясни, что репозиторий — это папка с `.git`; проекты лучше держать в отдельных репозиториях, иначе история перемешается.

```python
def cmd_edit(args: argparse.Namespace) -> int:
    """Изменить поля задачи: только те, что переданы."""
    if args.title is None and args.priority is None and args.due is None:
        print("Укажите хотя бы одно поле: --title, --priority или --due.", file=sys.stderr)
        return 2
    tasks = load_tasks()
    task = find_task(tasks, args.id)
    if task is None:
        print(f"Задача {args.id} не найдена.", file=sys.stderr)
        return 1
    if args.title is not None:
        task.title = args.title
    if args.priority is not None:
        task.priority = args.priority
    if args.due is not None:
        task.due = args.due
    save_tasks(tasks)
    print(f"Изменена задача {task.id}: {format_task(task)}")
    return 0

# в build_parser():
    p = sub.add_parser("edit", help="изменить задачу")
    p.add_argument("id", type=int)
    p.add_argument("--title")
    p.add_argument("--priority", choices=PRIORITIES)          # без default!
    p.add_argument("--due", type=parse_due, help="новый срок, YYYY-MM-DD")
    p.set_defaults(func=cmd_edit)
```

## Упражнение 6. Ревью чужого изменения

**Критерии**
- Обязательные: ≥ 3 проблемы найдены самостоятельно с «почему»; одна подтверждена запуском; замечено изменение в `storage.py`; ревью Claude в чистом context; сравнение; изменения отменены.
- Желательные: найдена ошибка удаления из списка во время итерации; предложено, как исправить, без реализации.

**Эталон: полный список проблем**

| # | Проблема | Почему плохо |
|---|----------|-------------|
| 1 | `tasks.remove(task)` внутри `for task in tasks` | изменение списка во время обхода пропускает элементы: две выполненные задачи подряд → одна остаётся. Проверено: `done 3`, `done 4` (5 уже выполнена) → `clear` → задача 4 осталась |
| 2 | в `storage.py` убран `ensure_ascii=False` | изменение вне задачи; кириллица в `todos.json` превращается в `П...` — файл нечитаем человеком, огромный diff данных |
| 3 | `print("DEBUG", tasks)` | отладочный мусор в выводе пользователя |
| 4 | безвозвратное удаление без подтверждения и без сообщения «сколько удалено» | пользователь не понимает, что произошло; ошибку не отменить |
| 5 | `task.done == True` | стилистика: достаточно `if task.done` |
| 6 | нет тестов | изменение нельзя проверить автоматически; тест сразу поймал бы п.1 |

Правильная идея исправления (студенту — только как направление): `remaining = [t for t in tasks if not t.done]`, сообщение «Удалено N задач».

```text
Сделай ревью изменений в git diff как строгий старший разработчик.
Ищи: ошибки логики, необработанные случаи, изменения вне задачи (команда clear).
Для каждого замечания: файл, строка, проблема, почему это плохо. Код не меняй.
```

**Частые ошибки**
- *Claude при внесении «исправил» код Павла.* → Попроси `git restore .` и повторить с явным «внеси буквально, это учебное ревью». Заодно хороший разговор: Claude склонен улучшать — в реальном ревью это мешает понять, что прислал автор.
- *Студент сразу попросил ревью у Claude.* → Попроси сначала свой список: цель — натренировать собственный глаз, а не делегировать.
- *Пропущено изменение в `storage.py`.* → Объясни, что `git diff` показывает **все** файлы; изменения «вне задачи» — частый способ незаметно что-то сломать.
- *Проблема 1 не воспроизвелась.* → Скорее всего выполненные задачи не стояли в файле подряд. Попроси посмотреть порядок в `todos.json` и повторить.
- *Забыл `git restore`, в следующем упражнении грязная рабочая копия.* → Напомни про `git status` перед каждой задачей.

## Упражнение 7. ⭐ Сначала тест, потом код + история проекта

**Критерии**
- Обязательные: коммит тестов раньше коммита фичи; тесты падали до реализации; `tests/` не изменён реализацией; `CHANGELOG.md` без выдуманных пунктов; найден коммит изменения `next_id` с хешем.
- Желательные: тест на «задачи без срока в конце»; сортировка по приоритету по умолчанию не сломана (есть тест).

**Эталон**

Prompt (тесты):
```text
Добавь в todo-app опцию list --sort due (по сроку, задачи без срока в конце; по умолчанию —
как сейчас, по приоритету). Сейчас напиши ТОЛЬКО тесты в tests/test_sort.py, код не трогай.
Запусти их и покажи, что новые тесты падают, а старые проходят.
```
Prompt (реализация):
```text
Реализуй list --sort due так, чтобы все тесты прошли. Файлы в tests/ не меняй.
```

Пример теста:
```python
def test_list_sort_due_puts_tasks_without_due_last(todo_file, capsys):
    main(["add", "Без срока"])
    main(["add", "Поздно", "--due", "2026-12-01"])
    main(["add", "Рано", "--due", "2026-11-01"])
    capsys.readouterr()
    main(["list", "--sort", "due"])
    lines = capsys.readouterr().out.splitlines()
    assert "Рано" in lines[0]
    assert "Поздно" in lines[1]
    assert "Без срока" in lines[2]
```

`CHANGELOG.md`:
```markdown
# Changelog

## Добавлено
- Команда `edit` для изменения задачи.
- Опция `list --sort due`.
- Регрессионные тесты на исправленные баги.

## Исправлено
```

Шаг 6: `git log -p models.py` → коммит «Выдавать новый id как максимальный + 1», строка `- return len(tasks) + 1` / `+ return max(...) + 1`.

**Частые ошибки**
- *Тесты и реализация в одном коммите.* → Тогда нельзя показать, что тесты падали до кода; смысл «тесты вперёд» теряется.
- *Claude поменял тест, чтобы он прошёл.* → `git diff HEAD~1 -- tests/` должен быть пустым после коммита реализации. Обсуди, почему фраза «тесты не меняй» обязательна.
- *CHANGELOG содержит то, чего не было.* → Hallucination на ровном месте; именно поэтому шаг «сверь с git log».

## Quiz

1. **Почему перед просьбой починить баг полезно попросить Claude только объяснить причину?**
   → Чтобы проверить диагноз до правки. → Иначе Claude может исправить симптом, а не причину, и ты не узнаешь об этом; диагноз проверить дешевле, чем diff.
2. **Что значит «дай Claude способ проверить себя»?**
   → Дать ему команду/тесты, по которым он сам увидит, работает ли код (например, `python -m pytest`). → Без обратной связи модель только предполагает, что код верный.
3. **Ты написал тест на баг, и он проходит на сломанном коде. Что не так?**
   → Тест не проверяет поведение, где баг проявляется (например, проверяет фильтр, а баг в разборе аргументов). → Тест должен сначала падать; иначе он ничего не доказывает.
4. **Зачем коммитить до большого изменения?**
   → Чтобы иметь точку возврата и видеть через `git diff` всё, что поменялось. → Rewind ограничен сессией Claude; git видит любые изменения и хранит их долго.
5. **Ситуация: Claude в acceptEdits поменял 6 файлов, а ты просил исправить одну функцию. Что сделаешь?**
   → `git diff`, найти посторонние изменения, откатить (`git restore` / rewind), повторить с просьбой о минимальной правке. → Непрошеные изменения трудно проверить и они часто ломают то, что работало.
6. **Ситуация: тесты прошли, но после прогона в `git status` изменён `todos.json`. Что это значит?**
   → Тесты пишут в настоящие данные, нет изоляции. → Нужно `tmp_path` + `TODO_FILE` через `monkeypatch`; иначе тесты портят данные и зависят от их содержимого.
7. **Ситуация: попросил ревью у Claude в той же сессии, где он писал код, — замечаний нет. Чему не стоит верить и что сделать?**
   → Ревью «автора» необъективно; сделать `/clear` или новую сессию и повторить, плюс прочитать diff самому. → Свежий context не «помнит» намерений и смотрит на код как посторонний.
8. **Ситуация: Claude предлагает починить дубликаты id, перенумеровав все задачи по порядку. Хорошая идея?**
   → Нет: id существующих задач изменятся, пользователь закроет не ту задачу. → Чинить нужно генерацию нового id, а не данные; спрашивай «к каким побочным эффектам приведёт фикс?».

## Ответы на «Вопросы для самопроверки» из README

1. Чтобы отделить диагностику от правки и проверить, что причина найдена верно; иначе возможен фикс симптома, и ты не узнаешь, что реальная ошибка осталась.
2. Rewind откатывает изменения в рамках сессий Claude Code (checkpoints) и, как правило, не трогает правки, сделанные вручную или командами; `git restore` возвращает файл к последнему коммиту независимо от того, кто менял. Rewind — для быстрого «ой» в сессии, git — надёжная точка сохранения.
3. Тест не воспроизводит баг — проверяет не то место или не то поведение. Нужно переписать так, чтобы он падал на сломанном коде, и только потом чинить.
4. Тесты не должны портить реальные данные и не должны зависеть от их содержимого — иначе результат непредсказуем, а данные однажды пропадут. Решение — временный файл (`tmp_path`, `TODO_FILE`).
5. Diff становится большим и непроверяемым, растёт риск незаметной поломки, фикс нельзя откатить отдельно от «рефакторинга», история не объясняет, что и зачем менялось.
6. В той же сессии Claude опирается на свои намерения и склонен считать код верным; новая сессия смотрит на diff без предубеждения.
7. `.venv` большой, зависит от ОС и пересоздаётся по `requirements.txt` за минуту; в git хранят рецепт (`requirements.txt`), а не результат.
8. План обсуждается до кода: ошибку в понимании задачи исправить одной фразой дешевле, чем переделывать написанный код; plan mode гарантирует, что Claude ничего не изменит, пока план не одобрен.
