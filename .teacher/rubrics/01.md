# Рубрика модуля 01

> Для агента-преподавателя. Не показывай студенту целиком. Эталон — только после принятия упражнения, как «вариант для сравнения».
> Модуль выполняется в claude.ai, поэтому большинство результатов — наблюдения и таблицы. Оценивай **качество наблюдений и объяснений «почему»**, а не совпадение ответов Claude с эталоном: ответы модели у всех разные (это и есть тема модуля).

## Упражнение 1. Сколько влезает в context window

**Критерии**
- Обязательные:
  - размер context window взят из документации (страница Models), указана модель;
  - для 3 документов посчитаны символы и диапазон tokens;
  - есть сравнение с оценкой Claude;
  - вывод про «не влезающий» документ содержит конкретный приём.
- Желательные:
  - студент учёл, что окно включает не только документ, но и историю, инструкции и ответ (запас 10–30%);
  - студент заметил разницу «влезает» vs «хорошо обрабатывается».

**Эталон / пример хорошего решения**

Окно (пример): 200 000 tokens (студент должен взять своё число из docs).

| Документ | Символов | Оценка tokens | Сколько поместится в окно |
|----------|---------:|---------------|---------------------------|
| `emails.txt` (10 писем) | ≈ 2 100 | ≈ 700–1 100 | ≈ 180–280 |
| `report.md` (отчёт) | ≈ 7 000 | ≈ 2 300–3 500 | ≈ 55–85 |
| Договор, 30 стр. | ≈ 60 000 | ≈ 20 000–30 000 | ≈ 6–9 (с запасом на разговор — 5–7) |

Оценка Claude: ответ в том же порядке величины; расхождение в 1,5–2 раза нормально — правила грубые, а Claude тоже оценивает «на глаз» (у модели нет счётчика своих tokens в чате).

Выводы:
1. Тяжёлый — договор. В одно окно помещается, но если в том же чате ещё обсуждать 5 других документов, лучше разбить работу на отдельные чаты.
2. Если документ не помещается: разбить по разделам и сделать краткое резюме каждого, затем работать с резюме; или вставлять только релевантные разделы; или (с модуля 02) положить файл в папку и дать Claude Code читать нужные части.

**Частые ошибки**
- *«Точное» число tokens без диапазона.* Реакция: спроси, откуда уверенность. **Почему важно:** правило символов/4 — грубое, точность ±50%; ложная точность приводит к решениям «впритык».
- *Окно взято «из головы» или из старой статьи.* Попроси открыть docs. **Почему:** размеры меняются между моделями, курс специально не хардкодит цифры.
- *Забыл, что окно делят история и ответ.* Наводящий вопрос: «Если вставить документ на 190K tokens в окно 200K, сколько места останется на ответ и на твои вопросы?»
- *Вставил в чат реальный договор с данными клиентов.* Мягко верни к разделу 10 README. **Почему:** привычка обезличивать нужна с первого дня.

## Упражнение 2. Один prompt — разные ответы

**Критерии**
- Обязательные:
  - A, B, C — по 3 прогона, наблюдения конкретные;
  - новая версия B с фиксированным набором ответов и правилом для смешанного случая;
  - объяснение разного разброса.
- Желательные:
  - студент заметил, что у C разброс в формулировках, но не в факте (366 дней), у A — в содержании, у B — иногда в самом выводе;
  - формат ответа B машиночитаемый (одно слово).

**Эталон / пример хорошего решения**

| Prompt | Что совпало | Что различалось |
|--------|-------------|-----------------|
| A | 5 пунктов, тема продаж | сами названия почти все разные, стиль (серьёзные / игривые), наличие пояснений |
| B | упоминание, что отзыв смешанный | итоговый вердикт: «скорее негативный» / «смешанный» / «нейтральный»; длина 1–3 абзаца |
| C | 366 дней, лишний день — 29 февраля | объяснение названия, наличие истории про юлианский календарь, длина |
| B v2 | одно слово | ничего (3/3 одинаково) |

Новая B:

```text
Определи тональность письма клиента. Ответь ровно одним словом из списка:
позитивное, негативное, смешанное.
«Смешанное» — если в письме есть и похвала, и претензия.
Письмо: «Инженер приехал вовремя, но принтер так и не починил, хотя объяснил, что делать».
```

Объяснение: модель выбирает token с учётом вероятностей. У A много равновероятных продолжений → большой разброс. У C одно очевидно верное содержание → разброс только в форме. B исходно неоднозначен (нет вариантов «смешанное», нет формата) → модель каждый раз по-разному разрешает неоднозначность. Чёткий формат и критерии сужают выбор.

**Частые ошибки**
- *«Ответы немного разные».* Попроси конкретику: что именно? **Почему:** умение видеть, *что* плавает, — основа отладки prompts в модуле 03.
- *Перегенерировал в том же чате, задавая вопрос повторно текстом.* Тогда второй ответ видит первый и подстраивается. Объясни разницу между «перегенерировать» и «спросить ещё раз в том же чате» (во втором случае история в context).
- *Новая B: «ответь кратко и точно».* Это не ограничивает варианты. Наводящий вопрос: «Какими словами может ответить модель? Можно ли перечислить допустимые?»
- *Вывод «модель ненадёжна, пользоваться нельзя».* Переформулируй: ненадёжна без чёткой постановки и проверки; для творческих задач разброс — плюс.

## Упражнение 3. Граница знаний

**Критерии**
- Обязательные: cutoff сверен с docs; описано поведение без контекста; есть ответ по поданному тексту; вывод «почему текст в context надёжнее».
- Желательные: проверен вариант с веб-поиском (если доступен) и наличие ссылок; замечено, знает ли модель сегодняшнюю дату.

**Эталон / пример хорошего решения**

- Вопрос: «Что нового в версии X программы Y, вышедшей 2 недели назад?»
- Без контекста: Claude сказал, что его знания ограничены датой N, и описал предыдущую версию, но предупредил, что могли выйти обновления. (Другой возможный исход — уверенно описал «новую» версию — это и есть опасный случай.)
- С выдержкой: ответ точно по тексту, без лишних деталей.
- С поиском: ответ со ссылками на источники; проверил одну — совпадает.
- Вывод: для свежих данных — вставлять выдержку из первоисточника или использовать поиск со ссылками. Память модели заморожена на дату обучения и не может знать о событии; поданный текст модель «видит» прямо сейчас.

**Частые ошибки**
- *Выбрал событие, которое было до cutoff.* Тогда Claude отвечает правильно, и вывод искажается. Попроси выбрать событие свежее даты cutoff из docs.
- *Принял ответ Claude о собственном cutoff за истину без проверки.* **Почему важно:** модель может ошибаться и о себе; первоисточник — документация.
- *Вывод «Claude плохо знает новости».* Углуби: дело не в «плохо знает», а в механизме — у модели нет данных после даты обучения, поэтому решение — подать данные.

## Упражнение 4. Поймай hallucination и защитись от неё

**Критерии**
- Обязательные: таблица по 3 вопросам с методом проверки; сравнение «до/после» разрешения не знать; ответ по документу с проверкой цитаты.
- Желательные: студент проверил не только «есть ли ссылка», но и совпадают ли авторы/год/название; заметил тонкость с «7 упоминаний».

**Эталон / пример хорошего решения**

| Вопрос | Что ответил Claude (возможные исходы) | Правда? | Как проверил |
|--------|---------------------------------------|---------|--------------|
| «Обратная пирамида Кастельского» | либо «не знаю такого метода, возможно, вы имеете в виду…», либо правдоподобное описание | метода не существует (придуман для упражнения) | поиск в интернете — нет результатов |
| Летнее время в 2019 | хороший ответ: указывает на ложную предпосылку (переходы отменены в 2011, в 2014 — переход на постоянное «зимнее» время; в 2019 ничего не отменяли). Плохой — начинает объяснять «причины» | предпосылка ложная | поиск по первоисточникам |
| 3 исследования об open space | часть может быть реальной, часть — с неверными авторами/годом/ссылкой | проверено по каждому пункту | открыл ссылки, нашёл названия поиском |

После добавки «если не уверен — скажи» модель чаще прямо говорит, что не знает метода / что предпосылка неверна.

По документу (`report.md`, разделы 4–5): правильный ответ — **точное число клиентов в тексте не указано**: из 18 ушедших опрошены 11, «долгое время ответа поддержки» упомянуто 7 раз, причём можно было выбрать несколько причин. Дословная цитата: «долгое время ответа поддержки — 7 упоминаний». Ответ «7 клиентов ушли из-за поддержки» — неточность (подмена «упоминаний» на «клиентов» и 11 опрошенных на всех 18).

**Частые ошибки**
- *Не открыл ссылки: «ссылки есть — значит, правда».* **Почему важно:** выдуманные ссылки часто выглядят идеально — правильный домен, правдоподобный путь. Проверка — только открыть.
- *Claude сразу сказал «не знаю», и студент решил, что hallucinations не бывает.* Объясни, что это результат обучения и формулировки, а не гарантия; попроси повторить с более «наводящим» вопросом или с перегенерацией.
- *Принял «7 клиентов» как верный ответ.* Задай вопрос: «Сколько человек опросили? Можно ли было выбрать несколько причин?» — это тренирует внимательность к данным.

## Упражнение 5. Сравнение моделей

**Критерии**
- Обязательные: обе задачи прогнаны; для сложной задачи — перечень найденных противоречий по моделям; рекомендация на основе наблюдений.
- Желательные: учтены скорость и «цена»; отмечено, что простую задачу обе модели решают одинаково, поэтому быстрая модель там выгоднее.

**Эталон / пример хорошего решения**

Простая задача — правильная разметка: 1 доставка, 2 цена (возможно «цена» + «качество» — спорно, приемлемы оба, если объяснено), 3 качество, 4 доставка, 5 цена. Обе модели обычно справляются.

Сложная задача — реальные противоречия в `report.md`:
1. Резюме: «Выручка выросла на 12%», а таблицы дают 5 840 / 5 320 = **+9,8%** (в разделе 3 так и написано).
2. Резюме: «Качество поддержки оставалось стабильным», а раздел 5: время первого ответа 3,2 → 5,9 ч, решено за день 78% → 64%, CSAT 4,5 → 4,1.
3. (Нюанс, засчитывать как бонус) Резюме: «клиентская база выросла» — формально верно (412 → 431), но отток вырос 3,1% → 4,4% — умолчание, а не противоречие. Также CSAT сравнивается при разной доле ответивших (38% vs 45%).

Рекомендация (пример): «Для разметки отзывов возьму Haiku/быструю модель — результат такой же, а быстрее и дешевле. Для поиска противоречий в отчёте — Opus или Sonnet: быстрая модель нашла только про 12%, а про поддержку пропустила».

**Частые ошибки**
- *Нет доступа к нескольким моделям — студент пропустил упражнение.* Прими частично: прогон на одной модели + пометка; напомни выполнить сравнение в модуле 02 через `/model`. Запиши это в PROGRESS.md.
- *«Opus лучше, значит, всегда Opus».* Спроси: «А если таких писем 5 000 в день?» **Почему:** выбор модели — компромисс качества, скорости и стоимости.
- *Не проверил, верны ли найденные моделью противоречия.* Модель могла придумать лишнее. Попроси сверить с таблицами.

## Упражнение 6. Память и приватность

**Критерии**
- Обязательные: объяснено, почему новый чат не помнит правило; обезличенный текст без PII; ответ Claude пригоден для отправки после подстановки; пояснение, что оставлено и почему.
- Желательные: если есть Projects — проверено правило в инструкциях проекта; заглушки осмысленные (`[ИМЯ]`, `[ДОГОВОР]`), а не просто удалённые куски.

**Эталон / пример хорошего решения**

Память: во втором чате Claude не знает правила (или говорит, что у него нет информации). Причина: модель stateless, каждый чат — отдельная история; правило было только в истории первого чата. Если в аккаунте включена функция memory, результат может отличаться — тогда студент должен это заметить и объяснить, что это продукт подставил сведения в context. Решение для постоянных правил — инструкции Project (или `CLAUDE.md` в Claude Code, модуль 06).

Обезличенное письмо:

```text
Здравствуйте! Меня зовут [ИМЯ КЛИЕНТА], договор [НОМЕР ДОГОВОРА].
Мой телефон [ТЕЛЕФОН], почта [EMAIL]. С моей карты [КАРТА]
дважды списали 4 900 ₽ за сервисное обслуживание за сентябрь. Прошу вернуть лишнее
списание и ответить, почему так произошло.
```

Оставлено: сумма, период, суть (двойное списание) — без них нельзя написать содержательный ответ, и они не идентифицируют человека. Удалено: ФИО, договор, контакты, номер карты.

**Частые ошибки**
- *Оставил номер договора («он же не персональный»).* Объясни: номер договора однозначно связывает текст с человеком в базе компании — это тоже идентификатор.
- *Удалил вообще всё, включая сумму и суть.* Claude отвечает слишком общо. **Почему важно:** цель — убрать идентификаторы, а не смысл.
- *«У меня Claude запомнил!»* — включена функция memory. Не спорь: попроси объяснить, *как* это работает (текст из прошлых разговоров подставляется в context), и где это проверить в настройках.

## Упражнение 7. ⭐ Ловушки tokenization

**Критерии**
- Обязательные: 5 задач с независимой проверкой; два обходных пути хотя бы для двух задач; объяснение через tokens; практическое правило.
- Желательные: проверена стабильность (перегенерация); замечено, что современные модели часто решают такие задачи правильно — но нестабильно.

**Эталон / пример хорошего решения**

Правильные ответы для примеров:
- «обороноспособность» — букв «о»: **7** (о-б-о-р-о-н-о-с-п-о-с-о-б-н-о-с-т-ь: позиции 1, 3, 5, 7, 10, 12, 15).
- «перпендикуляр» наоборот: **рялукиднепреп**.
- 48 372 × 9 617 = **465 193 524**.
- Сортировка: в русском алфавите «е» < «ё» < «э»: **еда, ель, ёж, ёлка, эхо**.

| Задача | «В лоб» | Пошагово | Кодом |
|--------|---------|----------|-------|
| буквы «о» | иногда 6 или 8 | верно | верно |
| слово наоборот | ошибка в середине слова | верно | верно |
| умножение | последние цифры неверны | чаще верно | верно |
| сортировка с «ё» | путает «ё» и «е» | верно | зависит от кода (обычная сортировка строк ставит «ё» после «я» — хороший повод обсудить!) |

Механизм: слово разбито на несколько tokens, модель не «видит» буквы по отдельности; длинные числа разбиты на куски, и умножение «в уме» — это предсказание правдоподобных цифр. Выписывание по буквам превращает каждую букву в отдельный token → задача становится видимой. Код делает вычисление детерминированным.

Правило: «Когда прошу посчитать, отсортировать или сравнить символы — сразу прошу сделать это кодом или пошагово».

**Частые ошибки**
- *Всё решено правильно, студент делает вывод «проблемы нет».* Попроси перегенерировать 3 раза или взять более длинное слово/число. **Почему:** правильный ответ «в лоб» не гарантирован, и важно понимать риск, а не единичный результат.
- *Объяснение «модель не умеет математику».* Направь к tokens и next-token prediction: модель не «вычисляет», а предсказывает.
- *Код сортировки дал «ё» в конце, студент считает код правильным.* Отличный повод показать, что и код нужно проверять (стандартная сортировка по кодам символов ≠ алфавитный порядок).

## Quiz

1. **Что делает LLM на каждом шаге генерации ответа?**
   → Оценивает вероятности следующего token с учётом всего контекста, выбирает один и повторяет.
   → *Почему:* из этого следуют и гладкость, и ошибки; если студент говорит «ищет ответ в базе» — это ключевое заблуждение, разбери его.
2. **Что входит в context window?**
   → System prompt, вся история разговора, вложенные файлы/результаты инструментов и сам генерируемый ответ.
   → *Почему:* студенты часто думают, что только последнее сообщение; отсюда непонимание, почему длинные чаты «тяжелеют».
3. **Почему один и тот же prompt даёт разные ответы, и как сделать ответ стабильнее?**
   → Случайный выбор с учётом вероятностей (temperature). Стабильнее — чёткий формат, фиксированные варианты, примеры; проверка результата.
   → *Почему:* важно, что стабильность достигается постановкой задачи, а не «просьбой отвечать одинаково».
4. **Что такое hallucination и почему её нельзя полностью «выключить» просьбой «не ври»?**
   → Правдоподобный неверный ответ; модель оптимизирована на правдоподобие, у неё нет встроенной проверки истины. Помогают источник, разрешение не знать, цитаты, проверка.
   → *Почему:* ищи в ответе механизм, а не только список приёмов.
5. **Ситуация: коллега прислал ответ Claude со ссылкой на «статью 15.3 регламента», которую никто не может найти. Что сделаешь?**
   → Считаю это вероятной выдумкой; прошу коллегу найти первоисточник; в следующий раз даю Claude сам регламент и прошу цитату.
   → *Почему:* правильный рефлекс — проверка первоисточника, а не «переспросить Claude, точно ли он прав» (модель может «подтвердить» выдумку).
6. **Ситуация: нужно разметить 3 000 отзывов по 4 категориям, бюджет ограничен. Какую модель попробуешь первой и как убедишься, что её достаточно?**
   → Быструю (Haiku) или модель по умолчанию; прогоню 20–30 отзывов, сравню с ручной разметкой или с сильной моделью; если качество устраивает — масштабирую.
   → *Почему:* выбор модели проверяется на выборке, а не на ощущениях.
7. **Ситуация: ты договорился с Claude в одном чате о формате отчётов, а в новом чате он его не соблюдает. Почему и что сделаешь?**
   → Модель stateless, история нового чата пуста. Сохраню правило в инструкциях Project (или в файле/`CLAUDE.md` в Claude Code) либо вставлю его в начало чата.
   → *Почему:* «память» — это текст, подставленный в context.
8. **Ситуация: руководитель просит быстро «прогнать через Claude» выгрузку CRM с ФИО и телефонами клиентов, чтобы найти неактивных. Что сделаешь?**
   → Не вставляю как есть: оставляю ID и нужные столбцы (даты последних заказов), убираю ФИО/контакты; уточняю политику компании по AI-инструментам.
   → *Почему:* отправленные данные не вернуть, а для анализа активности имена не нужны.

## Ответы на «Вопросы для самопроверки» из README

1. Модель генерирует ответ по token, выбирая правдоподобное продолжение. Правдоподобие ≠ истина: текст может звучать уверенно и гладко, потому что так выглядят хорошие ответы, при этом содержание неверно. Встроенной проверки фактов нет.
2. System prompt продукта, вся предыдущая история чата (твои сообщения и ответы Claude), вложенные файлы и вставленный текст, результаты инструментов (поиск, чтение файлов), а также сам ответ, который генерируется.
3. Не ошибка: выбор token случайный с учётом вероятностей. Если различаются формулировки — нормально. Если различается *суть* — вопрос, скорее всего, неоднозначен или модель не уверена; стоит уточнить prompt и проверить ответ.
4. Версия вышла после knowledge cutoff (или почти на границе) — модель может описать старую версию или выдумать «новые функции». Проверить: официальные release notes/документация; дать Claude выдержку или использовать поиск со ссылками.
5. Любые три из: дать сам документ и попросить отвечать только по нему; разрешить сказать «не знаю»; попросить дословные цитаты; проверять цифры/имена/ссылки по первоисточнику; для расчётов — код.
6. Для 5 000 отзывов — быструю и дешёвую (Haiku): задача простая и массовая, важны скорость и стоимость; качество проверить на выборке. Для сложного договора — самую сильную (Opus) или Sonnet: важны точность и нюансы, объём небольшой.
7. Модель stateless. Внутри сегодняшнего чата продукт при каждом сообщении заново отправляет всю историю — поэтому «помнит». Вчерашний чат — отдельная история, она в context не попадает (если не включены функции вроде memory/Projects, которые сами подставляют текст).
8. Обезличить: заменить имя, компанию, контакты, номера договоров/карт на заглушки, оставить суть, суммы и даты, нужные для ответа. После получения ответа подставить данные обратно.
