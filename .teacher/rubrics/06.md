# Рубрика модуля 06

## Упражнение 1. `/init` и критика результата

**Критерии**
- Обязательные: каждый пункт размечен (✅/🗑/❓); команды реально запущены; ≥ 3 пункта «чего не хватает», которых нет в коде; объяснение вреда «очевидных» пунктов.
- Желательные: замечены платформенные различия (`python` vs `python3`, активация venv); посмотрен `/context`.

**Эталон**

Типичная разметка сгенерированного файла:

| Пункт `/init` | Метка | Почему |
|---------------|-------|--------|
| «todo.py — CLI на argparse, models.py — dataclass Task, storage.py — JSON» | 🗑 | видно из имён файлов и первых строк |
| «Запуск тестов: `pytest`» | ❓ | работает только в активированном venv; надёжнее `python -m pytest` |
| «Данные хранятся в todos.json, путь через TODO_FILE» | ✅ | важно для тестов и экспериментов |
| «Python 3.11+» | ✅ | синтаксис `str \| None` требует новой версии |
| «Код следует PEP 8» | 🗑/❓ | общая фраза, на поведение не влияет |

Чего не хватает (знание студента после модуля 05):
- `todos.json` — живые данные, не трогать в экспериментах и тестах; использовать `TODO_FILE` / `tmp_path`.
- После любой правки — `python -m pytest`; тест на баг сначала должен падать.
- Один баг/фича — один коммит, сообщение на русском в повелительном наклонении.
- Ошибки — в stderr и код возврата 1, как в `done`/`delete` (конвенция CLI).
- Формат `todos.json` не менять без явной просьбы (совместимость с существующими данными).

**Частые ошибки**
- *Принял файл как есть («выглядит хорошо»).* → Попроси применить к каждой строке тест «если удалить — Claude ошибётся?». Цель — научиться видеть пересказ кода.
- *Не запускал команды.* → Объясни: неверная команда в CLAUDE.md хуже отсутствующей — Claude будет уверенно запускать её в каждой сессии.
- *«Чего не хватает» — снова про структуру кода.* → Наводящий вопрос: «Что ты повторял Claude в модуле 05 больше одного раза?»
- *Удалил сгенерированный файл до сравнения.* → Не критично; попроси хотя бы восстановить по памяти 3–4 пункта.

## Упражнение 2. Свой CLAUDE.md для todo-app

**Критерии**
- Обязательные: ≤ 40 строк; точные команды; ≥ 3 правила с причиной; ≥ 1 запрет с альтернативой; нет секретов/личных путей/общих советов; закоммичено.
- Желательные: позитивные формулировки; правило про проверку работы (тесты); указано, как устроены ошибки CLI.

**Эталон** (`CLAUDE.md`, 24 строки)

```markdown
# todo-app — менеджер задач для командной строки (Python 3.11+, без зависимостей)

## Команды
- Запуск: `python todo.py <команда>` (add, list, done, delete, stats)
- Тесты: `python -m pytest` из корня проекта, в активированном .venv
- Перед завершением любой задачи с кодом — запусти тесты, все должны пройти.

## Данные
- todos.json — живые данные пользователя. Не редактируй и не «чисти» его:
  для экспериментов — `TODO_FILE=test.json`, в тестах — `tmp_path` + `monkeypatch.setenv("TODO_FILE", ...)`.
- Формат todos.json менять только по явной просьбе: у пользователя уже есть файлы в этом формате.

## Конвенции
- Сообщения пользователю — на русском. Ошибки — в stderr и `return 1`, как в cmd_done/cmd_delete,
  чтобы CLI можно было использовать в скриптах.
- Новая команда = функция `cmd_<имя>` + регистрация в build_parser() + тест в tests/.
- Тест на баг сначала должен падать на текущем коде — иначе он ничего не проверяет.

## Git
- Один баг или фича — один коммит. Сообщение на русском, повелительное наклонение:
  «Исправить …», «Добавить …».
- Перед большими изменениями проверь `git status`: рабочая копия должна быть чистой.
```

Удалено на шаге 3 (пример): «models.py содержит dataclass Task», «используй argparse», «пиши читаемый код».

**Частые ошибки**
- *Файл написан Claude.* → Принцип курса: студент пишет сам. Объясни: смысл — сформулировать знание, которое есть только у тебя; Claude его не знает.
- *Правила без причин.* → Покажи пару «не редактируй todos.json» vs «…потому что это живые данные; для экспериментов — TODO_FILE». Спроси, в каком случае первый вариант не поможет (Claude решит «почистить» тестовые задачи).
- *Только запреты («не делай»).* → Модуль 03: позитивная инструкция с альтернативой работает лучше — Claude знает, что делать вместо.
- *80+ строк.* → Каждая строка — tokens в каждой сессии и конкуренция за внимание. Попроси сократить до 40 по тесту «удалить — ошибётся?».
- *Личный путь вида `C:\Users\Ivan\...`.* → Это `CLAUDE.local.md`; в project-файле путь сломается у коллег.

## Упражнение 3. A/B тест правила

**Критерии**
- Обязательные: наблюдаемое правило; одинаковый prompt без подсказки; новая сессия/`/clear` перед каждым прогоном; ≥ 2 прогона на вариант; вывод по таблице; при провале B — переформулировка.
- Желательные: правило выбрано так, что в A оно заведомо не выполняется; изменения откатывались между прогонами.

**Эталон**

Правило в CLAUDE.md:
```markdown
- Каждая новая функция получает docstring на русском, начинающийся с глагола
  («Вернуть…», «Показать…») — так оформлен весь проект, и docstrings читают нетехнические коллеги.
```
Prompt (одинаковый): `Добавь команду count, которая печатает число невыполненных задач. Добавь тест.`

| Прогон | Правило | Выполнено? | Что увидел |
|--------|---------|-----------|------------|
| A1 | нет | частично | docstring есть, но «Print number of pending tasks» на английском |
| A2 | нет | частично | docstring на русском «Команда count», без глагола |
| B1 | да | да | «Показать число невыполненных задач.» |
| B2 | да | да | «Показать количество невыполненных задач.» |

Вывод: «Без правила Claude подражает стилю файла непоследовательно; с правилом оба прогона соответствуют. Эффект есть, но на двух прогонах — это сигнал, а не доказательство».

Примечание для преподавателя: Claude часто сам подражает стилю проекта, поэтому в A правило может выполниться «случайно». Это не провал — это ценный результат: значит, правило лишнее, и его можно удалить из CLAUDE.md. Похвали студента, если он пришёл к такому выводу.

**Частые ошибки**
- *Prompt содержит подсказку («добавь команду с русским docstring»).* → Тогда проверяется prompt, а не память. Попроси переделать.
- *Все прогоны в одной сессии.* → В context остаются предыдущие ответы; Claude «помнит» решение из прошлого прогона. Нужен `/clear` или новая сессия.
- *Один прогон на вариант.* → Недетерминированность (модуль 01): один результат может быть случайностью.
- *Правило ненаблюдаемое («пиши качественный код»).* → Нельзя заполнить колонку «выполнено?». Попроси правило, результат которого виден в diff.
- *Не откатывал изменения между прогонами.* → В B Claude видит команду count из A и просто её дописывает — сравнение испорчено.

## Упражнение 4. Личная память

**Критерии**
- Обязательные: user-файл без правил проекта; наблюдаемое предпочтение проверено в другой папке; `CLAUDE.local.md` в `.gitignore`; студент перечисляет загруженные memory files в todo-app и их источник.
- Желательные: ответ на шаг 5 с причиной; проверка через `/memory`.

**Эталон**

`~/.claude/CLAUDE.md`:
```markdown
# Мои предпочтения
- Отвечай на русском, технические термины — на английском.
- Я не разработчик: перед командой, которая меняет файлы, одной фразой объясни, что она сделает.
- Сначала вывод одной фразой, потом детали.
- Если задача неоднозначна — задай 1–3 уточняющих вопроса до работы.
- В конце ответа — строка «Следующий шаг: …».
```

`CLAUDE.local.md` в todo-app:
```markdown
- Мой файл для экспериментов: TODO_FILE=scratch.json (в .gitignore).
```
`.gitignore`: добавлены строки `CLAUDE.local.md` и `scratch.json`.

Memory files в todo-app: `~/.claude/CLAUDE.md` (user), `CLAUDE.md` (project), `CLAUDE.local.md` (local). Если `~/claude-practice` содержит свой CLAUDE.md — он тоже (родительская папка).

Шаг 5: «"Объясняй команды перед запуском" — моя потребность новичка; в project-файле она бы раздражала коллег-разработчиков и тратила их context».

**Частые ошибки**
- *В user-файле правила todo-app («тесты через python -m pytest»).* → Они «протекут» во все проекты, где неуместны или ошибочны.
- *Наблюдаемое предпочтение проверено только в todo-app.* → Там его мог дать project-файл; проверка в `scratch` доказывает, что работает именно user-уровень.
- *`CLAUDE.local.md` добавлен в `.gitignore` после `git add`.* → Файл уже отслеживается; `.gitignore` не действует на отслеживаемые файлы. Объясни и помоги убрать из индекса с пояснением команды.
- *Файл создан как `CLAUDE.md.txt` (Блокнот на Windows).* → Попроси проверить `dir $HOME\.claude`; объясни про скрытые расширения.
- *Предпочтение не проявилось.* → Проверить `/memory` (виден ли файл), правильность пути `~/.claude/`, новая ли сессия.

## Упражнение 5. Imports и rules

**Критерии**
- Обязательные: import работает; rules-файл с корректным `paths:`; наблюдаемое правило проверено на задаче с тестами; нет дублирования.
- Желательные: проверен «отрицательный» случай (правка README); `docs/testing.md` полезен людям сам по себе.

**Эталон**

В `CLAUDE.md` вместо блока о тестах:
```markdown
## Тесты
Подробно: @docs/testing.md
```

`docs/testing.md`:
```markdown
# Тесты todo-app
- Запуск: `python -m pytest -v` из корня проекта, в активированном .venv.
- Тесты не трогают todos.json: используйте fixture с `tmp_path` и
  `monkeypatch.setenv("TODO_FILE", str(путь))`.
- Команды CLI тестируем через `main([...])` и `capsys`.
- Тест на баг сначала должен падать на старом коде.
```

`.claude/rules/tests.md`:
```markdown
---
paths:
  - "tests/**/*.py"
---
# Правила для тестов
- Каждый тест начинается с комментария `# Проверяет: <поведение>` — так отчёт pytest легче читать коллегам.
- Один тест — одно поведение; имя описывает поведение (test_list_hides_done_tasks_by_default).
```

Наблюдение: в новом тесте для `stats` есть `# Проверяет: …`; при правке README правила тестов не упоминались.

**Частые ошибки**
- *Frontmatter сломан (нет закрывающего `---`, табы вместо пробелов, `path:` вместо `paths:`).* → Правило молча не применяется. Попроси сверить с README модуля и проверить через `/memory`.
- *Текст продублирован в CLAUDE.md и в docs/testing.md.* → Две копии разойдутся при первой правке; смысл import — одна правда.
- *Не начата новая сессия.* → Memory читается в начале сессии.
- *Правило из rules не сработало.* → Сначала проверить, загружено ли оно (`/memory`); затем — наблюдаемость и формулировку; при сомнениях в поведении `paths:` — сверить с docs (функциональность может меняться).

## Упражнение 6. ⭐ CLAUDE.md для своей рабочей папки

**Критерии**
- Обязательные: только вымышленные/обезличенные данные; аудитория, формат, запреты с причинами; 3 задачи в новых сессиях с таблицей; ≥ 1 итерация переформулировки; сжатие ≥ 20 % без потери работающих правил.
- Желательные: разделение `input/`/`output/`; правило о формате итогового документа с примером.

**Эталон** (пример для папки «еженедельные отчёты отдела»)

```markdown
# Еженедельные отчёты отдела продаж (вымышленная компания «Альфа-Трейд»)

Папка: input/ — выгрузки CSV из CRM, output/ — готовые отчёты, templates/ — шаблоны.
Читатель отчётов — руководитель отдела: 2 минуты на чтение, решения по цифрам.

## Правила
- Не изменяй файлы в input/ — это исходные выгрузки, их нельзя восстановить. Результат — в output/.
- Отчёт ≤ 1 страницы: сначала 3 вывода, потом таблица. Руководитель читает только начало.
- Цифры считай скриптом (python), не «в уме» — ошибки в суммах подрывают доверие ко всему отчёту.
- Если в данных пропуски или дубликаты — перечисли их в конце отчёта, не исправляй молча.
- Имена файлов: output/report-YYYY-MM-DD.md.
```

Таблица проверки:

| Задача | Правило | Соблюдено? |
|--------|---------|-----------|
| «Сделай отчёт за неделю по input/week40.csv» | output/, ≤ 1 стр., 3 вывода | да / нет: 5 выводов → уточнил «ровно 3» |
| «Сколько продаж у менеджера Б.?» | считать скриптом | да |
| «Исправь опечатки в выгрузке» | не трогать input/ | да: предложил копию в output/ |

**Частые ошибки**
- *Реальные данные клиентов/коллег.* → Остановить, попросить заменить на вымышленные. Объясни: файлы уходят в context модели; это privacy-гигиена из модуля 01 и политика большинства компаний.
- *Нет аудитории.* → Без неё Claude не знает, насколько подробно и каким языком писать.
- *Сжатие удалило работающее правило.* → Ровно поэтому нужна перепроверка после сжатия.

## Quiz

1. **Что такое memory в Claude Code технически?**
   → Markdown-файлы (CLAUDE.md и др.), которые автоматически добавляются в context в начале сессии. → Важно понимать: это не «знание модели», а текст в prompt; его можно прочитать и проверить.
2. **Почему CLAUDE.md должен быть коротким?**
   → Он занимает context в каждой сессии и конкурирует за внимание; длинный файл размывает важные правила. → Тест строки: «если удалить — Claude ошибётся?»
3. **Чем отличаются `CLAUDE.md` и `CLAUDE.local.md` в проекте?**
   → Первый — общий для команды, в git; второй — личный, в `.gitignore`. → Личные пути и эксперименты не должны попадать коллегам.
4. **Почему правило с причиной лучше голого запрета?**
   → Claude понимает цель и правильно действует в ситуациях, которые правило явно не описывает. → Пример: «не трогай todos.json, потому что это живые данные» удержит и от «чистки» файла.
5. **Ситуация: ты добавил правило в CLAUDE.md, но Claude его игнорирует. Твои действия?**
   → Новая сессия/`/clear`; `/memory` — загружен ли файл; проверить противоречия с другими уровнями; сделать правило конкретнее и наблюдаемым; A/B тест. → Чаще всего виновата старая сессия или расплывчатая формулировка.
6. **Ситуация: коллега добавил в project CLAUDE.md токен доступа к API «чтобы Claude мог ходить в сервис». Что скажешь?**
   → Убрать немедленно, токен считать скомпрометированным и перевыпустить; хранить в переменных окружения. → CLAUDE.md в git и в context модели — секрет останется в истории навсегда.
7. **Ситуация: в новом проекте Claude внезапно отвечает по-английски и предлагает странные команды. Где искать причину?**
   → `/memory`: какие memory files загружены — user-level, родительские папки, rules. → Память собирается с нескольких уровней, и «чужой» CLAUDE.md из родительской папки — частая причина.
8. **Ситуация: правила для тестов занимают половину CLAUDE.md, а чаще всего ты правишь документацию. Что сделаешь?**
   → Вынести их в `.claude/rules/tests.md` с `paths:` на тесты (или в импортируемый документ). → Правила грузятся там, где нужны, и не тратят context в остальных задачах.

## Ответы на «Вопросы для самопроверки» из README

1. CLAUDE.md загружается в каждую сессию: каждая строка тратит tokens и конкурирует за внимание модели; в длинном файле важные правила «тонут». Большое окно не означает, что модель одинаково внимательна ко всему.
2. Русский язык во всех проектах — `~/.claude/CLAUDE.md` (user). Команда тестов todo-app — project `CLAUDE.md` в корне todo-app (нужна всем, кто работает с проектом).
3. Причина объясняет цель — Claude применяет правило разумно в непредусмотренных ситуациях, а человек через полгода понимает, можно ли правило удалить.
4. `/init` видит только код: пересказывает очевидное, не знает договорённостей, запретов и «почему», может угадывать команды. Знание, которого нет в коде, добавляет человек.
5. A/B тест: тот же prompt без подсказки, без правила и с правилом, каждый прогон в новой сессии, 2–3 повтора, сравнение по наблюдаемому результату.
6. Начата ли новая сессия (или `/clear`); видит ли сессия файл (`/memory`); нет ли противоречащего правила на другом уровне; достаточно ли конкретна формулировка.
7. Секреты (пароли, токены, ключи API): файл лежит в git и попадает в context модели — секрет утечёт в историю и к каждому, у кого есть репозиторий.
8. В `rules` с `paths:` — когда правила касаются только части файлов и их много (тесты, отдельная подсистема). Один файл — пока проект маленький и всё умещается в несколько десятков строк.
