# Рубрика модуля 09

> Общие принципы проверки модуля: главное — понимание **изоляции context** и **ограничения tools как «замка»**. Студент может не помнить синтаксис, но должен объяснить, почему агент устроен так, а не иначе. Не принимай упражнение, где студент скопировал пример из README без адаптации и не может объяснить ни одного поля.
>
> Если в модуле 05 студент починил все три бага todo-app — это нормально; в упр. 3 он вносит ошибку сам. Если баги остались — они хороший материал для ревьюера (упр. 3) и для test-writer (упр. 4: тесты будут падать — это ожидаемо).

## Упражнение 1. Трасса agent loop

**Критерии**
- Обязательные: ≥ 4 шагов с реальными tools (Read, Grep, Glob, Bash…); для каждого — влияние на следующий шаг; найден момент корректировки плана; есть вывод про отказ в разрешении.
- Желательные: студент отмечает, что результат tool (содержимое файла) попадает в context; замечает, что Claude иногда делает несколько вызовов в одном шаге.

**Эталон / пример хорошего решения** (`agent-loop-trace.md`; конкретные шаги у студента будут другими — это нормально, у модели недетерминированный путь):

```markdown
| № | Что хотела узнать | Tool и аргумент | Что получила | Влияние на следующий шаг |
|---|---|---|---|---|
| 1 | Где данные и как устроен проект | Glob `**/*` | todo.py, models.py, storage.py, todos.json, tests/ | Решила прочитать данные |
| 2 | Сами задачи | Read todos.json | 6 задач, из них невыполненных high — N | Посчитала N |
| 3 | Что показывает CLI | Bash `python todo.py list` | 6 строк, включая выполненные | Увидела расхождение: done задачи в выводе |
| 4 | Почему | Read todo.py | функция cmd_list, фильтр по --all | Нашла: фильтр не применяется по умолчанию |
| 5 | — | — | — | Ответ: 2 задачи, list показывает и выполненные (баг) |

Корректировка плана: на шаге 3 — после вывода CLI модель пошла читать код, хотя изначально хотела просто сравнить числа.

Отказ на Bash: модель не смогла запустить CLI и сказала, что сделает вывод по коду / попросила меня запустить команду самому. Цикл не сломался — отказ стал «результатом tool», и модель выбрала другой путь.
```

**Частые ошибки**
- *Таблица без столбца «влияние»* — это просто лог, а не понимание цикла. Спроси: «Почему на шаге 4 Claude открыл именно todo.py?» **Почему важно:** суть agent loop в том, что следующий шаг зависит от результата предыдущего.
- *Работал в `acceptEdits`/с разрешёнными командами, ничего не увидел* — попроси повторить в `default`. **Почему:** подтверждения — самый наглядный способ увидеть каждый шаг.
- *«При отказе Claude сломался»* — уточни, что произошло на самом деле. Обычно модель получает отказ как результат и адаптируется. **Почему важно:** отказ — нормальный инструмент управления агентом, а не авария.
- *Баги уже исправлены, расхождения нет* — нормально; тогда «корректировка плана» может быть в другом месте. Не требуй именно этого сценария.

## Упражнение 2. Explore: изоляция контекста

**Критерии**
- Обязательные: реальные числа `/context` для А и Б; описание признаков работы subagent; вывод с объяснением «почему»; упоминание цены.
- Желательные: вариант В (параллельные) выполнен; оценка качества ответа, а не только чисел; прогноз для большого проекта.

**Эталон / пример хорошего вывода** (числа у студента будут другими):

```markdown
| Вариант | До | После | Прирост | Качество | Время |
|---|---|---|---|---|---|
| А (сам) | 14k | 27k | +13k | 5 | ~40 с |
| Б (Explore) | 14k | 16k | +2k | 4 | ~60 с |
| В (3 Explore параллельно) | 14k | 18k | +4k | 5 | ~70 с |

Вывод: в варианте А всё прочитанное (код, тесты, todos.json) осталось в моём context.
В Б Explore читал те же файлы в своём context, а мне вернул только сводку — поэтому прирост меньше.
Цена: Б и В дольше и в сумме потратили больше tokens (агент читал файлы, плюс старт агента).
На todo-app разница небольшая, на проекте из 300 файлов вариант А забил бы context за несколько вопросов,
а Explore вернул бы те же 2–3k. Выгодно, когда сырого материала много, а нужен короткий вывод.
```

**Частые ошибки**
- *Не сделал `/clear` между вариантами* — числа несравнимы. **Почему:** прирост должен считаться от одинаковой стартовой точки.
- *Вывод «Explore экономит tokens»* — неточно. Он экономит **context основной сессии**, а суммарно tokens тратится обычно больше. Попроси различить эти две вещи. **Почему важно:** иначе студент будет звать агентов на всё подряд «ради экономии».
- *Разница мизерная/обратная* — на маленьком проекте возможно (сводка Explore почти равна объёму файлов). Это хорошее наблюдение, а не провал: обсуди, при каком соотношении «сырые данные / итог» subagent окупается.
- *Claude не вызвал Explore в варианте Б* — попроси переформулировать явнее («Используй subagent Explore…») и проверить, что студент видит запуск агента в интерфейсе.

## Упражнение 3. Read-only `code-reviewer`

**Критерии**
- Обязательные: `tools` без Edit/Write/Bash; `description` — «когда»; формат ответа и порядок проверки; найдена реальная ошибка; шаг 5 выполнен.
- Желательные: уровни серьёзности; инструкция на случай сомнений; `model` выбран осознанно; учтены ложные срабатывания в заметках.

**Эталон** (`.claude/agents/code-reviewer.md`):

```markdown
---
name: code-reviewer
description: Ревью изменений в Python-коде todo-app. Используй после любых правок кода, перед коммитом, а также когда пользователь просит "проверь код", "сделай ревью", "посмотри изменения".
tools: Read, Grep, Glob
model: sonnet
---

Ты — ревьюер Python-кода в небольшом CLI-приложении задач (todo.py — CLI, models.py — Task, storage.py — чтение/запись todos.json).

Тебе передают список файлов или описание изменений. Если передан diff — сосредоточься на изменённых строках, но смотри и на их окружение.

Порядок проверки:
1. Корректность: логика, граничные случаи (пустой список, несуществующий id, повторный done, удаление последней задачи).
2. Целостность данных: может ли код записать в todos.json некорректные данные или потерять задачи; уникальность id.
3. Поведение CLI: соответствует ли справке argparse (например, list без --all скрывает выполненные).
4. Читаемость: имена, длина функций, docstrings.
5. Тесты: есть ли тест на изменённое поведение.

Формат ответа (не длиннее 25 строк):
| файл:строка | серьёзность (критично/важно/мелочь) | проблема | почему это плохо | как исправить |
Вердикт: «можно коммитить» или «нужно исправить: N критичных, M важных».

Правила:
- Ты не меняешь файлы — только читаешь и комментируешь.
- Не придумывай проблемы ради количества. Если сомневаешься — пометь «под вопросом» и напиши, как проверить.
- Не переписывай код целиком; в «как исправить» — 1–2 строки идеи.
```

`reviewer-notes.md` (пример): «Найдено 4 замечания: 2 реальных бага (фильтр list, id через len), 1 мелочь (нет docstring), 1 ложное (сортировка — на самом деле я её уже починил). На шаге 5 subagent ответил, что не может редактировать файлы, и вернул рекомендации. После этого основная сессия предложила исправить сама и спросила разрешение на Edit — `git status` показал изменения, но их сделала основная сессия, а не ревьюер».

**Частые ошибки**
- *`tools: Read, Grep, Glob, Bash` «чтобы смотреть git diff»* — Bash позволяет и `rm`, и `sed -i`. **Почему плохо:** read-only теряется. Обсуди компромисс: diff может получить основная сессия и передать в задании, либо назвать изменённые файлы. Если студент осознанно оставил Bash и ограничил в prompt — прими как «желательно улучшить», но пусть объяснит риск.
- *`description: "Агент для ревью кода"`* — описывает «что», не «когда». **Почему плохо:** основная сессия не поймёт, в каких ситуациях звать его автоматически.
- *Вывод шага 5 «ревьюер исправил файл»* — разберись: почти всегда исправляла основная сессия. **Почему важно:** студент должен различать, кто действует; иначе он неверно оценит, что гарантирует ограничение tools.
- *Нет формата ответа* — ревьюер вернёт «простыню». **Почему плохо:** длинный ответ съедает context основной сессии и смешивает важное с мелочами.
- *Агент не виден в `/agents`* — проверь путь (`.claude/agents/`, не `.claude/agent/`), расширение `.md`, корректный frontmatter (`---` в первой строке), перезапуск сессии.

## Упражнение 4. `test-writer`

**Критерии**
- Обязательные: изменения только в `tests/`; реальный `todos.json` не затронут; pytest запускается, падения объяснены; выбор модели обоснован.
- Желательные: тесты через CLI или функции с изоляцией через `TODO_FILE`; агент сообщает о найденных багах, а не маскирует их; итоговый ответ агента короткий.

**Эталон** (`.claude/agents/test-writer.md`):

```markdown
---
name: test-writer
description: Пишет и запускает pytest-тесты для todo-app. Используй, когда нужно покрыть тестами новую или изменённую функцию или команду CLI.
tools: Read, Grep, Glob, Write, Edit, Bash
model: sonnet
---

Ты пишешь pytest-тесты для CLI-приложения задач на Python.

Порядок:
1. Прочитай код, который нужно покрыть, и существующие тесты в tests/ — следуй их стилю.
2. Составь список случаев: обычный, граничные (пустой список, несуществующий id), ошибочный ввод.
3. Напиши тесты в tests/test_<модуль>.py.
4. Запусти `python -m pytest -q` и прочитай результат.

Границы (строго):
- Создавай и меняй файлы ТОЛЬКО в tests/.
- НЕ меняй todo.py, models.py, storage.py, todos.json, requirements.txt.
- Тесты не должны трогать реальный todos.json: используй tmp_path и переменную окружения TODO_FILE (через monkeypatch.setenv или env при запуске subprocess).
- Если тест падает из-за ошибки в коде приложения — НЕ исправляй код и НЕ ослабляй тест. Оставь тест и сообщи о баге.

Итоговый ответ (до 15 строк):
- какие файлы создал/изменил;
- сколько тестов, сколько прошло/упало;
- для каждого упавшего: какое поведение ожидалось, что получено, вероятный баг в коде (файл и функция).
```

Обоснование модели (пример): «sonnet — тесты требуют понимания логики, haiku может пропустить граничные случаи, opus избыточен для маленького проекта».

Пример теста, использующего только контракт проекта (CLI + `TODO_FILE`), — устойчив к тому, как именно названы функции в `storage.py`:

```python
import json
import os
import subprocess
import sys
from pathlib import Path

APP = Path(__file__).resolve().parent.parent / "todo.py"


def run(tmp_path, *args):
    env = {**os.environ, "TODO_FILE": str(tmp_path / "todos.json")}
    return subprocess.run([sys.executable, str(APP), *args],
                          capture_output=True, text=True, env=env)


def test_add_saves_to_file(tmp_path):
    result = run(tmp_path, "add", "Купить бумагу", "--priority", "high")
    assert result.returncode == 0
    data = json.loads((tmp_path / "todos.json").read_text(encoding="utf-8"))
    assert any("Купить бумагу" in str(item) for item in data)


def test_stats_counts_done(tmp_path):
    run(tmp_path, "add", "Задача 1")
    run(tmp_path, "add", "Задача 2")
    run(tmp_path, "done", "1")
    result = run(tmp_path, "stats")
    assert result.returncode == 0
    assert "2" in result.stdout and "1" in result.stdout


def test_ids_unique_after_delete(tmp_path):   # ловит баг №2, если он не исправлен
    for t in ("A", "B", "C"):
        run(tmp_path, "add", t)
    run(tmp_path, "delete", "1")
    run(tmp_path, "add", "D")
    data = json.loads((tmp_path / "todos.json").read_text(encoding="utf-8"))
    ids = [item["id"] for item in data]   # todos.json — список объектов задач
    assert len(ids) == len(set(ids))
```

(Проверено на `practice/todo-app/`: первые два теста проходят, третий падает, пока не исправлен баг №2 (`assert 3 == 2`, ids `[2, 3, 3]`). Вывод `stats` — строки «Всего задач / Выполнено / Осталось / Просрочено / по приоритету», поэтому проверка `"2" in stdout` грубая; хорошее решение студента парсит конкретные строки.)

**Частые ошибки**
- *Тесты пишут в реальный `todos.json`* — после прогона данные студента испорчены. **Почему плохо:** тесты должны быть изолированы и повторяемы; второй запуск даст другой результат. Направь к `tmp_path`/`TODO_FILE`.
- *Агент «починил» код приложения, чтобы тесты прошли* — проверь `git diff`. **Почему плохо:** тестировщик, который меняет проверяемый код, подгоняет ответ под тест; баг скрыт, а не найден. Усилить prompt, а в модуле 10 — hook.
- *Агент ослабил assert, чтобы тест «позеленел»* — то же самое. Спроси: «Что этот тест теперь проверяет?»
- *Все тесты зелёные при неисправленных багах* — тесты, вероятно, проверяют фактическое (неправильное) поведение. **Почему важно:** тест должен описывать *ожидаемое* поведение, а не текущее.
- *`model: opus` «потому что лучше»* — допустимо, но попроси оценить цену/скорость. Цель — осознанный выбор.

## Упражнение 5. Цепочка из двух subagents

**Критерии**
- Обязательные: `search` работает, тесты есть и проходят; в заметках описаны оба агента и передача между этапами; рефлексия «стоило ли того»; коммит до изменений.
- Желательные: план в файле и правки студента в нём; основная сессия показала замечания до исправления; ревьюер нашёл что-то реальное; `/context` записан.

**Эталон** — `plan.md` (кратко):

```markdown
# План: команда search
1. todo.py: добавить subparser "search" с позиционным аргументом text.
2. Функция cmd_search(args): загрузить задачи, отфильтровать по text.lower() in task.title.lower(),

4. Пустой результат: сообщение "Ничего не найдено", код выхода 0.
5. Тесты (test-writer): найдено / регистр / не найдено / пустая строка.
```

`chain-notes.md` (пример):

```markdown
Порядок: Explore (структура CLI) → план → реализация (основная сессия) → test-writer → code-reviewer → исправления.
- Explore вернул: команды в todo.py через argparse subparsers, печать в функции print_tasks.
- test-writer: создал tests/test_search.py, 4 теста, 4 прошли. Сообщил: пустая строка находит все задачи — уточнить, желаемо ли.
- code-reviewer: 1 важное (search не обрабатывает пустую строку осознанно), 2 мелочи. Это пропустила основная сессия.
- Основная сессия передавала каждому агенту: список изменённых файлов и описание фичи из plan.md.
- /context в конце: 31k.
Стоило ли: для такой фичи — на грани. Ревьюер нашёл 1 реальную проблему, но цепочка заняла ~6 минут вместо ~2.
Для фичи, затрагивающей хранение данных, — стоило бы точно.
```

**Частые ошибки**
- *Цепочка не запустилась — основная сессия сама написала тесты и сама «проверила»* — попроси явно назвать агентов в prompt и убедиться, что они созданы (`/agents`). **Почему важно:** смысл упражнения — разделение ролей.
- *Нет коммита до изменений* — верни к правилу модуля 05. **Почему:** при неудачной цепочке откат должен быть одной командой.
- *Ревьюер ничего не нашёл → «ревью не нужно»* — обсуди: ревью — страховка; ценность в том, что изредка ловит дорогую ошибку. Но вывод «на маленьких фичах дорого» вполне корректен.
- *Не прочитал `plan.md`, сразу «ок»* — спроси, что в плане было спорным. **Почему:** пауза на план — твой главный рычаг контроля; без чтения она бесполезна.
- *Пытался заставить subagent вызвать другого subagent* — объясни, что оркестрирует основная сессия: она вызывает агентов по очереди и передаёт результаты.

## Упражнение 6 ⭐. Agent loop на SDK

**Критерии**
- Обязательные: `search_text` работает и использует `safe_path`; модель вызвала его сама; объяснены рост `tokens in` и `MAX_TURNS`; ключа нет в файлах.
- Желательные: ограничение размера вывода `search_text`; эксперимент с плохим и хорошим `description`.

**Эталон** — добавка в `agent.py`:

```python
# в TOOLS:
{
    "name": "search_text",
    "description": "Найти строку во всех .py и .md файлах внутри папки (рекурсивно). "
                   "Используй, когда нужно узнать, в каком файле что-то определено или упоминается, "
                   "вместо чтения всех файлов подряд.",
    "input_schema": {
        "type": "object",
        "properties": {
            "pattern": {"type": "string", "description": "Искомый текст (без учёта регистра)"},
            "path": {"type": "string", "description": "Папка относительно рабочей, например '.'"},
        },
        "required": ["pattern", "path"],
    },
},

# в run_tool, перед финальным return:
if name == "search_text":
    base = safe_path(args["path"])
    needle = args["pattern"].lower()
    hits = []
    for f in sorted(base.rglob("*")):
        if f.suffix in (".py", ".md") and ".venv" not in f.parts:
            for n, line in enumerate(f.read_text(encoding="utf-8", errors="replace").splitlines(), 1):
                if needle in line.lower():
                    hits.append(f"{f.relative_to(ROOT)}:{n}: {line.strip()}")
    return "\n".join(hits[:50]) or "Ничего не найдено"
```

Ответы для `sdk-notes.md`: `tokens in` растёт, потому что каждый запрос отправляет **всю** историю `messages`, включая результаты прошлых tools (API stateless — модель не помнит прошлый запрос). `MAX_TURNS` — предохранитель от бесконечного цикла (модель может «застрять», повторяя вызовы), то есть от бесконечных расходов; при `MAX_TURNS = 2` агент обрывается без ответа.

**Частые ошибки**
- *Ключ записан в `agent.py` или `.env` в git* — немедленно: удалить, **отозвать ключ в консоли** и создать новый. **Почему:** ключ в файле легко утекает (git, скриншот, чат), а это доступ к счёту.
- *`search_text` без `safe_path`* — агент может читать любые файлы на диске. **Почему плохо:** мы ограничиваем tools на стороне программы, а не надеемся на модель.
- *Модель не вызывает tool* — почти всегда слабый `description`. Хорошо, если студент сам это обнаружил и починил.
- *Не возвращают `assistant`-сообщение перед `tool_result`* — API вернёт ошибку. **Почему:** `tool_result` должен ссылаться на `tool_use_id` из предыдущего ответа модели.
- *Сканирует `.venv`* — тысячи файлов, огромный вывод. Отсюда исключение и лимит `hits[:50]`.

## Quiz

1. **Из каких трёх частей состоит agent?**
   → LLM, tools, цикл (agent loop).
   → Почему: без цикла модель делает один ход; без tools — только говорит. Обрати внимание, назвал ли студент цикл — это чаще всего забывают.

2. **Кто выполняет команду, когда Claude «вызывает Bash»?**
   → Программа Claude Code на твоём компьютере; модель лишь просит.
   → Почему: отсюда permissions и hooks — контроль на стороне программы. Если студент говорит «модель выполняет» — вернись к разделу 2.

3. **Что возвращается в основную сессию после работы Explore?**
   → Только итоговый ответ (сводка) subagent; прочитанные им файлы остаются в его context.
   → Почему: это и есть изоляция context. Проверь, что студент не путает «экономит context» и «экономит tokens».

4. **Почему `tools: Read, Grep, Glob` лучше, чем фраза «не редактируй» для ревьюера?**
   → Ограничение tools — физический запрет («замок»), фраза — просьба, которую модель может нарушить.
   → Почему: для ролей с дорогой ошибкой нужна гарантия, а не вероятность.

5. **Ситуация: ты 30 минут обсуждал с Claude тонкие требования к отчёту и хочешь поручить реализацию subagent. Что сделаешь?**
   → Скорее всего, сделаю в основной сессии, или сначала запишу требования в файл и передам агенту ссылку на файл.
   → Почему: subagent не видит разговора; без явной передачи он потеряет все договорённости.

6. **Ситуация: твой агент `test-writer` «починил» `storage.py`, чтобы тесты прошли. Что сделаешь?**
   → Откачу правку (`git restore storage.py`), усилю границы в system prompt (только `tests/`, о багах сообщать), повторю; позже можно поставить hook-замок (модуль 10).
   → Почему: тест должен находить баг, а не подстраивать код; изменения агента всегда проверяю `git diff`.

7. **Ситуация: нужно переименовать переменную в одном файле. Позовёшь цепочку из 4 агентов?**
   → Нет, основная сессия сделает это быстрее и дешевле.
   → Почему: накладные расходы агентов (старт, повторное чтение, время) окупаются только на объёмных/рискованных задачах.

8. **Ситуация: основная сессия ни разу сама не позвала твоего `code-reviewer`, хотя ты делал правки. Что проверишь?**
   → `description`: описано ли «когда звать» словами, похожими на реальные запросы; агент виден в `/agents`; при необходимости — правило в CLAUDE.md «после правок кода используй code-reviewer».
   → Почему: автоматический выбор агента идёт по `description`, как у skills.

## Ответы на «Вопросы для самопроверки» из README

1. **Agent vs LLM в чате.** Agent = LLM + tools + цикл. В чате модель отвечает один раз на твоё сообщение и не может действовать; agent сам собирает информацию, действует и проверяет результат, повторяя шаги.
2. **Кто выполняет tool.** Программа вокруг модели (Claude Code). Модель только формирует запрос. Поэтому безопасность обеспечивается на стороне программы: permissions, подтверждения, hooks, ограничения tools агента.
3. **Что попадает в основной context.** Задание, которое основная сессия передала subagent, и итоговый ответ subagent. Не попадают: файлы, которые он прочитал, промежуточные шаги, его рассуждения.
4. **`tools` vs фраза.** Без Edit/Write агент физически не может изменить файл; фразу модель обычно соблюдает, но гарантии нет (ошибка, двусмысленная задача, обманный текст в данных).
5. **«Когда», а не «что».** Основная сессия решает, звать ли агента, сравнивая текущую задачу с `description`. «Используй после правок кода, перед коммитом» совпадает с реальными ситуациями; «Агент для ревью» — слишком абстрактно.
6. **Когда subagent хуже.** Маленькая задача (накладные расходы больше работы); задача требует контекста долгого разговора; нужна быстрая реакция; ограниченный бюджет; неясная постановка.
7. **Передача в цепочке.** Основная сессия-оркестратор: вызывает агентов по очереди, читает результат и формулирует задание следующему. Способы: через текст задания или через файл (`plan.md`), который переживает `/clear` и может быть отредактирован человеком.
8. **Subagent vs skill.** Skill загружает инструкцию в **текущий** context и выполняется той же сессией. Subagent — **отдельный** исполнитель со своим context, system prompt, tools и моделью, возвращает только итог.
