# Рубрика модуля 07

## Упражнение 1. Анатомия skills курса

**Критерии**
- Обязательные: названы поля `name`, `description`, `argument-hint` и их назначение; объяснена обработка пустого аргумента в `check`; понятна роль слов-триггеров; плохой `description` с правдоподобным сценарием провала.
- Желательные: студент заметил, что тело skill — пошаговая процедура с форматом ответа; связал `description` с автоматическим вызовом.

**Эталон**
- Поля: `name` — имя и команда `/check`; `description` — что делает и когда применять (по нему Claude выбирает skill без явного `/check`); `argument-hint` — подсказка `[модуль.упражнение]` при наборе команды.
- `check`: `$ARGUMENTS` — идентификатор `MM.N`; если пусто — берётся текущее упражнение из `PROGRESS.md` и уточняется у студента.
- Слова-триггеры в `check`: «готово», «проверь», «сделал упражнение», «/check 03.2» — это фразы, которыми студент реально просит проверку; без них Claude может не связать «готово!» с проверкой.
- `disable-model-invocation`: ни один — оба skill не делают необратимых действий, а автоматический вызов («не получается» → `hint`) — главное удобство для студента. Приемлем и ответ «check», если обоснован (например, «проверка обновляет PROGRESS.md — пусть запускается только по явной просьбе»).
- Плохой `description` для `hint`: «Подсказки.» → на «я застрял, не понимаю что делать» Claude не свяжет запрос с skill и, скорее всего, просто выдаст решение — нарушив принцип «не делай работу за студента».

**Частые ошибки**
- *Перечисляет поля, не объясняя зачем.* → Спроси: «Что изменится, если убрать `argument-hint`? А `description`?» — второе ломает автоматический вызов, первое — только удобство.
- *Считает, что Claude читает тело skill, чтобы решить, вызывать ли его.* → Это важная ошибка: до вызова виден только `description`. Вернись к разделу 6 (progressive disclosure).

## Упражнение 2. Skill `commit-message`

**Критерии**
- Обязательные: правильный путь и вызов; динамический контекст с `git diff --staged`; осмысленная обработка B (ничего не добавлено) и C (несвязанные изменения); `allowed-tools` только на чтение; закоммичен.
- Желательные: `git log --oneline -5` для стиля; правила не дублируют CLAUDE.md дословно, а ссылаются/дополняют; формат результата (блок для копирования).

**Эталон** (`.claude/skills/commit-message/SKILL.md`)

```markdown
---
name: commit-message
description: Предложить сообщение коммита для изменений, уже добавленных через git add. Используй, когда пользователь просит придумать, написать или улучшить commit message.
allowed-tools: Bash(git diff *) Bash(git log *) Bash(git status *)
---

# Сообщение коммита

## Подготовленные изменения
!`git diff --staged`

## Статус
!`git status --short`

## Последние коммиты (ориентир по стилю)
!`git log --oneline -5`

## Как действовать
1. Если раздел «Подготовленные изменения» пуст — скажи, что в коммит ничего не добавлено,
   и подскажи `git add <файл>`. Сообщение не придумывай.
2. Если изменения решают несколько несвязанных задач — перечисли их и предложи разбить
   на отдельные коммиты (с вариантом сообщения для каждого).
3. Иначе предложи одно сообщение:
   - первая строка ≤ 50 символов, по-русски, повелительное наклонение («Исправить…», «Добавить…»);
   - если причина неочевидна — пустая строка и 1–3 строки «почему».
4. Выведи сообщение в блоке кода, чтобы его было удобно скопировать.
5. Коммит не выполняй — только предложи.
```

Ожидаемые результаты: A — одно сообщение вида «Исправить подпись срока в выводе задач»; B — «В коммит ничего не добавлено, выполни git add …»; C — «Здесь два несвязанных изменения: …; предлагаю два коммита: …».

**Частые ошибки**
- *`git diff` вместо `git diff --staged`.* → Покажет незакоммиченные, но не добавленные изменения; сообщение будет описывать не то, что попадёт в коммит. Попроси прогнать ситуацию «одно добавлено, другое — нет».
- *`allowed-tools: Bash(*)` или с `git commit`.* → Skill разрешает лишнее без подтверждения: принцип минимальных прав. Для skill, который только предлагает, `git commit` не нужен совсем.
- *Нет обработки пустого diff.* → В B Claude выдумывает сообщение «на основе разговора» — это ровно та hallucination, от которой защищает явная инструкция.
- *Правила коммитов скопированы из CLAUDE.md целиком.* → Две копии разойдутся. Варианты: оставить в CLAUDE.md коротко, а в skill — подробно; или только в skill, если коммиты делаются через него.
- *Тестировал в той же сессии, где писал skill.* → Claude «помнит» замысел; новая сессия честнее.

## Упражнение 3. Skill с аргументами: `bug-report`

**Критерии**
- Обязательные: `$ARGUMENTS`, обработка пустого вызова; воспроизведение на временном `TODO_FILE`; отчёт с шагами, ожидаю/вижу, результатом; код не меняется; есть `argument-hint`.
- Желательные: формат имени файла отчёта; предполагаемое место в коде с оговоркой «предположение»; `todos.json` не изменён (проверено `git status`).

**Эталон** (`.claude/skills/bug-report/SKILL.md`)

```markdown
---
name: bug-report
description: Воспроизвести баг todo-app по описанию симптома и оформить bug report в папке bugs/. Используй, когда пользователь описывает странное поведение программы или просит оформить баг. Код не исправляет.
argument-hint: "<описание симптома своими словами>"
---

# Bug report

Симптом от пользователя: $ARGUMENTS

Если симптом не указан — спроси, что случилось и какой командой, и остановись.

## Шаги
1. Сформулируй гипотезу: какая команда todo.py покажет проблему.
2. Воспроизводи ТОЛЬКО на временном файле данных, не на todos.json (это живые данные):
   PowerShell: `$env:TODO_FILE = "bug-tmp.json"`; bash: `TODO_FILE=bug-tmp.json python todo.py ...`.
   Наполни его командами add/done, нужными для воспроизведения.
3. Запиши точные команды и их вывод.
4. Посмотри код и укажи вероятное место (файл, функция) — как предположение, не как факт.
5. Создай `bugs/<короткое-имя-через-дефисы>.md` по шаблону:

   # <краткое название бага>
   **Симптом:** ...
   **Шаги воспроизведения:** 1. ... 2. ...
   **Ожидаю:** ...  **Вижу:** ...
   **Воспроизведено:** да / нет (что пробовал)
   **Вероятное место:** файл, функция — почему так думаю

6. Удали временный файл данных.

## Не делай
- Не исправляй код — задача только описать баг; исправление — отдельным шагом после обсуждения.
- Не трогай todos.json.
```

**Частые ошибки**
- *Skill чинит баг «раз уж нашёл».* → Нужна явная строка «не исправляй» с причиной. Объясни: смешение диагностики и правки — ровно то, от чего предостерегал модуль 05.
- *Воспроизведение на `todos.json`.* → `git status` после вызова покажет изменения в данных. Напомни правило из CLAUDE.md и попроси явно прописать `TODO_FILE` в skill.
- *Нет обработки пустого `$ARGUMENTS`.* → Без него Claude начинает искать «какой-нибудь» баг.
- *Синтаксис переменной окружения только для bash.* → На Windows студент запускает Claude Code, который использует Git Bash, — bash-вариант обычно работает; но если skill объясняет команды пользователю, стоит дать оба.

## Упражнение 4. Skill со скриптом: `todo-report`

**Критерии**
- Обязательные: скрипт работает отдельно, учитывает `TODO_FILE`, обрабатывает отсутствие файла; цифры отчёта совпадают с выводом скрипта; явный запрет пересчитывать; `allowed-tools` ограничен скриптом; объяснение progressive disclosure.
- Желательные: скрипт без внешних зависимостей; сверка со `stats`; отчёт для нетехнического читателя.

**Эталон**

`.claude/skills/todo-report/SKILL.md`:
```markdown
---
name: todo-report
description: Подготовить еженедельный отчёт по задачам todo-app для руководителя — сколько сделано, что просрочено, что горит на этой неделе. Используй, когда просят отчёт, сводку или статус по задачам.
allowed-tools: Bash(python .claude/skills/todo-report/scripts/report.py*)
---

# Отчёт по задачам

1. Запусти `python .claude/skills/todo-report/scripts/report.py`.
   Если скрипт завершился ошибкой — покажи её пользователю и остановись.
2. Используй ТОЛЬКО цифры из вывода скрипта. Не пересчитывай и не читай todos.json сам:
   скрипт считает точно, а пересчёт «в уме» даёт расхождения.
3. Формат (для руководителя, без технических терминов):
   - 3 главных вывода одной строкой каждый;
   - таблица: Всего / Выполнено / Открыто / Просрочено;
   - «На что обратить внимание»: просроченные и задачи на ближайшую неделю, high — первыми.
```

`.claude/skills/todo-report/scripts/report.py` (проверен):
```python
"""Посчитать цифры для еженедельного отчёта по todos.json (или файлу из TODO_FILE)."""

import json
import os
import sys
from datetime import date, timedelta
from pathlib import Path

sys.stdout.reconfigure(encoding="utf-8")

path = Path(os.environ.get("TODO_FILE", "todos.json"))
if not path.exists():
    print(f"Файл {path} не найден")
    sys.exit(1)

tasks = json.loads(path.read_text(encoding="utf-8"))
today = date.today()
week_end = today + timedelta(days=7)
open_tasks = [t for t in tasks if not t["done"]]


def due(t):
    return date.fromisoformat(t["due"]) if t["due"] else None


overdue = [t for t in open_tasks if due(t) and due(t) < today]
this_week = [t for t in open_tasks if due(t) and today <= due(t) <= week_end]

print(f"Дата: {today}")
print(f"Всего: {len(tasks)}, выполнено: {len(tasks) - len(open_tasks)}, открыто: {len(open_tasks)}")
for p in ("high", "medium", "low"):
    print(f"Открыто {p}: {sum(1 for t in open_tasks if t['priority'] == p)}")
print(f"Просрочено ({len(overdue)}):")
for t in overdue:
    print(f"  #{t['id']} [{t['priority']}] {t['title']} — срок {t['due']}")
print(f"Срок в ближайшие 7 дней ({len(this_week)}):")
for t in sorted(this_week, key=lambda t: t["due"]):
    print(f"  #{t['id']} [{t['priority']}] {t['title']} — срок {t['due']}")
```

Progressive disclosure (шаг 6): до вызова в context — только `name`/`description` skill; после — тело `SKILL.md` и **вывод** скрипта; сам код `report.py` в context не попадает (если Claude его не открывал).

**Частые ошибки**
- *Скрипт импортирует `models.py`.* → Работает, но связывает skill с внутренним устройством кода; при рефакторинге отчёт сломается. Приемлемо, если студент понимает компромисс.
- *Нет запрета пересчитывать.* → Claude может «перепроверить» и выдать другие цифры. Покажи расхождение, если оно случилось, — лучший аргумент.
- *`allowed-tools: Bash(python *)`.* → Разрешает запуск любого Python-кода без подтверждения. Ограничь конкретным скриптом.
- *Студент не понимает свой скрипт («написал Claude»).* → Попроси объяснить строки с `overdue` и `this_week`. Принцип курса: в проект попадает только понятный тебе код.
- *Путь к скрипту не находится.* → `claude` запущен не в корне проекта. Объясни, что путь относительный.

## Упражнение 5. Отладка `description`

**Критерии**
- Обязательные: 5 запросов (3 «да», 2 «нет») без имени skill; каждый в чистой сессии; итоговый `description` с «что» и «когда» и словами из запросов; прогон 2 лучше, остаток объяснён.
- Желательные: маркер в результате как объективный признак срабатывания; граница с соседними задачами («не для перевода/правки текста»).

**Эталон**

Итоговый `description`:
```yaml
description: Оформить протокол встречи из сырых заметок — участники, решения, задачи (кто, что, срок), открытые вопросы. Используй, когда пользователь присылает заметки, конспект или расшифровку встречи, планёрки или созвона и просит протокол, итоги, решения или «кто что делает». Не для перевода и не для исправления опечаток.
```

Пример таблицы:

| Запрос | Должен? | Прогон 1 | Прогон 2 |
|--------|---------|----------|----------|
| «вот заметки со встречи @meeting-notes.txt — сделай итоги» | да | нет | да |
| «кто что должен сделать после этой планёрки? @meeting-notes.txt» | да | нет | да |
| «оформи протокол созвона из @meeting-notes.txt» | да | да | да |
| «исправь опечатки в @meeting-notes.txt» | нет | да (!) | нет |
| «переведи заметки на английский» | нет | нет | нет |

Вывод: «С описанием "Помогает с текстами" skill срабатывал на любые тексты, включая исправление опечаток, и не срабатывал на "итоги". После добавления "что/когда", слов пользователя и границы — 5/5».

Примечание: срабатывание недетерминированно; 4/5 в прогоне 2 с внятным объяснением — тоже принимаемый результат.

**Частые ошибки**
- *Запросы содержат слово из имени skill («сделай meeting protocol»).* → Тогда проверяется не `description`. Попроси переформулировать.
- *Все запросы в одной сессии.* → Первый вызов skill остаётся в context и влияет на следующие ответы.
- *Улучшали тело skill, а не `description`.* → До вызова Claude тело не видит — правки тела не влияют на выбор.
- *Description на полстраницы со всеми синонимами.* → Он занимает context в каждой сессии; нужно 1–3 предложения.
- *Нет «отрицательных» запросов.* → Без них не видно, что широкий description срабатывает лишний раз.

## Упражнение 6. ⭐ Personal skill для своей рутины

**Критерии**
- Обязательные: `~/.claude/skills/<name>/`, работает в двух папках; вспомогательный файл со ссылкой из `SKILL.md`; обоснованные решения о frontmatter; автоматический вызов на ≥ 2 фразах; нет реальных персональных данных.
- Желательные: учтено ревью Claude; скрипт для точной части, если она есть.

**Эталон** (пример: еженедельное письмо-статус руководителю)

```text
~/.claude/skills/status-email/
  SKILL.md
  example.md      ← пример идеального письма (вымышленные данные)
```

```markdown
---
name: status-email
description: Написать еженедельное письмо-статус руководителю по моим заметкам за неделю. Используй, когда я прошу статус, отчёт за неделю или письмо руководителю об итогах недели.
argument-hint: "[файл или папка с заметками за неделю]"
disable-model-invocation: false
---

# Письмо-статус

Вход: $ARGUMENTS. Если пусто — спроси, где заметки за неделю.

1. Прочитай заметки. Выдели: сделано, в работе, риски, нужна помощь.
2. Оформи по образцу из файла example.md рядом с этим SKILL.md (тон, длина, структура).
3. Письмо ≤ 150 слов: руководитель читает его с телефона.
4. Не обещай сроков, которых нет в заметках — лучше вопрос в конце письма.
5. Выведи тему и текст письма. Не отправляй и не сохраняй никуда без просьбы.
```

Обоснования: аргумент — путь к заметкам, т.к. они лежат в разных местах; `disable-model-invocation` не нужен — skill только пишет текст, ничего не отправляет; скрипт не нужен — нет точных вычислений.

**Частые ошибки**
- *Реальные имена клиентов/коллег в `example.md`.* → Заменить на вымышленные; файл может уйти в чужой context и в git.
- *Ссылка на вспомогательный файл не работает (Claude не нашёл).* → Уточнить формулировку: «файл example.md в папке этого skill» и проверить, что Claude его действительно читает.
- *Skill делает необратимое (отправка, удаление) без `disable-model-invocation`.* → Обсуди риск автоматического вызова.

## Quiz

1. **Что Claude «видит» о skill, пока тот не вызван?**
   → Только `name` и `description`. → Поэтому вся логика выбора skill держится на `description`; тело на выбор не влияет.
2. **Зачем в skill строка `` !`git diff --staged` ``?**
   → Вывод команды подставляется в skill перед загрузкой — Claude сразу видит актуальные данные. → Экономит шаги и исключает работу по устаревшему контексту.
3. **Чем skill лучше раздела в CLAUDE.md для процедуры «как готовить отчёт»?**
   → Тело skill грузится только при вызове, CLAUDE.md — всегда; skill может содержать скрипты и шаблоны. → Экономия context и порядок: процедура нужна в одной задаче из многих.
4. **Почему точные вычисления лучше отдать скрипту внутри skill?**
   → Скрипт детерминирован и точен; LLM может ошибиться в арифметике и выдать разные цифры в разных прогонах. → В context попадает только вывод скрипта — дешевле, чем вся таблица.
5. **Ситуация: `/meeting-protocol` работает, но на «сделай итоги встречи» Claude skill не применяет. Что сделаешь?**
   → Доработать `description`: «что» + «когда» + слова пользователя («итоги», «планёрка»); проверить набором фраз в новых сессиях. → Тело skill не трогать — его Claude при выборе не видит.
6. **Ситуация: коллега сделал skill `deploy`, и Claude однажды запустил его сам посреди обсуждения. Как предотвратить?**
   → `disable-model-invocation: true` — только ручной вызов. → Для действий с последствиями удобство автоматики не стоит риска.
7. **Ситуация: в skill написано `allowed-tools: Bash(*)`. Что не так?**
   → Любые команды выполняются без подтверждения, пока skill активен. → Принцип минимальных прав: перечисли только нужные команды (`Bash(git diff *)`).
8. **Ситуация: ты используешь один и тот же skill во всех проектах, но он лежит в `.claude/skills` одного проекта. Что сделаешь?**
   → Перенести в `~/.claude/skills/<name>/` (personal). → Project skills — для процессов проекта и команды, personal — для твоих личных процессов.

## Ответы на «Вопросы для самопроверки» из README

1. Только `name` и `description` (они всегда в context). Поэтому `description` должен сам по себе объяснять «что» и «когда» — иначе Claude не поймёт, что skill подходит.
2. Раздел в CLAUDE.md загружается в каждую сессию целиком; skill — только при вызове и может включать файлы и скрипты. Короткие универсальные правила — CLAUDE.md; процедуры для конкретных задач — skill.
3. Коммит — действие с последствиями; без флага Claude может сам вызвать skill и закоммитить незаконченную работу. Флаг оставляет решение за человеком.
4. Скрипт считает точно и одинаково; модель может ошибиться и не предупредить. Плюс в context идёт только итоговый вывод, а не вся таблица.
5. Выполняет `git diff --staged` и подставляет вывод в текст skill; выполняется при вызове skill, до того как модель получит инструкцию.
6. Менять `description`: добавить «когда» и слова пользователя («итоги», «встреча», «планёрка»), границы. Проверить набором из подходящих и неподходящих фраз, каждую — в новой сессии; сравнить результаты до и после.
7. Явно прописать в теле: «Если `$ARGUMENTS` пусто — спроси …» (или задать разумное поведение по умолчанию). Иначе Claude начнёт угадывать.
8. Personal (`~/.claude/skills/`) — доступен тебе во всех проектах, не попадает в git проекта; project (`.claude/skills/`) — едет вместе с проектом и доступен команде. Личные рутины — personal, процессы проекта — project.
