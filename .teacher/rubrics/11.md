## Упражнение 1. Идея и бриф

**Критерии**
- Обязательные: задача повторяющаяся и своя; измеримый критерий успеха; раздел «Вне рамок»; тестовые данные без ПДн.
- Желательные: 3 кандидата с оценкой; интервью с Claude проведено; оценка «как сейчас» в минутах.

**Эталон** (`BRIEF.md`):

```markdown
# Бриф: еженедельная сводка по заявкам

## Задача
Каждый понедельник я делаю для руководителя сводку по заявкам клиентов за неделю: сколько пришло, по каким темам, что просрочено, что требует решения. Хочу, чтобы Claude делал черновик сводки за минуты.

## Пользователь
Я (менеджер поддержки «ООО Ромашка», вымышл.), понедельник утром; читатель сводки — руководитель отдела, читает с телефона.

## Как сейчас
1. Выгружаю заявки из CRM в CSV (5 мин). 2. Фильтрую и считаю в Excel (20 мин). 3. Читаю тексты просроченных (15 мин). 4. Пишу письмо (15 мин). Итого ~55 мин. Боль: шаг 3 и ошибки в подсчётах.

## Входные данные
CSV: id, дата, клиент, тема, статус, срок, текст. ~150 строк в неделю. Чувствительно: имена клиентов, тексты. Для проекта — обезличенная выгрузка (клиенты «Клиент-001…», тексты переписаны).

## Результат
`reports/YYYY-MM-DD.md`: 5–7 пунктов + таблица просроченных + 3 вопроса на решение.

## Критерий успеха
Черновик сводки ≤ 10 мин (вместо 55), 0 ошибок в цифрах на 3 тестовых неделях.

## Вне рамок
Автоматическая отправка письма; подключение к реальной CRM; ответы клиентам.
```

**Частые ошибки**
- *Тема слишком широкая* («автоматизировать поддержку») — **почему плохо:** не помещается в 10 часов, проект не будет доведён. Помоги сузить до одного процесса вопросом «что из этого ты делаешь каждую неделю?».
- *Критерий «станет удобнее»* — неизмерим. **Почему важно:** без измеримого критерия на ретро невозможно честно сказать, получилось ли.
- *Реальные выгрузки с именами клиентов* — остановить. **Почему:** данные уходят в модель; политика компании; орг-правила курса. Помочь сделать обезличенную версию той же структуры.
- *Бриф написал Claude целиком* — спроси 2–3 вопроса по брифу; если студент не может ответить, пусть перепишет своими словами.

## Упражнение 2. План и архитектура

**Критерии**
- Обязательные: все компоненты; обоснование каждого с альтернативой; ≥ 3 риска с мерами; послойный порядок; видна доработка предложения Claude.
- Желательные: поток данных; permissions; черновик демо.

**Эталон** (`PLAN.md`, фрагмент):

```markdown
## Компоненты
| Компонент | Имя | Что делает | Почему этот механизм |
|---|---|---|---|
| CLAUDE.md | — | структура папок, правило «data/ только чтение», стиль сводки | нужно в каждой сессии; коротко |
| Skill | /weekly-report <дата> | собирает сводку за неделю по шаблону | повторяемый процесс с параметром; в той же сессии, чтобы я мог сразу править |
| Skill | /overdue-digest | разбор текстов просроченных заявок → 1 строка на каждую | отдельный процесс, нужен и вне отчёта |
| Subagent | numbers-checker (Read, Grep, Glob + MCP tools) | перепроверяет все числа сводки по данным | независимая проверка: свежий context, не «влюблён» в черновик; read-only |
| MCP (свой, FastMCP) | tickets | tools: count_by(field, week), list_overdue(week) | точные подсчёты кодом, а не «на глаз» моделью; Claude не читает весь CSV |
| Hook PreToolUse | protect_data.py | блокирует Edit/Write в data/ | сырьё нельзя менять никогда — нужна гарантия, а не просьба |

Альтернатива для подсчётов: skill со скриптом. Отказался: MCP tools доступны и subagent-у, и в любом запросе, а не только внутри skill.

## Риски
1. Claude ошибается в цифрах → считать через MCP tools + numbers-checker.
2. Prompt injection в текстах заявок → тексты в тегах, deny на сетевые команды, default mode при первом прогоне.
3. Формат CSV изменится → MCP server проверяет колонки и возвращает понятную ошибку.
```

**Частые ошибки**
- *Subagent дублирует skill* (агент «пишет отчёт» и skill «пишет отчёт») — **почему плохо:** нет причины для изоляции; спроси «что сломается, если убрать агента?».
- *MCP «для галочки»* (подключён filesystem server к папке, которую Claude и так читает) — **почему плохо:** не решает проблему, которой нет без него. Спроси, к каким данным у Claude нет доступа или где нужна точность кода.
- *Hook, который можно заменить одной строкой deny, без объяснения выбора* — не ошибка, но нужно обоснование (подсказка Claude через stderr, логика). Иначе — предложи deny и спроси, чем hook лучше.
- *Нет рисков, связанных с данными* — **почему важно:** реальная задача = реальные данные; безопасность — часть архитектуры.
- *План = предложение Claude без изменений* — спроси, какую альтернативу Claude предложил и почему она отвергнута.

## Упражнение 3. Фундамент и skills

**Критерии**
- Обязательные: CLAUDE.md краткий, без секретов и очевидного; 2+ skills, один с аргументами/скриптом; проверены явным вызовом, один — автоматически; permissions; коммиты.
- Желательные: `TESTING.md` с итерациями description; правило CLAUDE.md проверено на `/clear`.

**Эталон** — `CLAUDE.md` (фрагмент):

```markdown
# Сводки по заявкам

Проект готовит еженедельные сводки по заявкам клиентов для руководителя.

## Структура
- data/ — выгрузки CSV. ТОЛЬКО ЧТЕНИЕ (защищено hook) — это исходники, их не восстановить.
- reports/ — результаты, файл на неделю: reports/YYYY-MM-DD.md.
- mcp/tickets_server.py — MCP server для подсчётов.

## Правила
- Все числа в сводке — только из MCP tools tickets (count_by, list_overdue), не считай сам: так меньше ошибок.
- Пиши для чтения с телефона: пункты ≤ 2 строк, без таблиц шире 4 колонок.
- Имена клиентов в сводку не выносить — только id.
```

Skill (`.claude/skills/weekly-report/SKILL.md`):

```markdown
---
name: weekly-report
description: Подготовить еженедельную сводку по заявкам. Используй, когда просят "сводку за неделю", "отчёт по заявкам", "weekly report", с датой понедельника или без.
argument-hint: "[YYYY-MM-DD понедельник недели]"
---
Неделя: $ARGUMENTS (если пусто — текущая неделя, спроси подтверждение).

1. Получи числа через MCP tools tickets: count_by("status", неделя), count_by("topic", неделя), list_overdue(неделя).
2. Для просроченных используй /overdue-digest.
3. Напиши reports/<дата>.md по шаблону template.md (в этой папке).
4. Попроси subagent numbers-checker сверить все числа. Исправь расхождения.
5. В конце покажи: путь к файлу и 3 вопроса на решение руководителя.
```

`TESTING.md` (фрагмент): «/weekly-report 2026-09-28 — ОК. Авто: "сделай сводку за прошлую неделю" — сработал. "что там с заявками" — не сработал; добавил в description "что с заявками", повторил — сработал».

**Частые ошибки**
- *CLAUDE.md из `/init` без сокращения* (100+ строк, описание каждого файла) — **почему плохо:** каждая строка тратит context в каждой сессии; то, что видно из кода, Claude найдёт сам.
- *Skill без проверки автоматического вызова* — **почему важно:** description — главная часть skill; без проверки неизвестно, будет ли он срабатывать в реальной работе.
- *Оба skill без аргументов и скриптов* — требование не выполнено; помоги найти, где параметр естественен (дата, файл, клиент).
- *Нет коммитов по этапам* — **почему важно:** точки отката и видимая история работы для защиты.

## Упражнение 4. MCP, subagent, hook

**Критерии**
- Обязательные: MCP подключён, tools работают, секретов в файлах нет; subagent с ограниченными tools и форматом; hook проверен вручную и в сессии; сквозной сценарий; отклонения от плана записаны.
- Желательные: scope MCP обоснован; subagent использует MCP tools; hook устойчив к битому входу.

**Эталон** — MCP tool (фрагмент своего FastMCP server):

```python
from mcp.server.fastmcp import FastMCP
import csv
from pathlib import Path

mcp = FastMCP("tickets")
DATA = Path(__file__).resolve().parent.parent / "data" / "tickets.csv"


@mcp.tool()
def count_by(field: str, week_start: str) -> dict[str, int]:
    """Посчитать заявки за неделю, начиная с week_start (YYYY-MM-DD), сгруппировав по полю field (status, topic)."""
    ...


if __name__ == "__main__":
    mcp.run()
```

Подключение (project scope — чтобы коллега получил его вместе с репозиторием):
`claude mcp add --transport stdio --scope project tickets -- python mcp/tickets_server.py`

Subagent `numbers-checker.md`:

```markdown
---
name: numbers-checker
description: Сверяет все числа в черновике сводки с данными. Используй после создания или изменения файла в reports/.
tools: Read, Grep, Glob, mcp__tickets__count_by, mcp__tickets__list_overdue
model: haiku
---
Ты проверяешь числа в сводке. Для каждого числа в указанном файле получи значение через MCP tools tickets и сравни.
Ответ: таблица «утверждение | в сводке | по данным | ОК/расхождение». Ничего не исправляй.
Если число нельзя проверить имеющимися tools — пометь «не проверяемо».
```

(Если перечисление MCP tools в `tools` не сработало в версии студента — проверить docs/`/agents`; альтернатива — не указывать `tools` и ограничить роль в prompt, с пометкой о компромиссе.)

Hook `protect_data.py` — как `protect_files.py` из модуля 10, но проверка «путь внутри data/». Ручная проверка: `echo '{"tool_name":"Write","tool_input":{"file_path":"data/tickets.csv"}}' | python .claude/hooks/protect_data.py` → 2.

**Частые ошибки**
- *Токен MCP server в `.mcp.json` в git* — **почему плохо:** утечка через репозиторий; токен нужно отозвать и перевыпустить; использовать `--env` / переменные окружения.
- *Subagent без ограничения tools «на всякий случай»* — **почему плохо:** проверяющий, который может править, перестаёт быть независимым.
- *Hook проверен только в сессии* — если не сработал, непонятно, проблема в скрипте или в подключении. Сначала вручную.
- *Сквозной сценарий не прогнан, компоненты проверены по отдельности* — **почему важно:** проблемы чаще на стыках (skill вызывает tool, который subagent не видит).
- *MCP server падает на первом же вызове из-за пути к данным* — относительный путь считается от папки запуска; в эталоне путь от `__file__`.

Хуже ожиданий: автоматический вызов /overdue-digest — срабатывает в 1 из 3 случаев. Иначе: начал бы с MCP, а не со skills; сделал бы шаблон сводки раньше».

### Защита: банк вопросов

Задай 5–8 вопросов, выбирая по компонентам проекта студента. Ищи ответы про **компромисс и альтернативу**, а не пересказ.

| Вопрос | Хороший ответ содержит |
|--------|------------------------|
| Почему это skill, а не строчка в CLAUDE.md? | процесс нужен не всегда → не тратить context каждой сессии; есть шаги/шаблон/аргументы |
| Почему это subagent, а не skill? | изоляция context / независимость проверки / ограничение tools; цена — не видит разговора |
| Почему у агента именно эти tools и эта model? | минимум для роли; замок vs просьба; цена/скорость модели |
| Почему hook, а не deny (или наоборот)? | логика/подсказка Claude vs простота; гарантия vs просьба в CLAUDE.md |
| Что будет, если MCP server недоступен? | как ведёт себя skill/агент; есть ли понятная ошибка; fallback |
| Какой scope у MCP и почему? | project — для команды через `.mcp.json`; local — личное/с секретами |
| Где в проекте риск prompt injection и что защищает? | какие данные чужие; слои: теги, deny, режим, ревью |
| Как ты понял, что проект работает «из коробки»? | демо на свежей сессии / в чистой папке |
| Что сломается первым, если данных станет в 10 раз больше? | context, скорость hooks, подсчёты в модели vs в коде |
| Что бы ты убрал, если бы нужно было сократить проект вдвое? | понимание ценности компонентов |
| Что изменится, если проектом будет пользоваться команда? | project vs local settings, README, plugin, permissions для всех |

Ответ «так предложил Claude» без собственного аргумента — повод для уточняющего вопроса: «А какую альтернативу ты рассматривал? Чем она хуже в твоём случае?». Защита пройдена, если на большинство вопросов есть содержательный ответ про компромисс.

**Частые ошибки**
- *Демо на той же сессии, где всё настраивалось* — **почему плохо:** накопленный context маскирует проблемы (Claude «помнит» договорённости, которых нет в CLAUDE.md/skills).
- *README без переменных окружения или с их значениями* — либо не запустится, либо утечка.
- *Ретро «всё получилось»* — попроси назвать одну вещь, которая сработала хуже ожиданий. **Почему важно:** навык честной оценки — основа дальнейших доработок.
- *Секреты/ПДн в истории git* — не принимать до очистки; объяснить, что удаление файла не удаляет историю.

## Quiz

Финальный quiz — сквозной по курсу.

1. **Каждый раз объясняешь Claude, как оформлять протокол встречи. Какой механизм?**
   → Skill (процесс, нужен не всегда, возможно с шаблоном).
   → Почему: CLAUDE.md тратил бы context в каждой сессии; subagent не нужен — работа в текущем разговоре.

2. **Нужно, чтобы Claude никогда не удалял файлы в папке `archive/`. Что выберешь?**
   → deny-правило (или PreToolUse hook, если нужна логика/подсказка), а не фраза в CLAUDE.md.
   → Почему: «никогда» требует гарантии, а не просьбы.

3. **Claude ошибается в подсчётах по большой таблице. Что сделаешь?**
   → Перенесу подсчёт в код: скрипт в skill или MCP tool; модель интерпретирует результат.
   → Почему: детерминированные вычисления надёжнее кодом; меньше данных в context.

4. **Чем subagent отличается от skill?**
   → Отдельный context, свой system prompt, tools, модель; возвращает только итог. Skill работает в текущем context.
   → Почему: выбор между «научить себя» и «поручить другому».

5. **Ситуация: проект работает у тебя, но не у коллеги — skill не срабатывает автоматически. Что проверишь?**
   → `description` (формулировки коллеги), что skill в project-папке, а не в `~/.claude/skills/`, версии и установку компонентов.
   → Почему: автоматический вызов зависит от совпадения запроса с description; личные skills коллеге не видны.

6. **Ситуация: в демо Claude всё сделал, но в новой сессии забыл правило оформления. Почему и что сделаешь?**
   → Правило было только в разговоре, а не в CLAUDE.md/skill; перенесу в подходящий файл и проверю на `/clear`.
   → Почему: у Claude нет памяти между сессиями, кроме файлов.

7. **Ситуация: нужно подключить сервис компании с токеном. Как сделаешь безопасно?**
   → Токен через env (`--env` / переменная окружения), не в `.mcp.json`/git; проверить, разрешено ли политикой компании; минимальные права токена.
   → Почему: файлы конфигурации расходятся по копиям и репозиториям.

8. **Ситуация: ты хочешь, чтобы сводка генерировалась каждое утро без тебя. Как?**
   → Headless-скрипт (`claude -p`), данные собирает скрипт, нужные действия — через узкие allow; запуск планировщиком ОС.
   → Почему: в headless некому подтверждать; детерминированные шаги — кодом.

## Ответы на «Вопросы для самопроверки» из README

Вопросы модуля 11 — о проекте студента, поэтому эталонных ответов нет. Оценивай по признакам хорошего ответа:

1. **Задача.** Названы частота (≥ раз в неделю) и время «как сейчас»; понятно, какая часть автоматизируется и почему именно она.
2. **Проблема каждого компонента.** Для каждого — конкретный пример из проекта («без MCP Claude ошибся в 2 из 7 чисел»), а не общие слова («для удобства»).
3. **Skill vs subagent.** Аргумент про context (свой или общий), независимость проверки, ограничение tools, цену; названа отвергнутая альтернатива.
4. **Hook.** Нужна гарантия (а не просьба в CLAUDE.md); сравнение с deny — что hook даёт сверх (логика, подсказка через stderr) или почему deny был бы достаточен.
5. **Чувствительные данные.** Названы конкретные поля/файлы; меры: обезличивание, `.env` + deny, read-only сырьё, проверка истории git.
6. **Свежая сессия.** Демо на `/clear` или новой сессии/чистой папке; что выяснилось.
7. **Команда из 5 человек.** project vs local settings, `.mcp.json` в git без секретов, README/plugin для установки, общие permissions, кто поддерживает и версионирует.
